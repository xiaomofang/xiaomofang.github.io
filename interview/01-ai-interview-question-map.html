大模型技术面试题整理

模型基础、推理系统、分布式部署、RAG、Agent 与线上排障。

模型基础推理核心工程排障

一、模型基础：先讲清楚模型在算什么

Q01—Q12 · 生成流程、Attention、位置编码、归一化与微调。

Q01 · ★★★★★从输入一个 Token 开始，Decoder-only Transformer 如何生成下一个 Token？

完整数据流：文本先由 Tokenizer 切成 token 并映射为整数 id；Embedding Table 把每个 id 查成 hidden vector。进入每一层 Decoder Block 后，向量先经过 Norm，再生成 Q/K/V。Q 与当前可见前缀的 K 做缩放点积，叠加 Causal Mask 后经 Softmax 得到权重，再对 V 加权求和；Attention 输出经过 O Projection 和残差连接，随后通过 Norm、FFN/SwiGLU 和第二次残差连接。多层堆叠后，最后一个位置的 hidden state 经 Final Norm 与 LM Head 投影到词表维度，得到每个候选 token 的 logits。

生成阶段：logits 经 repetition penalty、Temperature、Top-k/Top-p 等规则处理后形成概率分布，选择或采样下一个 token。新 token 被拼回上下文，模型重复这一过程，直到生成 EOS、命中停止词或达到长度上限。

Prefill 与 Decode 的区别：第一次可以并行处理完整 Prompt 并建立各层 KV Cache；之后每一步只输入最新 token，计算它的新 Q/K/V，历史 K/V 直接从 Cache 读取。这样避免反复重算整个前缀，但生成步骤之间仍有自回归依赖。

常见追问：为什么只使用最后一个位置的 logits？训练时每个位置都预测其下一个 token；在线生成时，前面位置的预测已经完成，当前只需要前缀末端的条件分布。
Q02 · ★★★★★Self-Attention 的 Q、K、V 分别是什么？

公式：给定输入 X，线性投影得到 Q=XWq、K=XWk、V=XWv，随后计算 Attention(Q,K,V)=softmax(QKᵀ/√dₖ+M)V。M 在 Decoder 中是 Causal Mask，把未来位置的分数置为负无穷。

作用：Q 表示当前位置正在寻找什么信息；K 表示每个位置可用什么特征被匹配；QKᵀ产生两两相关性，只决定“从哪里取”；V 承载真正要汇聚的内容，决定“取到什么”。将 K 和 V 分开，使模型可以用一种表示做寻址、用另一种表示传递信息。

多头的意义：不同 Head 使用不同投影子空间，可以并行学习局部依赖、指代、语法、主题等不同关系。Head 不是越多越好，因为固定 hidden size 下，Head 越多意味着每个 Head 的维度越小，还会增加调度和实现开销。

常见追问：Self-Attention 与 Cross-Attention 的区别在于 Q、K、V 的来源；Self-Attention 三者来自同一序列，Cross-Attention 的 Q 来自当前序列，K/V 来自另一序列或编码结果。
Q03 · ★★★★☆为什么 Attention 要除以 √dₖ？

若 Q、K 各维度近似独立、方差为 1，点积的方差会随 dₖ 增大。除以 √dₖ 可把 logits 的尺度拉回稳定范围，避免 softmax 过早饱和、梯度变小。它是数值稳定性设计，不是降低复杂度。

Q04 · ★★★★☆MHA、MQA、GQA 有什么区别？

MHA 的每个 Query Head 都有独立 K/V；MQA 共享一组 K/V；GQA 将 Query Head 分组，每组共享 K/V。GQA 在保留多 Query 表达能力的同时减少 KV Cache 容量和读取量，常是质量、显存、带宽之间的折中。

关联阅读：注意力机制如何演变。
Q05 · ★★★★☆没有位置编码会怎样？Causal Mask 能替代它吗？

Self-Attention 本身主要依据内容相似度聚合，不携带绝对位置、相对顺序和距离方向。Causal Mask 只限制不能看未来，不能告诉模型两个 Token 的相对位置。RoPE 通过对 Q/K 做位置相关旋转，把位置信息融入点积并表达相对关系。

Q06 · ★★★☆☆LayerNorm 和 RMSNorm 有什么区别？

LayerNorm 会减均值再按方差归一化；RMSNorm 只按均方根缩放，不做均值中心化，计算更简洁。Llama 等模型采用 RMSNorm，是在经验效果、稳定性和计算开销之间的选择，不能脱离具体模型说谁绝对更好。

Q07 · ★★★☆☆FFN 在 Transformer 中做什么？为什么常用 SwiGLU？

Attention 负责跨 Token 信息混合，FFN 在每个位置独立地做通道维度的非线性变换，提供特征变换和容量。SwiGLU 用门控分支调节信息通过比例，通常以参数和中间维度调整换取更好的表达能力。

Q08 · ★★★★☆为什么 8K 模型不能直接把 Context Length 改成 128K？

训练时的长度分布、位置编码外推能力、注意力数值稳定性、KV Cache 显存和长上下文数据质量都可能成为限制。需要位置插值或 RoPE scaling、长上下文继续训练和质量评测；改配置只改变上限，不会凭空获得泛化能力。

Q09 · ★★★☆☆Temperature、Top-k、Top-p 分别改变什么？

Temperature 缩放 logits，改变分布平滑度；Top-k 固定保留概率最高的 K 个候选；Top-p 保留累计概率达到 p 的最小集合。过滤后对剩余候选重新归一化。Beam Search 是序列搜索策略，不等于随机采样。

Q10 · ★★★★☆LoRA 为什么只训练少量参数也能微调？

冻结基础权重 W，只学习低秩增量 ΔW=BA，让任务变化落在较低维的适配子空间。训练参数、优化器状态和显存大幅下降，但低秩假设可能限制复杂任务，秩、目标层和数据质量需要验证。

Q11 · ★★★☆☆Base Model 如何变成 Chat Model？

常见链路是预训练得到 Base Model，经过指令数据 SFT 学会遵循格式，再通过偏好数据和 RLHF、DPO 等方法改善 helpfulness、harmlessness、风格和拒答边界。SFT 解决“怎么回答”，偏好对齐解决“多个回答中更偏好哪个”。

Q12 · ★★★☆☆大模型有“推理能力”吗？

更严谨的说法是模型表现出数学、代码、多步决策和规划等推理行为，但不能因此等同于意识或可靠的形式化推理器。CoT 能改善部分任务，却不保证正确；生产系统还需要验证器、工具、检索和约束输出。

二、推理核心：KV Cache、Prefill 与 Decode

Q13—Q30 · KV Cache、阶段瓶颈、调度、分页缓存与服务指标。

Q13 · ★★★★★KV Cache 是什么？为什么推理需要它？

为什么能缓存：在 Causal Attention 中，已经生成的历史 token 不会再改变，因此它们在每一层得到的 K/V 也不会改变。生成第 t 个 token 时，只需要计算新 token 的 Q、K、V；Q 与缓存中的 K₁…Kₜ 做匹配，再对 V₁…Vₜ 加权。新 K/V 追加到 Cache，供下一步使用。

节省了什么：如果没有 KV Cache，第 t 步必须重新前向整个长度为 t 的序列，生成 N 个 token 会不断重复计算历史投影和中间层。使用 Cache 后，历史 K/V 的投影不再重算，Decode 每步只新增一个位置。它没有消除新 Q 对全部历史 K/V 的 Attention，因此上下文越长，每步读取量仍会增长。

代价：每层、每个请求、每个 token 都要保存 K 和 V，容量与层数、上下文长度、并发、KV Head 数、Head Dimension 和 dtype 成正比。Decode 阶段还要反复从 HBM 读取 Cache，所以它既是容量问题，也是带宽问题。GQA/MQA、KV 量化、PagedAttention 和 Prefix Cache 分别从结构、精度、分配和复用角度优化这笔成本。

常见追问：训练为什么通常不依赖 KV Cache？Teacher Forcing 下整段 token 可以并行计算，缓存反而会破坏训练并行性；KV Cache 主要服务于自回归增量推理。
Q14 · ★★★★★Prefill 和 Decode 的瓶颈为什么不同？

Prefill：输入形状近似 [B,S,H]，线性层可转成 [B×S,H] 与大权重矩阵做 GEMM。S 较大时有足够多 token 复用权重并摊薄 Kernel launch，Tensor Core 更容易吃满，所以常偏 compute-bound；长上下文 Attention 的 O(S²) 计算和中间访存也会逐渐变重。Prefill 完成后写出整段 KV Cache，主要影响 TTFT。

Decode：每一步形状近似 [B,1,H]，GEMM 的 token 维很小。权重和历史 KV 的读取量相对计算量很大，算术强度较低，常偏 memory-bandwidth/latency-bound。同时下一 token 依赖上一步结果，无法把多个时间步直接并行；TP All-Reduce、PP Stage 同步和调度开销也更难摊薄，主要影响 TPOT 与 ITL。

不是绝对结论：短 Prompt、小模型或很大 Batch 下，Prefill/Decode 的瓶颈可能变化。判断时应结合 Roofline、GEMM shape、HBM 带宽、GPU 利用率与通信占比，而不是只凭阶段名称。

关联阅读：LLM 推理性能怎么分析。
Q15 · ★★★★★KV Cache 显存怎么估算？

单请求公式：KV bytes = 2 × L × T × Hkv × Dh × bytes_per_element。其中 2 表示 K 和 V，L 是层数，T 是当前总序列长度，Hkv 是 KV Head 数，Dh 是 Head Dimension。并发服务再乘活跃请求数；不同请求长度不一致时，应按实际已分配 token/block 求和。

手算例子：32 层、32 个 KV Head、Head Dimension 128、上下文 4096、FP16/BF16 每元素 2 字节，则单请求约为 2×32×4096×32×128×2 bytes，约 2 GiB。若改成 8 个 KV Head 的 GQA，理论 KV 容量降为四分之一，约 512 MiB。

工程预算：这只是有效数据量。实际还要考虑 Block 对齐和尾部碎片、页表元数据、CUDA workspace、通信 buffer、图捕获池以及框架预留。总显存预算应拆成权重 + KV Cache + Runtime/通信开销，并给 OOM 留安全水位。

常见追问：生成过程中 T=输入长度+已生成长度，因此即使 Batch 不变，KV Cache 仍会随 Decode 逐步增长。
Q16 · ★★★★☆为什么 Decode 通常比 Prefill 慢？

“慢”要先定义是单 Token 延迟还是总吞吐。Decode 的单步工作量小却要读取全历史 KV，矩阵乘形状也更像小 GEMM，难以吃满 GPU；自回归依赖让每步不能完全并行。Batch 能提高吞吐，但会增加带宽竞争和尾延迟。

Q17 · ★★★★☆FlashAttention 更快，但是否改变了 O(n²)？

标准 Attention 的理论计算复杂度仍是 O(n²)。FlashAttention 通过 tiling、片上 SRAM 重用和 online softmax，减少 HBM 读写与中间矩阵物化，因此实际更快、更省显存；它优化的是 IO 复杂度和常数，不是把一般 Attention 变成线性复杂度。

Q18 · ★★★★☆GPU 和 CPU 推理如何比较？

GPU 更适合大模型、批量矩阵、并发和低精度 Tensor Core；CPU 适合小模型、低并发、量化、成本敏感或没有 GPU 的场景。必须固定模型、量化、输入输出长度、并发、硬件和指标，不能只比较设备名称。

Q19 · ★★★★☆INT8 一定比 FP16 快吗？

不一定。INT8 可能降低权重和访存压力，并在支持良好的硬件与 Kernel 上提升吞吐；但 scale、反量化、算子覆盖和小 Batch 开销都可能抵消收益。应分别测 TTFT、TPOT、吞吐、显存和精度回归。

Q20 · ★★★★☆显存为什么涨了还一直占着？

要区分权重常驻、KV Cache 增长、workspace、通信 buffer 和分配器保留。nvidia-smi 更接近 reserved，不等于活跃 Tensor；应对照 allocated、reserved、KV block 使用量和请求生命周期。allocated 持续增长且对象无法释放，才更像泄漏或缓存归还问题。

Q21 · ★★★★☆Batch 增大时 Decode 延迟怎么变？

第一阶段：小 Batch 时 GPU 利用率不足，增大 Batch 能把多个请求同一步的矩阵运算合并，摊薄 Kernel launch、权重读取和通信固定成本，因此总体 Tokens/s 上升，单 token 延迟可能基本不变甚至下降。

第二阶段：当计算单元或 HBM 接近饱和，继续加 Batch 会增加每一步读取的 KV 总量和 Kernel 工作集，单步执行时间开始上升。排队等待、调度同步、不同长度请求之间的干扰也会推高 TPOT 和尾延迟。

服务侧结论：优化目标不是最大 Batch，而是在目标 SLA 下最大化 goodput。通常使用 token budget 而不是只限制请求数，并分别绘制并发/Batch 对吞吐、TTFT、TPOT、P95/P99 和 OOM 率的曲线，选择饱和拐点前的工作区。

Q22 · ★★★★☆什么是 Continuous Batching？

请求不是等整批结束再替换，而是在每个 Decode step 动态加入新请求、移除已完成请求。它提高设备利用率和吞吐，但需要处理不同长度、KV block、优先级、公平性和抢占。

Q23 · ★★★★☆Chunk Prefill 解决什么问题？

没有分块时，一个超长 Prompt 的 Prefill 可能长时间独占 GPU，使队列里正在流式 Decode 的请求无法及时执行，ITL 出现尖峰。Chunk Prefill 把长输入拆成若干 token chunk，每完成一块就把调度权交还 Scheduler，让高优先级 Decode step 或其他短 Prefill 穿插执行。

收益：降低 Head-of-Line Blocking，改善 Decode 公平性、ITL 和 P95/P99；也能通过 token budget 更细粒度地组合 Prefill 与 Decode 工作。

代价：Chunk 太小会增加调度和 Kernel launch 次数，破坏大 GEMM 效率，Cache 访问也可能更碎；Chunk 太大则无法有效改善抢占。它主要改变执行时序，不保证减少总计算量或 HBM 流量，参数要用目标流量分布实测。

Q24 · ★★★★☆PagedAttention 解决什么问题？

传统方案若按请求预留连续 KV 空间，要么按最大长度预留导致大量浪费，要么在序列增长时重新分配和搬迁；请求长度和生命周期又高度动态，容易产生外部碎片。PagedAttention 将逻辑连续的 KV 序列拆成固定大小 Block，通过 Block Table 映射到物理显存中不连续的 Block。

能力：请求增长时按需追加 Block，结束后立即归还；不同请求不必占连续显存；共享前缀时多个逻辑序列还可以引用同一物理 Block，并用引用计数或 Copy-on-Write 管理。

代价：Kernel 需要按 Block Table 寻址，产生元数据、间接访问和边界处理；Block 太大会有内部碎片，太小会增加映射和调度开销。因此它提升的是可管理容量和并发，不代表 Attention 数学计算本身消失。

Q25 · ★★★☆☆PageSize 大小如何取舍？

大 Page 减少元数据与管理次数，访问更连续，但序列尾部和短请求的内部碎片更大；小 Page 分配灵活、碎片少，却会增加映射、调度和访存开销。PageSize=1 通常管理成本过高，不是免费获得最优碎片率。

Q26 · ★★★★☆Prefix Cache 命中率低怎么排查？

检查公共前缀是否被时间戳、用户字段、随机示例、工具结果、空格换行和 Chat Template 变化污染；确认 Tokenizer、模型和 Prompt 版本一致，再看 Cache Key、TTL、容量淘汰、Block 粒度和权限域。稳定公共内容放前，动态内容放后。

Q27 · ★★★★☆多租户 Prefix Cache 如何保证安全？

Cache Key 至少纳入 tenant、项目、模型版本、Prompt 版本和权限域，按租户隔离或做严格 ACL；不能因为前缀相同就跨租户复用可能包含私密信息的结果。缓存命中率必须服从数据安全边界。

Q28 · ★★★☆☆输入分桶 Input Bucketing 的目的是什么？

按输入长度把请求放入近似长度的桶，减少 Padding，提升 Batch 内形状一致性和 Kernel 利用率，也让 Benchmark 输入分布可控。桶过多会增加调度复杂度，过少则仍有 Padding 浪费。

Q29 · ★★★★☆TTFT、TPOT、ITL 分别看什么？

TTFT 是请求到首 Token 的时间，包含排队、预处理、检索和 Prefill；TPOT 是平均每个输出 Token 时间；ITL 是相邻输出 Token 的间隔。线上体验还应看 E2E、请求级 P95/P99，不能只报一个平均 Tokens/s。

Q30 · ★★★☆☆冷启动包含哪些阶段？

容器/进程启动、权重加载、CUDA 初始化、Kernel 编译或 autotune、Engine 初始化、Cache 建立、连接池和依赖服务准备都可能是冷启动。Warmup 只覆盖其中一部分，排查时要按链路拆时间。

三、调度、并行与 P/D 分离

Q31—Q40 · P/D 分离、TP、PP、流水线气泡与请求链路。

Q31 · ★★★★★P/D 分离为什么有价值？

动机：Prefill 需要高算力和大 GEMM 吞吐，Decode 需要低单步延迟和高 HBM 带宽。混部时，一个长 Prefill 可能阻塞 Decode，统一的 TP、Batch 和调度参数也很难同时适合两类负载。

分离方式：Prefill Worker 处理 Prompt 并生成各层 KV Cache，随后通过高速网络或共享存储把 KV 交给 Decode Worker；Decode Worker 接管自回归生成。两侧可独立选择硬件、TP/DP、Chunk Size、Batch、扩缩容和 SLO。

新的瓶颈：KV 体积大，传输延迟可能抵消计算收益；还会引入路由、背压、实例配比、失败恢复和缓存生命周期问题。判断是否值得分离，要比较 TTFT、TPOT、KV transfer latency、队列时间、两侧利用率和单位 token 成本，而不是只看某一侧吞吐。

Q32 · ★★★★☆P/D 分离中的主要通信问题是什么？

Prefill 产出的 KV 需要可靠、高吞吐、低抖动地交给 Decode；要考虑传输协议、拓扑、序列化、分块、流控、失败重试和 KV 一致性。优化不能只看 GPU 算力，还要测 KV transfer latency 和队列等待。

Q33 · ★★★★★Tensor Parallel 和 Pipeline Parallel 的区别？

TP：把同一层的权重沿列或行切到多张卡，每张卡计算部分结果，再通过 All-Reduce/All-Gather 合并。优点是同一层并行、单请求延迟可能下降并分摊权重显存；缺点是几乎每层都通信，对 NVLink/IB 拓扑敏感，Decode 小消息通信尤其难摊薄。

PP：按层把模型切成多个 Stage，Stage 之间传递 activation，用多个 Microbatch 填充流水线。优点是跨设备容纳超大模型且层内通信少；缺点是启动/排空 Bubble、最慢 Stage 限制吞吐、切分不均和跨 Stage 调度复杂。

选择：模型单层放不下或希望降低层内延迟时考虑 TP；整体模型放不下且设备组间带宽较弱时考虑 PP；服务吞吐通常还会叠加 DP。真实部署常采用 TP×PP×DP 的组合，先满足容量，再用目标 workload 优化延迟和吞吐。

Q34 · ★★★★★Pipeline Bubble 从哪里来？

设 P 个 Stage、M 个 Microbatch。流水线启动时，后面的 Stage 要等待前面产出；排空时，前面的 Stage 已结束而后面仍在处理，形成不可避免的空闲。若各 Stage 时间近似相等，简单前向流水线的利用率可粗略理解为 M/(M+P-1)，因此 M 相对 P 越大，启动和排空成本越容易被摊薄。

实际 Bubble 还来自 Stage Imbalance、通信阻塞、动态请求长度和调度断粮。只增加 Microbatch 不一定更好：它会增加队列与状态管理，训练时还涉及激活内存，推理时则可能推高单请求等待和尾延迟。

定位方法：画每个 Stage 的时间线，区分 compute、send/recv 和 idle；同时比较 stage latency、队列深度与 GPU Utilization。优化方向包括重新切层、虚拟/交错流水线、通信计算重叠，以及持续给流水线提供形状相近的 Microbatch。

Q35 · ★★★★☆Stage Imbalance 如何定位？

分别记录每 Stage 的计算时间、通信时间、空闲时间、输入输出队列和显存使用，找出最长 Stage 或等待链。原因可能是层计算量不同、Embedding/LM Head 特殊、Kernel 不同或通信拓扑不均。不要只看整机 GPU Utilization。

Q36 · ★★★★☆PP 对 Prefill 和 Decode 的影响一样吗？

Prefill 有较多 Token，可用 Microbatch 更充分地填满流水线；Decode 每步 Token 少且同步频繁，Bubble 和通信占比更明显。应分别测 TTFT、TPOT、吞吐和 Bubble，而不是用 Prefill 的加速推断 Decode。

Q37 · ★★★★☆如何选择 TP、PP、DP？

先由模型权重、KV 和 workspace 判断单副本能否放下，再结合通信拓扑、目标并发和指标选择。TP 扩大单实例容量，PP 跨层拆模型，DP 复制服务实例承接请求。最终必须用目标输入输出分布实测。

Q38 · ★★★★☆连续 Batch 如何和 PP 配合？

需要让动态加入/退出的请求在不同 Stage 间保持一致的 Microbatch 状态和 KV 生命周期，并处理短请求完成、长请求占用、公平性和回压。调度器不仅要决定“下一个请求”，还要维护流水线可持续供料。

Q39 · ★★★☆☆为什么 Batch 不是越大越好？

Batch 提升并行度，但会增加 KV 读取、显存、同步和排队时间；长请求还会拖累短请求的尾延迟。应设最大 Batch 或 token budget，并用吞吐曲线和 P95/P99 找拐点。

Q40 · ★★★★☆如何分析一次推理请求的完整链路？

请求接入 → 排队 → Tokenize → RAG/预处理 → Prompt 构造 → Prefill → Decode → 流式网络返回。每段都打时间戳和 trace/span，才能区分应用、调度、模型、通信和网络延迟。

四、量化与真实优化

Q41—Q48 · 低精度、Kernel、投机解码与 Benchmark 对齐。

Q41 · ★★★★☆FP8 量化哪些层需要谨慎？

LayerNorm/RMSNorm、Softmax、Embedding、LM Head、首尾层、MoE Router 和 outlier 明显的投影层常需要更高精度或特殊 scale。不是绝对不能量化，需结合模型、硬件、scale 方案和精度回归决定。

Q42 · ★★★★☆剪枝、蒸馏和量化分别解决什么？

剪枝移除结构或权重，只有硬件 Kernel 能利用稀疏性才有实际收益；蒸馏用教师监督训练更小模型；量化降低数值表示精度和存储带宽。它们都可能损失质量，需联合评测。

Q43 · ★★★☆☆Kernel Fusion 和 CUDA Graph 为什么能加速？

Fusion 减少中间读写和 Kernel launch，把多个小操作合并；CUDA Graph 预先记录稳定执行图，减少 CPU 发射和调度开销。动态形状、分支和请求变化会限制收益，不能脱离形状稳定性判断。

Q44 · ★★★★☆Speculative Decoding 为什么可能加速？

用便宜的 Draft Model 或并行草稿一次提出多个 Token，再由 Target Model 并行验证；接受的连续 Token 越多，越能减少 Target 自回归步数。收益取决于接受率、草稿成本、验证并行度和额外 KV 管理。

Q45 · ★★★☆☆CPU Offload 什么时候值得用？

当模型或 KV 无法完全放入 GPU，且吞吐要求允许 PCIe/NVLink 传输代价时可用于容量兜底。它通常会牺牲延迟，必须分析传输带宽、驻留策略和访问热度。

Q46 · ★★★☆☆为什么梯度裁剪不算主要显存优化？

梯度裁剪主要控制训练中的梯度爆炸和稳定性，通常不显著降低参数、激活或优化器状态占用。训练省显存应优先考虑混合精度、Checkpointing、Gradient Accumulation、ZeRO/FSDP 和动态 Padding。

Q47 · ★★★★☆Benchmark 如何避免 Prefix Cache 污染？

明确缓存开关和状态，预热与正式测量分开，控制 Prompt 前缀是否重复，记录命中率和 Cache eviction；不同框架必须统一模型、Tokenizer、硬件、量化、输入输出分布、并发、Warmup 和指标定义。

Q48 · ★★★★☆vLLM 的 GPU Memory 和某框架 Static Memory 能直接换算吗？

不能只看名字。应拆成权重、KV Cache、Runtime Workspace、通信 Buffer、元数据和框架开销，并确认两边的预留策略、动态池、最大长度和 Cache 配置。最终以同环境的可用 KV 容量和运行指标对齐。

五、RAG 与 Agent：应用系统的可靠性

Q49—Q57 · 检索、Rerank、工具调用、状态与失败恢复。

Q49 · ★★★★☆为什么 RAG 不直接 Fine-tuning？

RAG 适合知识经常更新、需要引用和权限控制的场景，更新成本低且可追溯；Fine-tuning 更适合行为、格式和领域能力迁移，不适合当作动态数据库。二者可以结合。

Q50 · ★★★★☆完整 RAG Pipeline 怎么讲？

文档解析 → 清洗 → Chunk → Embedding/倒排索引 → Query Rewrite → 召回 → Hybrid Search → Rerank → Context Compression → Prompt 构造 → 生成 → 引用与答案评测。每一段都可能引入召回损失或延迟。

Q51 · ★★★★☆BM25、Embedding Retrieval、Hybrid Search 的关系？

BM25 擅长关键词、稀有词和精确匹配；向量检索擅长语义相似。Hybrid Search 融合两类信号，通常提升召回稳健性，但要处理分数归一化、权重、去重和额外延迟。

Q52 · ★★★★☆为什么检索到了正确 Context，模型仍会答错？

可能是 Context 太长或排序不佳、证据被噪声淹没、Prompt 约束不足、模型未使用证据、冲突信息未处理、引用范围错误或生成参数不稳。应分别评估 Retrieval Recall、Context Precision、Groundedness 和最终答案。

Q53 · ★★★★☆Agent、Workflow、Function Calling 有什么区别？

Workflow 是预定义流程；Function Calling 是模型输出结构化工具调用的能力；Agent 根据目标、观察结果和状态动态选择行动。Function Calling 是能力组件，不自动等于 Agent。

Q54 · ★★★★☆ReAct 和 Plan-Execute 的本质区别？

ReAct 边思考边行动，适应性强但轮次、延迟和成本不可控；Plan-Execute 先形成计划再执行，流程稳定、易审计，但计划错误时需要重规划。生产中常做受限 ReAct 或混合 Workflow。

Q55 · ★★★☆☆如何限制 ReAct 的开销？

限制最大轮数和 Tool 次数，设置超时与重试上限，使用 Tool 白名单、结果缓存、并行调用、小模型路由和大模型决策，超限后转固定流程、人工确认或降级。

Q56 · ★★★★☆Checkpoint 能恢复什么，不能恢复什么？

可保存消息、当前节点、状态变量、工具参数和结果；不能天然回滚已发生的数据库写入、扣款或第三方副作用。需要幂等键、事务日志、Saga、补偿动作和人工审计。

Q57 · ★★★☆☆MCP 和 Function Calling 的关系是什么？

Function Calling 描述模型如何请求一个函数；MCP 更关注工具、资源和提示的标准化发现与连接协议。MCP 可以承载工具调用，但两者抽象层次不同，是否采用要看生态和治理需求。

六、Benchmark、质量与线上排障

Q58—Q67 · 延迟分位数、质量回归、OOM、NCCL 与基准验证。

Q58 · ★★★★★首 Token 从 1 秒突然变成 3 秒，代码和模型没变，怎么排查？

先确认口径：看升高的是平均值还是 P95/P99，是全量还是某租户/模型/实例，是持续还是周期尖峰。确认客户端计时、服务端 TTFT 与监控窗口一致，避免先排一个并不存在的模型问题。

按链路拆分：入口网关与排队 → 鉴权/限流 → Tokenize → RAG/Rerank → Prompt 构造 → Scheduler Queue → Prefill → 首次 Decode → 流式网络。为每段对比历史基线，先找到新增的约 2 秒发生在哪里。

模型服务侧：检查流量和输入长度分布、活跃序列数、Batch/token budget、长 Prefill 阻塞、Prefix Cache 命中率、KV Cache 水位与 eviction；再看 GPU 利用率、频率、温度、ECC、HBM 带宽、Kernel 时间和通信。实例扩容、模型加载、CUDA Graph 捕获或 Kernel autotune 都可能造成冷启动。

验证：按实例和请求类型切片，回放同一请求并绕过 RAG/网关做对照；必要时降低并发、固定 Prompt 长度或把流量切到健康实例。每次只改变一个变量，最后把根因映射回 TTFT 的具体分量。

Q59 · ★★★★★P95 和 P99 怎么计算？请求级和 Token 级有什么区别？

在固定统计窗口内收集 N 个样本并排序，P95/P99 是对应 95%/99% 分位位置附近的值；具体使用 nearest-rank 还是插值法要由监控系统定义。不能把不同实例的 P99 再取平均得到全局 P99，因为分位数不可直接聚合；应聚合原始样本或可合并 Histogram。

请求级：每个请求贡献一个 TTFT、E2E 或排队延迟样本，长短请求权重相同，最接近用户体验和 SLA。Token 级：每个输出 token 或 Decode step 贡献 ITL 样本，长请求会贡献更多样本，适合观察生成稳定性与底层调度。

还要按输入/输出长度、并发、租户和模型版本分桶，否则长请求比例变化会让 P99 上升，看起来像系统回归。面试中应明确“什么对象、什么时间窗口、什么延迟定义、如何聚合”。

Q60 · ★★★★★模型质量回归应该看哪些指标？

任务准确率、Recall/Precision/F1、Groundedness、Faithfulness、幻觉率、引用准确率、工具调用成功率和用户满意度；同时看 TTFT、E2E、吞吐、Token 成本和错误率。离线集、线上抽样和版本对照要分开。

Q61 · ★★★★★OOM 怎么定位？

先看发生阶段：启动即 OOM 多半是权重、并行切分或静态预留；Prefill OOM 常与长输入、Attention workspace 或大 Batch 有关；Decode 运行一段时间后 OOM 常与 KV Cache 增长、并发、碎片或 Block 未归还有关。

拆显存：总占用 = 权重 + Runtime/临时激活 + KV Cache + CUDA Graph/Kernel workspace + 通信 buffer + 分配器 reserved。结合 allocated、reserved、peak、KV block 使用率和每请求 token 数判断；reserved 高但 allocated 低更像缓存分配器或碎片，二者持续同步增长更像真实对象未释放。

二分验证：依次固定或降低 max sequence length、并发、token budget、Batch、Cache 容量，关闭 Prefix Cache/CUDA Graph，或改变精度。若随请求数单调增长且请求结束后不回落，检查请求对象、引用计数和 Cache block 回收；若只在特定 shape 出现，检查 Kernel workspace 与图捕获池。

修复顺序：先做正确的容量预算和限流，再优化 GQA/量化/分页/Offload。不要把频繁 empty_cache 当根治方案，它可能降低复用效率，也无法释放仍被引用的 Tensor。

Q62 · ★★★★☆NAN/Inf 常见原因是什么？

学习率或梯度爆炸、混合精度溢出、非法输入、除零、Softmax 数值问题、量化 scale 异常都可能造成。需要定位首次出现的层和 batch，检查输入、激活范围、loss scale、算子精度和 checkpoint，而不是只在末端加 clamp。

Q63 · ★★★★☆NCCL Timeout 该怎么查？

检查是否有某个 Rank 先崩溃、Shape/Collective 次序不一致、某 Stage 计算过慢、网络拓扑或 IB 配置异常、GPU hang/降频。收集各 Rank 日志、通信耗时、拓扑和最小复现，不能只盲目增大 timeout。

Q64 · ★★★★☆CUDNN Error、Shape Mismatch、Illegal Memory Access 如何区分？

CUDNN Error 常需结合输入 shape、dtype、workspace 和版本；Shape Mismatch 检查模型配置、Tokenizer、Batch 和并行切分；Illegal Memory Access 可能是异步 Kernel 越界，需同步执行、缩小复现并检查自定义 Kernel。先让异步错误变同步，定位才可靠。

Q65 · ★★★★☆如何对齐 SGLang 与 vLLM Benchmark？

对齐模型权重、Tokenizer、Chat Template、GPU/驱动、精度、最大上下文、输入输出分布、并发/到达模式、Warmup、Prefix Cache、Chunk Prefill、Sampling 和统计窗口。还要确认指标定义一致，避免把实现差异误判成框架能力差异。

Q66 · ★★★★☆如何证明一次优化真的有效？

固定环境和 workload，保留优化前基线，至少比较 TTFT、TPOT/ITL、吞吐、P95/P99、显存、GPU Utilization、HBM 带宽、通信时间和质量指标。做多次重复、置信区间或稳定窗口，并解释收益来自哪个资源瓶颈。

Q67 · ★★★★★技术题最后如何给出“工程化的一句话回答”？

用“机制 + 目标 + 代价 + 验证”四段式。例如：KV Cache 复用历史 K/V，避免 Decode 重复计算；代价是显存和带宽压力；因此要结合 GQA、分页管理和 Cache budget，并用 TPOT、HBM 带宽和 KV 命中/占用验证。
