Envoy 与 AIBrix：数据面四件套、ExtProc 与 LLM 感知路由

入口层如果只记得「两个网关名字」，排查 TTFT 时就会把调度误判成算力。 本文把 Envoy 拆到 Listener / Filter / Router / Cluster，再把 AIBrix 拆到 ExtProc 与指标缓存驱动的选路。

2026年8月10日 · 22 分钟 · 4680 字 · MOFANG

生产推理链路里，请求常常是： 业务平台 → Envoy → AIBrix → 调度/KV → vLLM Prefill/Decode。 表面上都叫「网关」，职责却不在同一层： Envoy 解决的是「流量如何被可靠、可观测地搬运」；AIBrix 解决的是「在 LLM 语义下，请求该落到哪个副本、哪种资源形态」。

把二者写成并列名词，会漏掉一个关键机制：AIBrix Router 并不是另起炉灶的 HTTP 服务器， 而是挂在 Envoy Gateway 的 External Processing（ExtProc）钩子 上—— Envoy 仍负责连接、协议与转发，选路决策被外置到「看得懂 KV / 负载 / SLO」的插件。

一、先回答：为什么不直接打 vLLM？

微服务时代，服务发现、熔断、限流、可观测性最早塞在各语言 SDK 里。 规模上来之后，问题很具体：多语言栈各自维护一套治理库；SDK 与业务同进程，升级治理能力等于逼业务发版。 Service Mesh 的转向，是把这些能力抽到独立 Proxy（Sidecar），业务只和本机代理说话—— 这就是「框架思维 → 平台思维」。

Envoy 正是这类 Proxy 的主流实现之一：C++ 写成，架构上接近 Nginx 那条线—— 多线程 + 非阻塞 + 异步 IO（Libevent）。 核心是 L3/L4 代理，再在其上叠 HTTP L7、HTTP/2、gRPC、服务发现、负载均衡、Tracing 与动态配置。 部署上既可以是每个 Pod 旁的 Sidecar，也可以是集群边缘的 Front/Edge Proxy。 你在推理入口图里看到的 Envoy，多数是后者：统一收流量，再转给后面的 LLM 网关/引擎。

对 LLM 服务的直接含义： 业务进程不必自己实现连接池、HTTP/2 多路复用、重试与熔断； 但也意味着——默认配置下，Envoy 不会根据「前缀 KV 是否命中」来选 pod。

二、Envoy 的四件套：一次请求怎么被拆开

《深入架构原理与实践》把 Proxy 拆成四个关键组件。这比「它是个七层代理」更利于读配置、读火焰图：

组件 职责 对应你在配置里看到的东西
Listener 定义如何接收入站连接（TCP）；连接建立后交给 Filter Chain listeners[].address.socket_address
Filter 链式处理入站/出站；可压缩、鉴权、做 HTTP 连接管理等 filter_chains[].filters，如 envoy.http_connection_manager
Router 按匹配规则把请求导向某个 Cluster route_config.virtual_hosts[].routes
Cluster 上游端点集合 + LB / 超时 / 服务发现策略（类似 Nginx upstream） clusters[] 的 hosts、lb_policy、connect_timeout

用一份静态配置把路径走通

动态 xDS（控制面推配置）是生产常态；但静态配置更适合建立心智模型。 下面按 thebyte 文中的骨架，压缩成「你真正要记住的映射」： 

static_resources:
  listeners:
  - name: listener_0
    address:
      socket_address: { address: 0.0.0.0, port_value: 8000 }
    filter_chains:
    - filters:
      - name: envoy.http_connection_manager
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
          codec_type: AUTO
          stat_prefix: ingress_http
          route_config:
            name: local_route
            virtual_hosts:
            - name: backend
              domains: ["thebyte.com.cn"]
              routes:
              - match: { prefix: "/" }
                route: { cluster: targetCluster }
          http_filters:
          - name: envoy.filters.http.router

  clusters:
  - name: targetCluster
    connect_timeout: 0.25s
    type: STRICT_DNS
    lb_policy: ROUND_ROBIN
    load_assignment:
      cluster_name: targetCluster
      endpoints:
      - lb_endpoints:
        - endpoint:
            address:
              socket_address: { address: 127.0.0.1, port_value: 8082 }
        - endpoint:
            address:
              socket_address: { address: 127.0.0.1, port_value: 8083 }

admin:
  address:
    socket_address: { address: 0.0.0.0, port_value: 9901 }

几处容易被一笔带过、但对排查很关键的点：

  • 域名不在 Listener 上定死，而在 virtual_hosts.domains；Host 头不匹配会直接 404，和后端是否健康无关。
  • envoy.http_connection_manager 才是 HTTP 世界的入口；同一 Listener 也可换 TCP/Redis 等 Filter，说明 L3/L4 与 L7 是分层插拔。
  • Cluster ≈ Nginx upstream，但超时、LB、服务发现策略都挂在 Cluster 上，而不是散落在业务代码里。 STRICT_DNS 下 DNS 返回几个 IP，Envoy 就认为上游有几台 host。
  • admin（常开 9901） 用来看配置快照、stats、日志——入口层「慢」时，先看这里比先看 GPU 利用率更理性。
边界： 到这一步，Envoy 已经能做边缘接入、按 path/host 分流、对一组 HTTP 上游做 RR/最小请求数等。 它仍然把上游当成「等价 HTTP 端点」。LLM 副本并不等价——有的 KV 热、有的在 Prefill、有的接近显存墙。

三、AIBrix：把「等价端点」假设拆掉

AIBrix （字节开源，现属 vLLM 生态）要补的，正是「规模化跑 vLLM」时的缺口： 多模型/多副本路由、按推理指标扩缩、LoRA 密度、分布式 KV、异构成本与故障检测。 文档把它拆成 Control Plane 与 Data Plane：

平面 代表能力 和「只部署 vLLM」的差别
Control Plane LoRA Controller、RayClusterFleet、LLM Autoscaler、GPU Optimizer、AI Runtime Sidecar、加速器诊断 按 KV 利用率等做秒级扩缩；异构 GPU 成本优化；适配器与多机编排进 K8s 控制环
Data Plane Request Router、Distributed KV Cache Runtime TPM/RPM、公平性、工作负载隔离；跨节点 KV 复用，减少重复 Prefill

关键词不是「又一个 Ingress」，而是 system × inference engine co-design： 扩缩容信号来自 KV / 推理指标，路由目标函数可以是前缀命中、SLO 或 PD 分离，而不是单纯的连接数。

四、叠层关键：ExtProc 如何把 LLM 决策塞进 Envoy

AIBrix Router 文档写得很硬：它是 Envoy Gateway 的扩展，通过 external processing hooks 挂上， 作为 LLM 请求的单一入口。热路径可以抽象成： 

Client
  → Envoy（TLS / HTTP/2 / Filter Chain / 连接池）
    → ExtProc Hook → GatewayPlugin
         │              │
         │              ├─ 读本地缓存的 pod 指标 & KV 状态
         │              └─ 跑 routing-strategy，选出目标 pod
    → Envoy 按决策转发
  → Inference Pod（vLLM …）
  ← 流式 token 原路返回

为什么必须「外置决策」，而不是写死在 Cluster LB？

Envoy 内建 LB（RR、Least Request…）看到的是连接/请求计数一类通用信号。 LLM 选路还要看：prompt 前缀能否命中已有 KV、当前 KV 水位、GPU cache、历史 latency、用户级公平、甚至 PD 角色。 这些信号刷新频率高、维度多，不适合每次请求都阻塞去扫全集群。

所以 Router 的核心工程选择是： 高频维护一份本地指标/KV 状态快照（pull + subscribe），热路径只读快照做多目标决策。 这样既能撑高 QPS，又不会把「查一下谁更空」变成 TTFT 的主项。

路由策略不是功能清单，是目标函数

策略可通过环境变量 ROUTING_ALGORITHM 全局指定，或按请求头 routing-strategy 覆盖。按目标函数归类更有用：

类别 代表策略 你在优化什么 误用时的症状
通用负载 least-request / least-latency / power-of-two 把请求摊开，避免个别 pod 过热 长上下文场景仍大量重复 Prefill
KV / 缓存感知 prefix-cache / least-kv-cache / prefix-cache-preble 复用前缀 KV，或避开显存已紧的副本 只追命中率导致少数热 pod 被打爆
公平性 vtc-basic 多租户下按用户 token 消耗做折中 看起来「总吞吐还行」，但大户饿死小户
SLO slo / slo-least-load / slo-pack-load 按延迟目标打包或打散负载 平均延迟好看，P99 / 违约率恶化
专用形态 pd / session-affinity Prefill/Decode 分离，或粘滞会话保 KV 局部性 PD 拓扑与路由策略不一致 → 传输/排队异常
和 Envoy Cluster LB 的本质差别： Cluster LB 假设端点近似同质；AIBrix 策略显式承认端点异质且有状态（KV 就是状态）。 这就是「LLM 网关」配得上这两个字的原因。

五、回到生产图：TTFT 里「传 / 选 / 算」各占什么

一张常见图是： 

Mass / 业务平台
  → Envoy                         # 传：连接、协议、边缘策略
    → AIBrix 网关                  # 选：模型、副本、路由目标函数
      → Coordinator / KV Conductor # 选+备：实例与 KV 资源
        → vLLM-P / vLLM-D          # 算：Prefill 与 Decode

两个常见误判：

  • 首字慢，先骂 GPU：若 ExtProc / 调度排队或 KV 分配卡住，火焰图在引擎侧什么都看不到。
  • 引擎侧 Prefill 变长，先调 kernel：若路由从不做 prefix-aware，每条多轮对话都在冷启动 KV，再强的 Attention 优化也救不了系统性浪费。

六、小结

  • Envoy：云原生数据面。记住四件套——Listener 接、Filter 加工、Router 定向、Cluster 均衡；admin 是入口层的体检口。
  • AIBrix：LLM 控制面 + 推理感知数据面。控制环管扩缩与适配器，Router 管「异质有状态副本」上的目标函数。
  • 接合点：ExtProc——Envoy 负责搬运，AIBrix 负责决策；决策依赖异步刷新的指标/KV 快照，而不是每次现场扫集群。
  • 读图：把链路拆成传 / 选 / 备 / 算，TTFT 才能归因，优化才找得到杠杆。
浅层说法是「两个网关」；深层说法是：一个通用数据面，外挂一个承认 KV 状态的决策面。
