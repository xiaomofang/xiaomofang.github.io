大模型部署的容器与 Kubernetes：算法工程师必须知道的部分

部署失败很少来自模型代码，而来自容器给的资源边界与调度器假设之间的缝隙： CPU 被配额节流、内存账本把 page cache 也算进去、/dev/shm 只有 64MB、发布窗口里新实例还没加载完权重。 本文只讲会直接改变推理延迟、吞吐与稳定性的那部分容器与编排机制，以及对应症状该看的指标、该改的参数； Ascend 的设备链路与多机 RDMA 单独成节，它们是「能部署」与「能调优」的分界。

容器与 K8s 推理框架

2026年11月3日 · MOFANG

文章假设读者能写 YAML、能跑 kubectl，缺的是字段背后的机制，因此不按 K8s 教程的对象顺序讲， 而按一个请求从进容器到出 token 要过的几本资源账组织：容器边界、CPU 账本、内存账本、Pod 共享、网络、 调度与发布、权重存储、平台层；Ascend 设备链路与多机 RDMA 各成一节。 读完应当能判断一段性能问题落在哪本账上，以及要改哪个字段、看哪个指标。

容器知识本身有边界。下面这张表是本文的取舍依据：「必须」之外的内容在线上排障时用不到，读了也不形成判断。

层级 内容 为什么在这个位置
必须 cgroup 的 CPU/内存账本、page cache 记账、/dev/shm、PID 1 与信号、端口与 sysctl、镜像只读层、ulimit 直接决定 OOM、节流、启动失败与流被截断，踩到就是线上事故
需要 pids.max / io.max、cpuset 与 NUMA、conntrack、设备插件链路、RDMA 与 memlock 用来区分「资源不够」与「配置错」，缺了会误判方向
略过 capabilities / seccomp 细项、user namespace、cgroup v1 兼容、CRI 实现差异 平台已兜底，知道名字即可，不进入日常判断

一、容器边界：三个内核对象决定你看到什么、能用多少

容器没有自己的内核。它让一组进程看到一套新的文件系统与网络，同时给这组进程记一本资源账。 这件事由三个互相独立的内核对象完成，混在一起记就会永远分不清「看不到」和「不够用」：

对象 决定 部署时的具体后果
namespace 进程「看得见什么」：挂载点、网卡与端口、进程号、主机名、IPC 权重路径在容器里不存在；同 Pod 端口冲突；sysctl 只对 Pod 生效
cgroup 进程「能用多少」：CPU 时间、内存、PID 数、IO CPU 被节流、内存被 OOMKill、线程数开得比配额大
device cgroup + capabilities 进程「能碰什么设备、有哪些特权」 看不到 /dev/davinci*；默认丢掉特权后需要显式声明的能力

先看 namespace，因为「看不到」最容易被误判成「文件丢了」。 mnt 决定根文件系统与挂载点，只读挂载除了防误写，还能让多个容器共享同一份 page cache； net 不只是隔离网卡，内核网络参数也是 per-netns 的—— somaxconn、tcp_max_syn_backlog、tcp_tw_reuse 都跟着 Pod 走。 高并发短连接下 SYN 队列溢出，表现为「服务端 CPU 不高、客户端连不上」，在宿主上改 sysctl 却不见效。 pid 决定你在容器里看不到宿主进程，也决定谁负责回收孤儿进程——这个下面还会踩一次。

再看镜像。镜像是只读层叠，容器在最上面加一个可写层；读命中下层，写只在最上层留脏页（copy-on-write）。 两个直接结论：同镜像的多个副本在节点上共享只读层， 所以 8 个引擎容器不会各自把 Python 解释器和 .so 读进内存一份； 而写日志到容器层会同时造成层膨胀和 IO 放大；日志走 stdout 或挂载目录可以避开这两者。 镜像体积本身也是启动时间的一部分：20GB 镜像首次拉取受节点带宽限制，滚动更新时这段时间会被计算进「启动」，不是「加载」。

统计口径。 判断容器内存时看 cgroup 的 memory.current 与 memory.stat， 统计口径以 cgroup 的 memory.current 为准：页缓存按 cgroup 记账，ps 的 RSS 只反映匿名页。 同一个权重文件被多个容器 mmap，节点上只有一份物理页，但各自的账本里都可能计入， 用 RSS 相加会得出「内存早就爆了」的错误结论。

二、CPU 账本：配额、节流与线程数

CPU 配额在 cgroup v2 里就是一行 cpu.max：quota period。 limits.cpu: 1.6 换算成 160000 100000，意思是每个 100ms 周期最多用 160ms 的 CPU 时间。 超出不会报错，只会被推迟到下一个周期——这就是「平均 CPU 不高，但 P99 周期性抖动」的机制来源： 抖动的周期就是配额周期，通常是 100ms。

验证不需要特殊工具，容器里直接读账本： 

cat /sys/fs/cgroup/cpu.max          # quota period，例如 160000 100000
cat /sys/fs/cgroup/cpu.stat         # nr_throttled / throttled_usec 是累计节流次数与时长
cat /sys/fs/cgroup/cpu.pressure     # 有 PSI 时可以直接看 CPU 争抢
路径不同不代表机制不同。 cgroup v2 的账本集中在 /sys/fs/cgroup/（cpu.max、memory.max）； v1 按子系统分目录（/sys/fs/cgroup/cpu/、/sys/fs/cgroup/memory/）。 K8s 1.25 之后默认 v2，但在老集群里 exec 进去找不到文件时，先确认版本，再怀疑命令。

nr_throttled 持续增长而 throttled_usec 占比不低，说明配额就是瓶颈，加并发没有意义。 此时有两条路：提高配额，或者只设 requests 不设 CPU limit。 后者不节流，但会和其他 Pod 抢；在专用推理节点上，这通常比被硬限流更划算。

配额和亲和是两件事，经常被混为一谈。cpu.max 只限总量， cpuset 才决定实际跑在哪些核上。绑核之所以对推理有意义，是因为跨 NUMA 访问内存带宽会掉， 而 NPU 的 PCIe 传输、网卡中断也有 NUMA 归属；同一张卡上的请求如果跨 NUMA，拷贝延迟会比预期高。 排查这类问题看的是节点拓扑与 lscpu，不是配额。

线程数是算法侧最常出错的地方，因为它由框架而不是你决定。 Python 的 os.cpu_count() 返回宿主核数，len(os.sched_getaffinity(0)) 才是当前进程可用的核；OpenMP、MKL、部分 tokenizer 实现默认按前者建线程池。 在「限了 16 核、宿主 160 核」的容器里，这会开出十几倍于配额的线程，结果不是更快，而是上下文切换与节流叠加。 部署时显式设置 OMP_NUM_THREADS、MKL_NUM_THREADS， 并把 tokenizer 的并行度单独当作一个参数来调，而不是交给默认值。

字段 机制 调法
requests.cpu 调度依据：节点剩余可分配 CPU 够不够 按稳态负载给，别按峰值；GPU 节点上 CPU 常是瓶颈
limits.cpu 运行期 CFS 配额，超出即节流 延迟敏感服务建议不设或给足，避免 100ms 级抖动
cpuset / affinity 决定跑哪些核，影响 NUMA 与缓存 大 EP 实例按 NUMA 绑核，与 NPU 同一侧
OMP 线程数 数值库默认按宿主核数建池 显式赋值，通常等于 cpuset 核数或更小

CPU 之外还有三条限制会直接出现在推理里。pids.max 限制容器内进程数， dataloader 或多进程 worker 起不来时报 Resource temporarily unavailable； io.max 按字节率与 IOPS 限盘，权重加载会被静默限速； ulimit -l（memlock，属于 rlimit 而不是 cgroup）决定能锁多少页， RDMA 与共享内存注册都要锁页，太小会让 HCCL/NCCL 初始化直接失败。 这三处分别对应「起不来」「加载慢」「通信初始化失败」三类现象。

三、内存账本：limit、page cache 与 /dev/shm

memory.max 是硬上限，超了触发 cgroup OOM killer，进程以 137 退出； K8s 里看到的就是 OOMKilled。关键在于这个账本包含 page cache， 不只是进程的匿名内存。大模型部署几乎必然踩到这一点。

safetensors 通常以 mmap 方式读取，权重文件页会进入 page cache 并记到容器账上。 当 memory.max 小于「权重工作集 + 运行时堆 + 通信缓冲」时，内核会先回收 page cache； 下一次读同一个 tensor 又要回磁盘。于是出现一个很反直觉的现象： 加载越来越慢、GPU 长时间空转，但机器整体内存看起来还充足。 判断方法还是读账本： 

cat /sys/fs/cgroup/memory.current     # 当前已用（含 file cache）
cat /sys/fs/cgroup/memory.stat        # anon / file / slab 的拆分
cat /sys/fs/cgroup/memory.events      # oom / oom_kill 计数
cat /sys/fs/cgroup/memory.peak        # 峰值，排查"偶发 OOM"最有用

memory.stat 里 file 占比高、memory.events 里 oom_kill 增长， 基本就是「limit 设得太紧，把权重缓存挤掉了」。 实践上有三种处理：给 limit 留出 page cache 余量；把权重放本地盘并让多副本共享同一目录； 或者干脆不设内存 limit（只靠节点规格隔离），但要接受故障时影响面更大。

还有一个固定 64MB 的坑：/dev/shm 是 tmpfs，按内存记账，而 Docker 默认只给 64MB。 多进程推理、共享内存张量、部分 dataloader 会在 batch 变大时直接崩，报 Bus error 或 No space left on device。K8s 的写法是用内存型 emptyDir 覆盖它： 

volumes:
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: 8Gi
volumeMounts:
  - name: dshm
    mountPath: /dev/shm

sizeLimit 计入容器内存账本，所以它和 memory.max 是同一个池子： 把 shm 调到 8Gi，就要在 limit 里预留这 8Gi，否则 OOM 会来得更早。 大页（2MB/1GB）是另一条线：它对 KV cache、通信缓冲区确实有收益，但需要节点预留， 属于「确定性优化项」，不是部署必需。

四、Pod：共享了什么，代价是什么

Pod 是最小调度单位，同 Pod 内共享网络命名空间、IPC 与卷，PID 默认不共享。 共享网络的直接后果是端口全局唯一：引擎占 1025，指标 sidecar 就不能再用 1025， 第二个容器启动时只会得到一句 address already in use，看起来像程序 bug。 共享 IPC 的后果是 /dev/shm 对同 Pod 的所有容器可见， sidecar 也能看到引擎的共享内存段——排查内存问题时别只看主容器。

推理服务的两种打包方式，代价不同： 一容器（引擎）+ 指标/日志 sidecar，省机器但共享端口与内存账； 引擎独占 Pod，账目干净，适合大 EP 这类每卡都敏感的实例。 hostNetwork 能省掉一层 NAT 与 conntrack，降低小包延迟，但端口与节点冲突、 且 sysctl 变成节点级——收益只在收发热点路径上明显，默认不打开。

五、网络：请求怎么到达，什么时候会被掐断

Pod IP 会变，Service 给的是稳定虚拟 IP 加一组就绪端点。链路上真正影响推理的是三个点： 就绪判定、连接复用、超时链。

就绪判定决定了 Pod 在不在端点列表里。readinessProbe 失败只是把 Pod 从列表里摘掉， 不重启容器；livenessProbe 失败才会重启。把「端口在监听」当成就绪， 是发布期 5xx 的常见来源：进程还没加载完权重就已经在监听端口了。

连接与超时链的问题在流式输出上最明显：客户端 → 网关 → 协调器 → 引擎，每一跳都有自己的 idle timeout。 只要上游比下游先超时，长流就会在中间被切断，表现为「输出到一半停了」或「尾部缺 token」。 正确做法是超时时间沿链路单调递增，并让 keepalive 小于最上游的空闲阈值。 NodePort 这种暴露方式还要注意端口在集群内唯一：两套部署共存时撞号，流量会进错实例。

规模上来之后还有两笔网络成本：conntrack 表容量与转发规则数量。 在 kube-proxy 模式下，ClusterIP 靠 iptables/IPVS 规则转发，规则数随 Service 与端点数量增长， 建连时要查表，表现是「高并发下建连变慢」，而带宽和 CPU 都不像瓶颈； NodePort 的 SNAT 还会为每条连接占一个 conntrack 条目，短连接一多表就满，满了直接丢新连接。

六、调度与发布：Pod 被放到哪，什么时候接流量

调度器先按 requests 过滤节点，再打分选一个。所以 Pending 的第一层原因是资源账： 节点 allocatable 减去已分配，不够就直接出局，与实际空闲率无关。 第二层是约束：nodeSelector 标签写错、taints 没声明容忍、affinity 过窄， 都会让节点明明有空闲也不参与调度，Events 里只留一句「0/N nodes are available」。

推理的特殊性在于设备是不可压缩资源：申请一张就独占一张，资源名（如 huawei.com/Ascend910） 的 requests 必须等于 limits，数量只能是整数。 节点的可分配数来自设备插件——插件异常时卡还在机器上，但节点显示 0 张可分配，Pod 直接 Pending； 容器里能看到 /dev/davinci*、/dev/davinci_manager、/dev/devmm_svm， 才说明设备与容器运行时都注入成功。

还有一个只有大 EP 才会暴露的问题：一个实例要 8 个 Pod 同时通信，普通调度器逐个绑定， 可能出现「起了 7 个、第 8 个没卡」的半启动状态。Gang scheduling（成组调度，通常由 Volcano 这类调度器提供） 要求整组资源同时满足才一起绑定，代价是实现更重，收益是消除这一类死锁。

探针解决的是三个不同问题，混用会制造两类事故： startupProbe 等启动完成（最长允许 periodSeconds × failureThreshold）， 通过之前 readiness 与 liveness 都不生效； readiness 判断能不能接流量；liveness 判断要不要重启。 加载 850GB 权重可能需要几十分钟，如果只配 liveness，容器会在加载中途被反复重启， 现象是「启动日志每次从头开始」——这几乎总是探针问题，不是加载脚本问题。

还要把 warmup 算进窗口：加载完成不等于可服务，图捕获（CUDA graph、图编译）与首次推理预热常在之后发生， 耗时从几十秒到几分钟。startup 的 periodSeconds × failureThreshold 要覆盖「加载 + 预热」， 否则容器会在就绪前被判成启动失败。

第二个容易漏的是优雅退出，它和流式响应直接冲突。收到 SIGTERM 后， 进程收到信号后停止接新请求、等在途请求结束再退出；terminationGracePeriodSeconds 必须大于最长请求时长，否则会被 SIGKILL，客户端看到的是流被截断。 还有一层：如果容器里的 PID 1 是不转发信号的 shell，SIGTERM 根本到不了子进程， 优雅退出等于没做。用 exec 形式启动，或加 --init / tini。

滚动更新还有一个 GPU 特有的约束：maxUnavailable=0 能保证容量， 但新副本需要一张空闲卡才能起来；maxSurge 给的余量在 CPU 服务里是「多几个 Pod」， 在推理里是「多几张卡」。没有余量时发布会停在中途，旧版本全在、新版本 Pending， 看起来像「发布失败」，实际是资源不足。

七、存储：权重从哪来，决定启动时间与稳定性

权重进容器的路径只有三条，代价完全不同： 对象存储直接下载（首次慢、每次冷启动都慢，但节点无关）； 网络盘挂载（节点无关、吞吐受网络限制，随机读尤其差）； 本地盘 + 预分发（最快，但绑节点，需要额外的分发与清理流程）。 大 EP 部署几乎都走第三条，因为 850GB 量级下「每次从对象存储拉」的时间成本无法进入滚动发布的窗口。

路径 首次加载 节点无关性 适用场景
对象存储直下 受带宽限制，可能几十分钟 是 小模型、测试环境、临时验证
网络盘 PVC 取决于网络与随机读性能 是 多节点共享、更新频繁的权重
本地盘 + 分发 最短，且可预热 page cache 否，绑节点 生产大模型、固定节点池

本地盘的边界要写清楚：local 类型的 PV 必须配 nodeAffinity， 因为这块盘只在某一台机器上；capacity 只是绑定与调度的声明值，不会真的对目录做配额； Retain 会保留数据，但 PV 会停在 Released，需要手工清掉 claimRef 才能复用。 把权重做成只读挂载，既能防止误写，也能让同节点的多个副本共享同一份 page cache。

分发本身适合做成 CR 而不是脚本：脚本执行完没有状态，失败只能靠退出码； CR 把进度写进 status，可以按节点看 TARGET、READY、FAILED， 失败只影响单个节点，且天然可以重放。权重分发 CR 里的 nodeSelector 同时承担了「分发范围」与「调度约束」两个职责， 这也是它适合声明式管理的原因。

八、平台层：Helm、ArgoCD、CRD 的责任边界

读部署问题时，先分清差异发生在哪一层，比逐行看 YAML 有效： helm template 是「模板 + values 的渲染结果」， helm get manifest 是「发布时提交的那一份」， kubectl get -o yaml 是「集群里当前的、可能被 webhook 改过的对象」。 三者对不上时，问题分别落在模板层、参数层、集群层。

CRD 只是把平台自己的领域语言接进 K8s：CRD 定义类型，CR 是实例，controller 负责把实例变成真实动作。 kubectl get 输出的那些 PHASE、READY、FAILED 列， 来自 CRD 的打印列声明，数据源是 status；所以「看起来像内置资源」不代表它是内置的。 排障时 kubectl describe 看 conditions，kubectl explain 看字段语义， 比翻文档快。

九、Ascend 设备链路：容器里的 /dev/davinci 从哪来

容器能看到几张卡，由四段链路决定；任何一段断掉，现象都不是「卡坏了」，而是「卡不见了」： 宿主驱动与固件 → device plugin 上报可分配数 → kubelet 分配设备并注入环境变量 → 容器运行时挂载设备节点与驱动目录。

环节 正常表现 断掉时的现象
驱动 / 固件 宿主执行 npu-smi info 能看到卡与健康状态 节点被标记不可用，或卡报错；容器内任何工具都读不到设备
device plugin 节点 allocatable 中出现 huawei.com/Ascend910 Pod Pending，Events 只有「0/N nodes are available」
kubelet 分配 Pod 内存在 ASCEND_VISIBLE_DEVICES 声明了资源却没有可见性变量；多卡实例只看到一张
运行时注入 /dev/davinci*、/dev/davinci_manager、/dev/devmm_svm 齐全 npu-smi 报无设备；框架初始化时报找不到 device

最容易误判的是后两段：显存访问、驱动库与设备节点是分开注入的。 只有 /dev/davinci0 而缺 davinci_manager 与 devmm_svm，说明运行时只挂了部分节点； 节点齐全但框架仍报错，多半是镜像里的 CANN 版本与宿主驱动不匹配，或 LD_LIBRARY_PATH 指向了错误的驱动目录。 判断顺序因此固定：宿主 npu-smi → 节点 allocatable → Pod 环境变量 → 容器内设备节点 → 框架初始化日志。

多卡可见性由 ASCEND_VISIBLE_DEVICES 收敛，PID 命名空间隔离并不会隐藏设备， 因此「容器里只看到一张卡」不能当作隔离生效的证据；真正起作用的是这个环境变量与设备 cgroup 的允许列表。

十、多机 RDMA：memlock、设备与 NUMA 亲和

单机多卡走 PCIe，多机大 EP 走 RDMA（RoCE 或 IB）。这一层的失败通常发生在容器边界而不是算法里， 集中在三处：设备没进容器、锁页额度不够、网络与拓扑不匹配。

锁页额度是第一处。RDMA 注册内存要把页锁定在物理内存（ibv_reg_mr）， 而容器默认的 ulimit -l 常在几十 KB 到 64KB 量级，通信库在初始化阶段就会失败， 报错形如 ibv_reg_mr failed 或 Failed to initialize HCCL。 这类报错看起来像驱动或权限问题，实际是 rlimit；它不在 cgroup 里，调大内存 limit 不会解决，需要单独把 memlock 放开。

设备是第二处。容器需要看到 /dev/infiniband/uverbs* 与 rdma 设备， 常见做法是 hostNetwork 加 hostPath 挂载 /dev/infiniband，或由 RDMA device plugin 分配。 只给 hostNetwork 却没挂设备时，容器里能看到网卡但没有 verbs 设备，通信库会静默退化到 TCP—— 不报错，带宽只剩一个数量级，这类配置错误往往到压测才暴露。

拓扑是第三处。NPU 与网卡挂在不同的 PCIe root 上时，跨 NUMA 的内存拷贝会吃掉带宽。 宿主侧用 npu-smi info -t topo 与 lspci -tv 可以确认相对位置； 容器侧则要求 cpuset、内存分配策略与设备分配落在同一个 NUMA 域，否则 CPU、卡、网卡分属不同侧， 调优参数会整体失效。

十二、需要能给出数字的项

下面每一项都应当能给出具体数字或结论，而不是「大概是」： CPU 配额与实际节流次数；内存 limit 里为 page cache 留出的余量； /dev/shm 的大小以及它是否计入 limit；启动窗口与就绪判定的时长； 在途请求的最长时长；权重的存放位置、分发方式与失败影响面； 线程数的来源；容器内可见的卡数与设备节点；RDMA 的锁页额度与 NUMA 归属。 这些项对应机制而不是平台方言，换一套平台，数值会变，判断方式不变。

容器的价值不是「打包」，而是把 CPU、内存、设备这些资源变成可计量、可约束的账本； 调优的起点，是知道自己的账本记在哪、什么时候会被扣款。
