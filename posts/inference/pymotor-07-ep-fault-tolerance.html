一个分布式推理实例由多个节点、端点和设备共同组成。某个端点异常时，系统需要先停止把新请求送到不可靠的服务，再判断证据是否足以支持局部恢复，最后让所有组件看到同一份新拓扑。Controller 的代码把这三个过程连接起来。本章先阅读常态生命周期，再用一个四 DP 实例的故障贯穿证据收集、恢复计划、引擎指令和幸存端点发布。

常态路径由实例状态机和观察者连接

Controller 的模块组装

Controller.init_modules() 建立 InstanceAssembler、EventPusher、可选 FaultManager、InstanceManager、可选观测门面以及管理 API，然后把相关观察者绑定到 InstanceManager。Assembler 管理节点如何组成逻辑实例，Manager 管理这个实例当前的生命周期，Pusher 负责把变化传播到 Coordinator。恢复逻辑可以观察同一份只读实例快照，减少模块间直接修改共享对象带来的耦合。源码 · Controller 组装与角色切换

InstanceManager.transitions 明确写出状态与条件事件的对应关系。正常启动常沿 INITIAL 到 ACTIVE，ACTIVE 收到异常或心跳超时后进入 INACTIVE，恢复正常又可能回到 ACTIVE，持续超时最终进入 DELETED。PAUSED 另有暂停、恢复和异常分支。学习时先为“注册成功、端点正常、端点异常、主动暂停、长期失联”五个触发条件各画一条路径，再对照完整转移表补边界。源码 · 实例生命周期状态机

从状态变化走到可调度变化

InstanceManager 通过 notify() 给观察者传递 ReadOnlyInstance。EventPusher 将 INSTANCE_READY、INSTANCE_SEPARATED 等事件转换成 ADD、DEL、PAUSE、RESUME 等成员操作，排队后向 Coordinator 发送。增量失败可以触发 SET 全量对账，周期同步、Coordinator 心跳与切主通知也参与收敛。阅读时应区分 ACTIVE 这样的生命周期状态和 INSTANCE_READY 这样的观察事件，前者保存在实例对象里，后者表示一次变化。当前 SET 对控制器内存为空有专门跳过分支，分析全量同步时仍需读到实际条件。源码 · 观察事件 源码 · 实例变化传播

贯穿本章的例子

设某个逻辑实例最初包含 DP0、DP1、DP2、DP3。第一轮 DP2 被确认死亡，恢复后服务端点为 0、1、3。第二轮 DP0 再发生故障，系统需要记得 DP2 已经退役，并把累计移除集合交给引擎，同时选择存活 rank 中的新 master。以下数字仅用于说明事务和集合关系。

先归并故障证据，再选择恢复计划

软件事实与硬件事实的来源

软件路径来自 NodeManager 对原生引擎 FT、进程死亡和运行异常的汇报。硬件路径通过 K8s Node 与相关故障 ConfigMap 进入 resource_monitor.py，再由 configmap_parser.py 和 fault_types.py 解析等级、故障码和设备归属。mixin/resource_manager.py 维护节点与实例的关联，mixin/persistence.py 管理故障状态保存。FaultManager 汇总这些事实，为各实例维护故障快照和策略运行生命周期。源码 · 故障汇总与策略中心 源码 · 故障分类与设备归属

FaultNormalizer 将证据映射回 Motor 保存的原始 DP 坐标。明确 DEAD 的引擎 rank 可以成为移除候选，UNHEALTHY 还可能出现在受集体通信故障影响的幸存者身上。硬件证据需要结合 Pod 与设备拥有关系映射到 endpoint。对于设备归属信息不完整的历史注册，代码保留较保守的节点级处理。这一层决定了“哪些 rank 确实可移除”，因此应先读证据归一化，再读真正执行 scale-down 的函数。源码 · 故障归一化与运行态

RecoveryPlan 保留决策理由和回退来源

build_recovery_plan() 接收实例身份、配置、ScaleDownContext、原等级策略与故障码，返回不可变的 RecoveryPlan。计划里包含来源、选中策略、上下文、fallback 和证据。代码检查实例是否适合引擎恢复、硬件映射是否完整、是否还在等待 FT 证据、所有 DP 是否都受影响，以及收集是否超时。某些情况下计划暂时不分配策略，继续等待证据。完整证据到达且存在待移除 rank 时，才进入启用的 DP 缩容路径。源码 · 恢复计划选择

这个设计让“先收到哪种证据”和“最终依据什么决策”可以分别表达。例如先收到硬件故障时，会有相关性等待窗口，稍后完整引擎快照仍可参与最终判断。另一个值得跟踪的分支是单 DP 的纯软件死亡，若原策略允许原地重拉且条件满足，计划保留这条恢复路径。读规划器时，为每个 return 写下事实前提，比直接背策略名称更容易掌握边界。

恢复策略各自控制什么资源

从等级映射走到有生命周期的执行

strategy/strategy.py 建立故障等级和初始策略映射，硬件类别、角色和配置开关都会影响选择。StrategyBase 管理执行、停止、完成和失败的公共状态，FaultManager 再跟踪运行结果，决定清理证据、继续等待或使用回退。策略中出现的线程和事件说明它们可能跨多个观察周期运行，API 接受一次请求与恢复最终完成之间还有一段生命周期。源码 · 等级策略映射 源码 · 策略生命周期

大 EP 场景中的 DP 缩容事务

能力门槛和原始 rank 坐标

DpScaleDownStrategy._gate() 检查功能开关、引擎 FT、external LB、scale-down 支持、EPLB 和冗余专家，并要求原生 auto-recovery 与外部控制路径没有冲突。门槛结果保存成带 reason codes 的 GateSnapshot。冗余专家数量是可行性检查输入，专家布局及通信恢复最终还要由引擎执行。通过门槛后，策略解析原始 DP rank，拒绝不属于原拓扑的候选，再构造本轮移除集合与幸存者。源码 · DP 缩容事务

运行态 FtRuntime 保存 original_dp_ranks、dead_committed、pending_removed_ranks、request id、阶段、能力快照、引擎状态以及服务是否已发布。第一轮移除 DP2 后，dead_committed 为集合 {2}。第二轮发现 DP0 时，发送给引擎的累计移除集合为 {0,2}，幸存者为 {1,3}，新 master 取最小存活 rank 1。累计坐标避免连续恢复把旧退役 rank 当作仍然可用的通信成员。

guard 与 status 建立可执行窗口

策略为本轮生成 request id，再按 NM 分组。guard 在各 NM 建立有期限的退出保护，避免全局恢复期间本地代理因暂时不健康自行退出。随后只对幸存端点收集 FT 状态，等待它们观察到故障并进入允许外部 scale-down 的状态。当前 readiness 分类把 unhealthy 且没有 recovering 子状态视为可执行，把 healthy 或 unhealthy/recovering 视为仍需等待。等待中若又收到明确 DEAD 的幸存 rank，会扩展本轮移除集合并重新计算分组。这个阶段把证据收敛与真正 apply 分开。

撤流、apply 和 finalize 的先后关系

就绪后，策略先通过 ServingOverlay.withdraw() 确认 Coordinator 已撤下服务视图，再将阶段推进到 SCALING_DOWN。随后向幸存 NM 扇出一次 apply，传递累计 removed ranks 和新 master 信息。代码轮询异步结果，healthy 表示本轮成功，recovering 继续等待，终态失败或截止时间耗尽则进入回退。测试覆盖阶段失败时停止推进以及避免盲目重复 apply 的行为。

引擎成功后，策略先向 NM finalize commit，提交本地退役端点，再更新 dead_committed，进入清理阶段，最后发布幸存服务视图。如果引擎已经提交而 Coordinator 发布失败，运行态仍保留已提交结果，并把 serving_published 置为未完成，等待后续发布收敛。引擎提交之前失败的路径会在 finally 中发出 finalize abort。这个区分让恢复事务能够表达“底层已经恢复、对外发布仍待完成”的中间状态。

幸存者投影、退役 Pod 和重复故障

为什么同时保存原始拓扑与服务视图

Controller 需要原始拓扑解释故障设备、历史 rank 和连续恢复，同时 Coordinator 只应收到当前可以调度的端点。ServingOverlay.project() 从实例生成分离的副本，恢复中的多个阶段返回无可服务视图，进入 SCALED_DOWN_RUNNING 后过滤 dead_committed。后续 ADD、RESUME、SET 都可以经过同一投影，因此退役 DP 不会仅仅因为一次正常心跳或周期性全量同步再次出现。fingerprint() 用实例及端点集合描述发布视图，mark_published() 在确认收敛后更新运行态。源码 · 服务拓扑投影

退役集合怎样影响节点和 Pod

NM 的 finalize 会把已退役端点从心跳、异常判断和 FT 监控等出口过滤。Controller 的 TopologyResolver 再根据节点拥有的端点判断哪些 Pod 已完全退役。当前 enable_dp_scale_up 关联这类可回收 Pod 的停止触发，PodLifecycle.stop_recyclable_pods() 通过已有 NM stop 合同停止选中的代理，后续 Pod 回收由资源系统接管。阅读到这个开关时，应继续跟调用方和实际资源动作，按已经实现的行为描述能力。源码 · 退役 Pod 生命周期

重复证据还需要事务去重。若待移除 rank 已经属于 dead_committed，策略根据当前阶段判断这是一条已处理故障，或一个需要回退的阶段冲突。实例重建后还会出现新的运行身份，因此旧 job 的迟到事件必须结合实例 id 处理。这里的难点来自时间顺序，故障、心跳、成员通知和恢复结果都可能跨线程或跨进程到达，单独修改某一个列表不足以表达整次提交。

主备持久化与可复述的恢复实验

主备切换需要恢复什么

开启主备时，Controller 先运行管理 API 和 StandbyManager，成为 master 后启动实例组装、生命周期、事件推送和故障管理，退为 standby 时逆序停止相关模块。etcd 同时承担锁与租约相关协调、版本化状态保存等职责。InstanceManager 的持久化包含版本、时间戳和校验信息，恢复后还要重新协调心跳时效与成员发布。源码 · 主备管理 源码 · 版本化持久状态

FT 运行态只持久化恢复所需的最小字段。已经提交的缩容阶段恢复成 SCALED_DOWN_RUNNING，仍需确认服务重新发布。处于 DECIDING、WAITING_ENGINE_FAULT、SCALING_DOWN 等未完成阶段的记录在恢复后转向原回退。这样控制器重启不会依赖一份丢失的进程内 future 继续假定事务仍在执行。阅读 restore_persistent_data() 时，可以把每个旧阶段映射到恢复阶段，并写下 dead_committed 与 serving_published 分别如何处理。源码 · FT 状态持久化与恢复

可以把两轮缩容写成一份手工事务账本。初始原始 rank 为 {0,1,2,3}，已提交退役集合为空。第一轮证据确认 DP2 死亡，本轮 pending 为 {2}，引擎成功以后 dead_committed 才更新为 {2}。第二轮确认 DP0 死亡，本轮 pending 为 {0}，累计移除集合为 {0,2}，服务投影成为 {1,3}。若第二轮 apply 前失败，账本仍需保留上一轮已经提交的 {2}，同时记录本轮失败及回退原因。这个练习能够直接检验自己是否分清原始坐标、待提交动作和已提交历史。

另一个练习是在成功恢复后让成员发布暂时失败。此时引擎已经确认新通信拓扑，NM 也已经过滤退役端点，Controller 不能因为发布失败就把已提交 rank 从历史集合中抹去。应继续观察保存的恢复阶段、发布标志、错误信息以及下一轮 EventPusher 对账。对应地，如果控制器恰在 apply 进行中重启，恢复代码会依据保存阶段选择回退，避免凭空假设旧线程已经完成。这两个时刻的处理差异体现了事务提交边界，也是解释代码设计时可以具体展开的工程问题。

完成这些练习后，再在受控集群实验中观察故障证据到达、撤流确认、apply 发出、引擎完成、发布成功几个时间点。实验记录应同时保存能力开关、原始 rank、累计移除集合、幸存者、request id 和错误分支。项目介绍可以围绕“多层状态怎样随着一轮恢复事务收敛”展开，个人经历则根据实际参与的开发、部署或验证范围描述。

把机制讲清楚

先自己回答，再展开核对。把答案落到对象、状态和代码位置上。

一次超时就能删掉某个 DP 吗？

恢复规划结合硬件证据、引擎 FT 状态、rank 映射、收集时限和能力门槛。未知或暂时失败的状态不足以直接决定不可逆移除。

继续追问 · 区别症状、明确 DEAD 证据和可执行恢复计划。

怎么保证下一次 SET 不会复活退役端点？

Controller 保留原始拓扑与累计 dead_committed，同时通过 ServingOverlay 生成可服务端点投影。后续 ADD、RESUME、SET 持续消费同一投影。

继续追问 · 完成两轮缩容，再投影一次全量成员。

引擎恢复成功，成员发布却失败了怎么办？

底层提交结果与服务发布分别记录。保存已提交的退役集合和发布标志，后续对账继续推进服务视图，而不是抹去已经完成的拓扑变化。
