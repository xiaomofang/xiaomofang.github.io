推理引擎解剖室：vLLM × Ascend

SP 把 token 切开后，为什么 FFN 还要 all-gather？PCP 和 DCP 都涉及序列分片，为什么一个分 query、另一个分 KV？这个专栏从这些执行细节写起，继续讨论专家路由、缓存传输、投机解码和调度。

vLLM × Ascend 推理框架 并行与通信

先从 SP 开始

  1. SP 到底切了什么：从 Transformer Block 到 PCP、DCP 与 DSA-CP

    用两张卡、四个 token 解释 all-gather、all-reduce、reduce-scatter；推导 attention o_proj 与 FFN down_proj 的部分贡献，解释 RMSNorm 的本地计算条件，再进入 PCP query 分配与 DCP softmax 合并。

    文中有双卡交互图、计算量与通信量的手算，以及可运行的 NumPy 复算脚本。

后续选题

  1. 长上下文分给谁：PCP、DCP 与稀疏注意力

    一条长提示词分给两张卡，每卡究竟负责哪些 query、保存哪些 KV？如果各卡先对自己的 KV 做 softmax，局部结果又该怎样合并？还会接着看 prefix cache、chunked prefill 和变长请求如何改变这张分工表。

    Context Parallel · Sequence Parallelism

  2. o_proj 和 FFN 为什么不必使用同样的并行度

    同一层里，o_proj、FFN 与 attention 的矩阵形状不同，通信代价也不同。Fine-grained TP 怎样选择各自的并行度？层再被分到不同 PP 阶段时，Dynamic Chunk Pipeline 又怎样安排计算与等待？

    Fine-grained TP · Pipeline Parallelism · Dynamic Chunk Pipeline Parallel

  3. 热门专家怎样拖慢整批 token

    如果大量 token 同时选中同一个专家，其他卡空闲也不一定能让它更快。这里会区分 Router 的专家选择、EPLB 的专家映射以及 token 的跨卡传输，再看 Large Scale EP 和 EPD 分离中的通信边界。

    Expert Parallelism Load Balancer · Large Scale EP · EPD Disaggregation

  4. Prefill 还没结束，KV 能不能先传过去

    P 节点生成某一层的 KV 后，D 节点是否必须等整次 prefill 完成？逐层传输依赖什么同步，混合注意力又要额外交接哪些卷积或递推状态？缓存池、Mooncake 与 KVPP 可以放在同一条交接过程中理解。

    KV Cache Pool / Ascend Store · Mooncake Layerwise Adaptation and Optimization · Mooncake Layerwise Hybrid Attention · KVPP

  5. 把 KV 放到 CPU，什么时候比重算划算

    显存里放不下的缓存，下沉以后还要付出传输和恢复时间。这里会比较普通 KV、encoder cache、稀疏缓存与抢占状态，追踪预取何时发生，以及 UCM、LMCache 等方案怎样介入缓存的分配和回收。

    Layerwise and Sparse KV Cache Offloading · KV Cache CPU Offload · Encoder Cache CPU Offload · Preempt Offload · UCM Deployment · LMCache Ascend Deployment

  6. 起草五个 token，只接受两个，还能赚到时间吗

    投机解码多做了起草和验证，收益取决于一次能提交多少 token，以及验证怎样利用硬件。会把这些开销与 FlashAttention 的分块、IO、KV 写入和回滚接在一起看，继续展开已有的 MTP、EAGLE、DFlash 与 DSpark 文章。

    Speculative Decoding · Flash Attention · 投机解码演进 · FlashAttention 深入解析

  7. 同一个 prompt，换一批请求为什么可能算出不同数值

    batch shape、归约顺序、量化和图执行都可能影响实际计算路径。Batch Invariance 到底保证哪一部分？图捕获里的稳定缓冲区，又怎样接住不断变化的请求和 padding？

    Batch Invariance · Graph Mode · Quantization

  8. 短问答遇到长 prefill，应该先算谁

    单次 forward 更快，不代表排队中的请求更早结束。ShortRequestFirst 和 Batch-Job-Aware Scheduler 改变了哪些请求获得 token budget，需要同时看等待时间、TTFT、TPOT、吞吐和尾延迟。

    ShortRequestFirst Prefill Scheduling · Batch-Job-Aware Scheduler

  9. 模型文件已经在本地，启动为什么还慢

    从读取权重到设备初始化、图准备，再到实例可调度，冷启动包含多段工作。NetLoader 和 RFork 分别复用或加速了哪一段，哪些资源仍必须重新建立？这也能接到 PyMotor 的实例上线过程。

    NetLoader · RFork · PyMotor 实例上线
