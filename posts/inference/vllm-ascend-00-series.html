一、为什么从「解剖一次执行」开始

推理系统文档里有许多并行、缓存和调度特性。按名字逐项记忆，容易把「功能可以启用」误读成「当前模型已经走到该分支」，也容易把一个版本的收益沿用到另一个版本。这个专栏把研究单位缩小到一次执行：请求在哪一步等待，张量在哪一维分片，谁拥有缓存，哪一次通信真正解除后续计算的依赖。

「解剖室」强调把完整系统拆开再接回去。「vLLM × Ascend」既覆盖上游通用机制，也追踪 Ascend 适配中的算子、通信和运行时差异。专栏保留 MOFANG 博客的整体名称，为这些文章建立一个持续扩展的入口。

每篇都区分四类结论：严格的数学关系、固定版本的代码事实、教学模型的复算结果、真实环境的性能测量。证据适用于哪一层，结论就写到哪一层。

二、已经发布的起点

  1. 01 · 已发布

    SP 到底切了什么：从 Transformer Block 到 PCP、DCP 与 DSA-CP

    用两张卡、四个 token 解释 all-gather、all-reduce、reduce-scatter；推导 attention o_proj 与 FFN down_proj 的部分贡献，解释 RMSNorm 的本地计算条件，再进入 PCP query 分配与 DCP softmax 合并。

    包含逐步交互图、版本对照、通信和显存手算，以及可运行的 NumPy 等价性检查。适合从「为什么 FFN 也要 all-gather」开始建立张量布局的直觉。

第一篇刻意保留版本差异：v0.30.0 的 Dense SP 与旧 DSA-CP 不等于当前主分支的同名配置。后续文章也会把「概念能否组合」与「目标版本是否实现并验证」分别说明。

三、后续可深度研究的特性与问题

下面覆盖本次整理的特性清单，并补上理解它们所需的执行背景。每项先提出可检验的问题，再决定是否值得单独成篇；计划编号用于阅读顺序，未完成条目不创建空文章链接。

  1. 02 · 待研究 · 上下文与缓存分片

    长上下文分给谁：PCP、DCP 与稀疏注意力

    继续展开 PCP 的头尾分配、变长请求、prefix cache、chunked prefill、slot mapping 与 restore map；推导 DCP 的 partial output/LSE 合并，并核对 MLA、GQA、SFA、DSA 各后端的差异。

    研究入口：Context Parallel、Sequence Parallelism。计划产出是一张 query、KV、头、权重与 rank 的所有权图，以及带版本和后端条件的组合矩阵。

  2. 03 · 待研究 · 模型分工与流水

    每层为什么不必使用同样的并行度

    从 attention、o_proj、MLP 的矩阵形状出发，研究不同层的 TP 度数怎样改变通信、临时权重视图和 decode 开销；再分析 PP 的阶段边界与 Dynamic Chunk Pipeline 如何安排计算和等待。

    研究入口：Fine-grained TP、Pipeline Parallelism、Dynamic Chunk Pipeline Parallel。计划通过一张流水时间图解释气泡从哪里产生、何时值得换并行配置。

  3. 04 · 待研究 · 专家并行

    token 怎样找到专家，专家又怎样迁移

    区分模型 Router、token dispatch/combine、专家权重布局和服务端负载均衡；追踪热门专家造成的跨卡不均衡，以及调整专家映射时哪些状态必须保持一致。进一步研究 attention 与专家阶段分离后的边界成本。

    研究入口：Expert Parallelism Load Balancer、Large Scale EP、EPD Disaggregation。计划产出 token 归属与 expert 归属两张表，并记录路由倾斜、通信和专家迁移的成本口径。

  4. 05 · 待研究 · 缓存池与逐层传输

    KV 从一块显存变成跨实例资源

    逐层传输什么时候可以与计算重叠，依赖怎样保证，混合注意力中的普通 KV、卷积状态和递推状态如何交接？同时核对 KVPP 的具体所有权与流水边界，避免只凭缩写推断实现。

    研究入口：KV Cache Pool / Ascend Store、Mooncake Layerwise Adaptation and Optimization、Mooncake Layerwise Hybrid Attention、KVPP。

  5. 06 · 待研究 · 缓存分层与抢占

    把缓存挪到 CPU，什么时候比重新计算划算

    从重算、下沉、预取、恢复四个阶段核算带宽与延迟；区分 decoder KV、encoder cache、稀疏/分层缓存和抢占上下文。计划比较缓存生命周期与调度队列如何耦合，再评估恢复时间和尾延迟。

    研究入口：Layerwise and Sparse KV Cache Offloading、KV Cache CPU Offload、Encoder Cache CPU Offload、Preempt Offload、UCM Deployment、LMCache Ascend Deployment。

  6. 07 · 待研究 · 注意力与投机执行

    一次多算几个 token，怎样真正缩短生成时间

    连接 FlashAttention 的分块、IO 账本与投机解码的起草/验证周期；分析 acceptance length、验证批大小、回滚状态和缓存写入怎样影响收益。已有文章解释算法演进，后续转向 Ascend 具体执行图与 CP、图模式的组合。

    研究入口：Speculative Decoding、Flash Attention；可先读站内投机解码演进与FlashAttention 深入解析。

  7. 08 · 待研究 · 执行图与数值

    换一批请求，为什么数值可能变化

    研究不同 batch shape、归约顺序、量化、图捕获与 padding 如何影响 logits；明确 Batch Invariance 保障的边界，并把「数学等价」「容差内相同」「逐位一致」分别验证。图捕获的稳定地址与动态请求之间也需要一张状态图。

    研究入口：Batch Invariance、Graph Mode、Quantization。后两项是理解性能特性所补充的执行背景。

  8. 09 · 待研究 · 服务调度

    一次更快的计算，为什么未必让请求更快结束

    用相同请求集合比较长短请求混合、在线与批处理混合、prefill 插入和缓存压力；把等待时间、TTFT、TPOT、吞吐与尾延迟同时纳入。研究调度策略改变了谁先获得 token budget，而不只比较单次 forward 时间。

    研究入口：ShortRequestFirst Prefill Scheduling、Batch-Job-Aware Scheduler。计划用可复算的小型队列轨迹解释策略的得失，再设计真实负载实验。

  9. 10 · 待研究 · 加载、启动与扩缩容

    一份模型怎样变成可服务的实例

    研究模型权重从存储到设备的各段成本、重复实例能复用哪些资源，以及 fork 类机制在设备上下文和进程生命周期中的边界。把冷启动拆成读取、传输、初始化、图准备和进入调度池，避免用一个总秒数掩盖瓶颈。

    研究入口：NetLoader、RFork。可以与PyMotor 实例上线连接，区分引擎加载完成和服务真正可调度。

研究顺序沿依赖推进：先理解张量与并行，再理解专家和缓存，最后连接执行图、调度与实例生命周期。同一项特性若依赖多个子系统，会在对应主题之间互相链接。

四、后续每篇怎样形成可靠的结论

4.1 先冻结版本，再确认优化实际生效

记录源码 commit、模型 architecture、权重精度、NPU 与互联、CANN/框架版本和关键配置。阅读启用谓词、模型分支、算子注册和日志，再检查实际执行 shape。文档是入口，配置校验和调用链是机制证据，真实机器的 trace 才能解释时间花在哪里。

4.2 一张图、一份算例、一组可追溯的指标

图负责展示执行顺序与状态所有权；手算或小脚本验证形状和等价关系；性能实验在固定基线下只改变少数因素。没有硬件测量时，就停在源码和数学证据，不把估算画成实际 benchmark。若出现兼容性结论，记录模型、后端、版本与完整组合，而不只写一个勾。

4.3 把失败与回退也纳入模型

一个特性可能因为 token 数、精度、设备能力、图模式或通信拓扑而没有匹配到预期实现。文章需要回答回退到哪里、正确性依赖是否保持、代价如何变化。排障线与成功执行线共同构成可复用的理解。

后续计划不会自动等同于部署建议。涉及大量设备、缓存池或多机网络的方案，需要针对目标负载另做容量、正确性与性能验证，不能只用文档标题决定启用。
