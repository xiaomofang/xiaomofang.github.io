流式返回让请求拥有多个提交边界

从一次中途断开的生成开始

沿着非流式 HANDOFF 已经可以看清 P、ticket、D 和资源释放。将 stream 改为 true 后，客户端会在整个请求完成前看到输出。如果 D 连接在第两个可见 token 之后断开，系统必须知道客户端已经看过什么、引擎还在执行什么，以及下一次尝试应该从哪个状态继续。

这时至少有三种时刻需要分别记录。上游各阶段接受请求，意味着可以满足响应提交屏障。向 ASGI 发送 HTTP 响应头，意味着状态码已经进入发送流程。真正向客户端发送首个 body，又决定了用户是否可能已经观察到内容。源码通过 StreamCommitController、CommitAwareStreamingResponse 和 Router 的 _stream_body_sent 分别处理这些状态。流式提交控制

readiness 屏障保护什么

StreamCommitController 保存本次 attempt 的编号、所需 ready parts 以及 ready/committed 事件。旧 attempt 的迟到 ready 通知会被忽略。CommitAwareStreamingResponse 同时等待上游生成器终止和 readiness，若屏障满足前失败，仍有机会返回带正确 HTTP 状态的 JSON 错误。屏障满足后开始发送响应头，随后 stream pump 才把 body 继续交给客户端。

第一遍阅读问题

在 _stream_response() 中标出 ready_to_commit、mark_commit_started()、mark_committed()，再看 _pump_stream() 如何等待 committed。把它们画成时序，比只搜索 StreamingResponse 更容易理解错误边界。

根请求和 attempt 怎样组织任务

一条用户请求可以经历多次内部执行

PDDispatchSession 保存根请求 id 和 attempt 序号。每次建立 AttemptContext 时，分配新的 pair_id，并保存这次尝试的 P/D 资源、异步任务、派发和完成标志、释放标志、停止锁等。这样，当 attempt 1 已经被终止而 attempt 2 正在生成时，系统仍能辨认旧请求的回调与清理动作。

状态枚举包含 CREATED、DISPATCHING、ACTIVE、FIRST_VISIBLE、DONE、STOPPING、STOPPED。transition() 对 DONE 与停止态有专门保护，终止后的尝试不能被普通进展重新推进。阅读这些枚举时，应同时查看改变它们的调用位置，尤其是流式生成器、错误处理和 finally 清理。Session 与 AttemptContext

请求执行与端点连接共同影响取消

Attempt 会把取消回调登记到 HTTP 连接池，并在 P/D 阶段结束后解除相应登记。HANDOFF 延后选择 D 时，还要等 D client 真正进入连接池再登记 D canceller。端点被移除或连接池清理时，仍在这个端点上的请求可以收到取消信号，而每次尝试的 pair_id 用于区分登记。

cancel() 只取消属于本次尝试、仍未完成且并非当前任务的 P/D task，并等待它们收敛。needs_abort() 则根据“已经派发但尚未完成”判断是否需要向原生引擎发 abort。取消本地协程、关闭 HTTP 连接以及请求引擎中止，是几个有联系的动作，执行顺序要根据具体协议适配器查看。

状态归属练习

把根请求记录在 Worker RequestManager，把 P/D task 记录在 AttemptContext，把负载总量记录在 SHM，把真实 KV 记录在引擎或存储后端。随后分析客户端断开时，哪些记录需要本层清理，哪些需要通过协议或引擎生命周期继续处理。

可见输出之后怎样继续生成

token 身份决定能否构造重放输入

Rescheduler.process_stream_chunk() 解析 SSE 内容，保存原始 prompt token 与累计输出 token。若已经出现可见输出，却缺少与之对应的 token ids，它会将重放进度标记为不完整。收到 finish_reason 或 DONE 后也会记录流已结束。恢复判断因此需要同时检查功能开关、token 缓存完整性、流结束状态和请求合同。

can_resume_after_visible_output() 要求具有 prompt 和输出 token 缓存，通常还要求单 choice。Chat 请求会进一步经过 completions_retry_eligible_for_chat_request()，检查 tools、logprobs、多模态片段、结构化 response_format 等条件。读到这里就能理解为什么“缓存了几个字符串”不足以保证语义一致的续接。token 重放计划与资格判断

一次可以手算的续接

假设原始输入 token 为 [11,12,13]，客户端输出预算为 5。第一轮已输出 [21,22]，随后发生可重试的连接故障。在完整缓存且请求类型受支持时，下一轮使用 [11,12,13,21,22] 作为 prompt，并将后续输出预算调整为 3。已有两个 token 留在客户端，新的模型执行将它们作为历史上下文继续。

教学伪代码
原 prompt         [11, 12, 13]
已输出 token       [21, 22]
重放 prompt        [11, 12, 13, 21, 22]
原输出预算         5
剩余输出预算       5 - 2 = 3

源码的预算调整还带有至少 1 的边界保护，是否执行到该路径受结束状态和资格判断约束。Chat 入口重放会转为 Completions 的 token-id prompt，completion_to_chat.py 再把结果恢复成客户端期待的 Chat 形状。请求字段的移除、预算字段优先级和响应 id/role 等适配，都属于协议连续性的一部分。

重试前还要考虑提交与 Render 状态

UnifiedPDRouter._generate_stream_response() 逐次建立 attempt，并与 Render streaming session 协调。失败处理既检查是否还能重试，也判断是否可以进入混部重启或续接路径。首个 body 尚未发出时，可以考虑从头重试。已经发出内容时，需要满足重放条件，避免再次输出已观察到的内容或破坏客户端响应结构。

阅读边界

先分析单 prompt、单 choice、纯文本的例子，再进入工具调用、多模态和 token-only 分支。将每个资格检查解释成一个具体反例，能够更准确地理解系统支持的恢复范围。

错误分类、取消与负载回收怎样衔接

可重试与可计入熔断分别判断

upstream_error.py 定义了携带状态码、响应体、必要响应头和阶段信息的 UpstreamHTTPError。它还分别提供重试判断和熔断判断。当前可重试 HTTP 集合包含 408、425、429、500、502、503、504，传输层还有连接、读写和协议错误等类型。上游 4xx 通常不会累计为实例故障，5xx 可计入。因而 429 可以具备重试机会，同时避免惩罚实例健康。

客户端主动断连和内部取消也需要携带明确原因。_process_response_error() 会将取消理由转换为请求取消异常，取消类异常不会继续成为普通重试。流式 response 监听 http.disconnect，整体 deadline 超时则携带 infer timeout 原因取消上游任务。两者都要停止工作，但返回语义与告警含义不同。上游错误合同

在不同阶段向客户端表达错误

响应尚未提交时，代码优先保留完整上游错误的状态码和正文，传输超时对应 504，其他传输异常通常对应 502。上游错误体若超过大小限制而截断，则改用完整可解析的错误封装。响应已经提交后，通过 SSE 错误帧表达失败并结束流，状态码的表达空间已经不同。

这要求流式测试通过真正的 ASGI 调用验证 HTTP response start，而不能只迭代 body_iterator。源码保留兼容直接迭代的接口，同时用 single-consumer 检查防止同一原始生成器被两种消费方式同时读取。测试入口不同，会观察到不同的协议时序。

可以用两个细小反例检验这一设计。第一个例子中，上游连接建立成功后立即返回 400，此时应保留参数错误语义，调用者能够依据状态码修正输入。第二个例子中，HTTP 200 已经发出，随后 D 的读连接断开，客户端需要从事件流中的错误对象知道生成没有正常完成。把这两个错误统一写成一个空输出，会丢失决定下一步行动的信息。

清理也有并发顺序

BaseRouter._manage_request_context() 在 finally 中使用取消屏蔽作用域，等待必要清理并删除请求记录。_reclaim_residual_workloads() 先等待尚未结束的后台释放，再弹出残余负载。若后台释放已经更新 SHM、但本地记录还未完成确认，此时直接再次回收就可能重复扣账。源码因此明确协调 drain、确认和残余处理。请求上下文与残余负载回收

故障练习

给第一次 attempt 分配 P 负载 100、D 负载 80，令 P 已完成、D 输出两个 token 后断连。标出 P 的后台释放、D 的停止、重放计划、新 attempt 分配和根请求最终清理，逐项检查每笔实际提交量怎样被结算。

从一个请求失败扩大到实例熔断

Mgmt 汇总跨 Worker 的实例证据

Worker 通过 report_cb_event() 把成功或可计入的失败发给 Mgmt。CircuitBreakerManager 以 instance_id 为键保存连续失败数、触发次数和当前恢复等待时间。任一端点的失败可能使整个协作实例进入 open，这与大 EP 实例内部的耦合边界有关。

当连续失败达到配置阈值时，Mgmt 先把该实例 SHM 槽位设为 BLOCKED，再通知 Worker 更新本地状态。这样尚未收到通知的 Worker，在 CAS 分配入口仍然能遇到阻断检查。连续成功会清零失败数，已有在途请求的成功也可能触发提前恢复。实例级熔断状态、SHM 阻断与状态广播

定时器到期还要主动探测

恢复等待时间按触发次数指数增加，并受上限约束。Mgmt 的恢复任务到期后，会检查实例仍在可用池中，并要求所有可调度端点的原生 health 返回成功，之后才解除阻断。探测失败则延长等待并安排下一次探测。若成员已经由 Controller 移除，相关恢复状态应随之清理。

当前领域对象显式状态为 open/closed，探测由运行时组织。阅读时应对照真实枚举、定时任务和池成员检查，再描述状态机。请求重试、实例熔断、Controller 实例恢复处在不同范围，各自的证据和完成条件需要分别记录。

构造一条连续结果序列也能帮助理解计数。设本次配置的失败阈值为三，报告顺序是失败、失败、成功、失败、失败、失败。中间的成功清除了前两次连续失败，最后三个失败才触发本轮隔离。若 open 后还有已经在途的请求成功返回，运行时可以提前关闭并取消恢复计时。这个行为依赖跨 Worker 消息到达时机，测试要同时检查共享阻断标志和后续通知。

一致性检查

假设 Worker A 已收到 open，Worker B 还保留旧成员视图。追 B 的 CAS 检查能否挡住分配，再追 Controller 删除实例后恢复定时器怎样退出。这个例子串起广播延迟、共享状态和成员生命周期。

输出异常检测怎样接入同一条请求链

先领取抽样资格，再收集额外字段

HTTP 成功仅提供传输层和服务层事实，输出异常检测还需要 token 与 logprob 信息。SampleController.claim_sample() 在发送引擎请求前按 D 实例领取抽样窗口，生产调用通过调度客户端进入 Mgmt 统一协调，避免多个 Worker 在同一窗口重复抽样。调用失败时放弃本次资格，测试场景才使用本地状态。

router/precision_sample/request.py 注入采样所需字段，response.py 提取 token/logprob，sample_builder.py 构造包含 P/D 身份、prompt/output token、对齐 logprob 与 trace 信息的 DecodeSample。给客户端返回结果之前，还需要按照客户端原始合同去掉仅为内部检查添加的字段。样本检查由被跟踪的后台任务执行，关闭时取消并排空。抽样入口与后台生命周期

检查器失败也有独立语义

checker.py 定义 CheckResult，同时保存 has_issue 和 valid。缺失 logprob、长度不对齐或检查器内部异常时，valid 可以为 false，这类样本不会推进异常或正常连续计数。msprobe detector 使用进程内单例，工作在线程中执行，并通过进程内锁保护其可变状态。

PrecisionReporter 按 P/D group 组织检查与结果上报，生产路径把连续异常、连续正常以及告警动作状态交给全局调度状态协调。达到动作条件后，InternalRouterProbe 构造固定问答，通过相同 Router 与 Scheduler 路径，定向到触发异常的 P/D group。探测自身关闭 sampling_manager，避免再次生成抽样链。

探测结果继续进入告警闭环

PrecisionAlarm.execute() 在 raise 路径运行探测，将异常计数、探测失败数和实例信息组织为告警发给 Controller。clear 路径需要原告警的 moi，确保解除动作对应同一告警身份。Reporter 跟踪动作结果，避免跨 Worker 重复探测或错误地清除其他告警。Reporter 状态衔接、探测与告警动作

例如，某个 P/D group 先出现两次有效异常，随后检查器因为 logprob 缺失返回 invalid，再出现一次有效正常。这里 invalid 说明本次检查缺少可信判断，不应被当成正常结果推动解除，也不应被当成新的异常推进告警。具体连续计数与动作规则由 Mgmt 侧维护，Reporter 负责把结果完整提交。将检测算法输出的可信度与服务健康动作分开，可以降低数据采集故障造成的误报。

抽样资格以 D 实例为粒度，结果关联却包含 P/D group，两种键服务于不同问题。前者控制同一 D 的额外采样开销，后者帮助在异常时定位组合路径。混部请求的 P 身份可为空，仍能使用同一份样本模型。阅读 DecodeSample 时注意这些可选字段，才能解释为何普通业务请求、混部和内部探测能够共用后续接口。

发过响应头与发过可见内容有什么区别？

参考回答

发送响应头后，客户端已经获得 HTTP 状态与协议合同。发送可见正文后，客户端又拥有一段输出前缀。StreamCommitController 先等待所需上游阶段就绪，CommitAwareStreamingResponse 随后发送响应头，再允许 stream pump 输出正文。

源码把 readiness 也作为语义提交边界，需要留意刚就绪但响应头尚未发送的窄窗口。首 body 前的普通传输重试仍可建立新 attempt，已有可见输出后，续接要满足 token 重放条件。已经提交响应的终态错误通过流内错误合同结束。

源码定位 · StreamCommitController 与 CommitAwareStreamingResponse._stream_response()

继续追问 · 说明何时还能替换错误状态，何时必须保持已输出前缀。

追问参考 · 屏障尚未满足且响应未提交时，上游最终失败仍可返回对应 HTTP 错误状态。响应头发送后保持已提交状态，正文发送后还要保持客户端已经观察到的内容前缀。混部整次 restart 另受 commit_sealed 门槛限制。

流式重试需要哪些条件？

参考回答

先判断错误是否可重试，并确认仍有传输重试次数。可见输出之后，Rescheduler 还要求续接开关已启用、prompt 与累计输出 token 缓存存在、进度完整且流未结束，n 必须为 1。Chat 请求会继续校验工具、logprobs、多模态和结构化格式等限制。

满足资格后，用原 prompt 与累计生成 token IDs 构造下一轮输入。Chat 入口转为 Completions 的 token-id prompt，再适配回客户端响应形状。预算根据累计输出调整，当前下发 max_tokens 至少为 1，其字段边界还要与流完成状态一起解释。

源码定位 · Rescheduler.can_resume_after_visible_output()、build_retry_plan() 与 apply_retry_plan()

继续追问 · 把缓存 token 拼入下一轮输入，并计算剩余生成预算。

追问参考 · 原 prompt 为 [11,12,13]，已输出 [21,22]，预算为 5，重放输入成为 [11,12,13,21,22]，后续预算为 3。旧输出保留在客户端，后续内容接着发送。若已经缺失可见片段的 token IDs，重放进度会被标记不完整。

客户端取消为什么要单独分类？

参考回答

客户端取消表达用户已离开，处理目标是停止无用工作并收尾。代码沿取消原因传播 CLIENT_DISCONNECT，流式响应监听断开并取消生成任务。上游传输失败则另行判断是否重试、是否报告实例故障，归因错误会影响其他请求可用的候选集合。

AttemptContext 保存本次任务和资源，停止路径取消相关任务并释放分配。RequestManager 记录当前 Worker 中请求及尝试对应的实际负载。根上下文在取消屏蔽范围内等待后台释放，再回收残余账目并删除请求记录，减少中途取消造成的遗漏和重复扣账。

源码定位 · BaseRouter._manage_request_context() 与 _reclaim_residual_workloads()

继续追问 · 沿 upstream_error、AttemptContext 和 RequestManager 找到处理边界。

追问参考 · upstream_error 判断重试与熔断资格，AttemptContext.stop()/cancel() 停止任务，RequestManager 配合根上下文清账。客户端断开后停止上游，不当作实例故障重试。可重试超时可进入新 attempt，参数类 4xx 通常不重试，也不报告为实例熔断故障。
