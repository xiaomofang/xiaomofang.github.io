一、先问一个能串起全项目的问题

1.1 从一个模型进程到一个推理服务

设想一套已经能运行模型的 vLLM 引擎。输入 prompt，执行 Prefill，循环 Decode，返回生成结果。模型执行的最短闭环已经成立。接下来把它扩展到多个节点，新的问题会连续出现。多个 Pod 怎样认识彼此，哪个节点成为通信入口，哪些引擎负责 Prefill，哪些负责 Decode，请求由谁选路，某个 DP 失败后哪些入口仍能使用，这些问题共同构成了 Motor 的工作范围。

MindIE Motor 把原生引擎组织成具有生命周期、调度规则和恢复机制的服务。阅读时可以持续跟踪一个问题——一条用户请求如何找到一组已经准备好的引擎，并在结束时留下正确的系统状态。这个问题会经过配置、部署、注册、资源发布、阶段编排、负载记账和故障恢复，恰好覆盖项目的主要模块。

1.2 一次请求与一次实例生命周期

请求的生命周期通常从接入开始，到响应结束和资源清理结束。实例的生命周期更长，从节点注册开始，经历组装、启动、健康检查、上线、暂停、故障和删除。一个运行中的实例会处理很多请求。把这两条时间线分别画出来，再找交点，会比按目录逐个阅读更容易建立因果关系。

本系列的阅读单位是状态变化。每进入一个函数，都记录调用者、输入、读写的状态、输出和失败收尾。这样可以从文件之间的跳转恢复出系统行为。

二、五个角色怎样协作

角色 输入与职责 主要输出
Coordinator 接收请求，维护路由成员视图，选择 P/D/U 端点，转发并处理响应 引擎请求、客户端响应、请求级负载变化
Controller 消费注册、心跳和故障证据，组织逻辑实例与恢复计划 启动命令、实例状态、成员变更、恢复事务
NodeManager 读取本地配置并执行管理命令，监督引擎与辅助服务 原生进程、健康状态、注册与心跳
Engine 执行模型，管理序列、KV 和设备侧通信 token、KV 交接信息、指标和缓存事件
KV Conductor 消费缓存事件，维护模型与租户下的连续前缀位置索引 按实例和 DP 划分的缓存覆盖

普通推理时，Coordinator 直接连接引擎业务端口。NodeManager 通过管理路径影响这些端口的生命周期。缓存亲和启用后，Worker 查询 Conductor 获得选路信息。三种网络访问承载不同的数据，阅读日志时需要先判断它属于哪条路径。

后续文章中出现的 Scheduler 指 Motor 的请求端点选择器。引擎内部的批处理调度器与 MoE 专家选择器，分别需要继续追踪引擎和模型执行代码。

三、先认识贯穿各模块的资源对象

3.1 Instance、Pod、Endpoint 与 Device

Instance 表达一个逻辑协作实例，保存角色、并行配置、NodeManager 列表和端点集合。Endpoint 表达可定位的引擎入口，携带 IP、业务端口、设备信息和状态。默认多端点模式通常把 endpoint 身份关联到全局 DP rank。一个 Pod 可以提供多个端点，一个实例也可以跨越多个 Pod。

跨节点执行时，一些节点参与计算但以 headless 方式运行。业务候选集合通过 get_all_endpoints() 过滤这类端点。关闭多端点等部署模式还可能由一个 HTTP 入口承载引擎内部多个 DP，因此阅读时应以配置和访问器为准。资源对象与端点访问器

3.2 一个可以手算的并行例子

取一个教学拓扑，PCP 与 PP 都为 1。P 侧配置 DP1、TP16，D 侧配置 DP8、TP2，并开启 EP。Motor 内部对常规并行配置采用以下规模关系。

\[W=D\times C\times T\times P,\qquad W_{\mathrm{local}}=C\times T\times P\]

这里 D、C、T、P 分别表示 DP、PCP、TP、PP 的规模。P 侧为 1×1×16×1=16，D 侧为 8×1×2×1=16。当前 ParallelConfig 在 enable_ep=True 时把内部 ep_size 设为 world_size。启用 EP 后，应结合引擎如何组织这些 rank 理解专家布局，额外再乘一次 EP 会重复计算设备规模。

在默认多端点模式下，D 侧可提供 8 个 DP 入口。请求选中其中一个入口后，MoE 专家阶段仍可能依赖同一并行域的其他 rank。这个协作关系决定了故障处理有时需要以整个 Instance 为边界。ParallelConfig 与 Instance

3.3 请求也有根身份与尝试身份

RequestInfo 随请求携带原始数据、token、时间点和追踪信息。请求可能在传输失败后进入下一次内部尝试，AttemptContext 保存该次尝试的 P/D 资源、任务和释放标记。把根请求和尝试分开，才能准确说明某个端点分配属于哪一轮，以及重试之前应该清理哪些状态。

四、进程边界决定状态归谁所有

4.1 Coordinator 内部有多个进程

Coordinator 的父 Daemon 组织 Mgmt、Obs 和多个 Inference Worker。Mgmt 先启动，使控制通信和共享内存准备好，其他进程再连接。SchedulerServer 位于 Mgmt 内，Worker 的 SchedulerClient 本地执行选点并通过 Rust 共享内存提交高频负载变化。当前架构可以沿着启动函数直接验证。CoordinatorDaemon.run

状态 所在位置 典型变化
实例生命周期 Controller 的 InstanceManager 注册、健康、隔离、恢复、删除
调度成员与控制状态 Coordinator Mgmt，并传播到 Worker ADD、DEL、SET、熔断变化
请求与按请求记账 当前 Inference Worker 的 RequestManager 请求加入、分配记录、释放与收尾
并发负载槽位 同一 Coordinator 进程组的共享内存 CAS 加减、BLOCKED、槽位代际变化
实际 KV 张量 引擎及配置的缓存后端 分配、复用、传输、下沉和淘汰
缓存位置索引 KV Conductor 事件更新、前缀查询、注销清理

4.2 看见多个 InstanceManager 时怎样判断职责

Controller 的 InstanceManager 管实例生命状态，Coordinator 的同名对象维护路由成员视图，Worker 还缓存用于本地选路的数据。它们通过消息与版本衔接。继续追问“谁能决定状态”和“谁只是消费状态”，就能解释为什么控制面修改之后，请求侧还需要一次传播过程。

ZMQ 承载成员同步与控制消息，共享内存承载高频负载变化，HTTP 承载注册、管理和引擎推理。etcd 用于选主、锁和状态持久化。把通信方式与状态归属放在一起读，才能解释丢通知、进程退出和切主时如何恢复视图。

识别进程边界后再理解单例。线程安全单例在各进程中分别创建，跨 Worker 的一致性需要显式通信或共享内存机制。

五、把目录压缩成三条阅读路线

5.1 请求执行线

InferenceServer
  → dispatch.handle_request
  → TokenizationService / RequestInfo
  → UnifiedPDRouter / AttemptContext
  → SchedulerClient.select_and_allocate
  → P 请求 → handoff ticket → D 请求
  → 响应整理 → 负载释放 → 请求记录回收

第一遍只读单 prompt、非流式的 HANDOFF。这样每个阶段都有明确的输入输出，能先看懂 P/D 协同的骨架。第二遍再加入 token-only、Render、流式提交和协议分支，避免一开始进入大量异常和兼容代码。

5.2 实例上线线

用户配置 → Deployer → boot.sh → 角色 main
  → NodeManager 注册 → Controller 组装
  → StartCmd → LaunchSpec → 原生引擎
  → 心跳 → ACTIVE → 观察者事件
  → EventPusher → Mgmt → Worker 候选集合

这一条线解释请求到达之前的准备工作。进程启动、原生健康检查通过、实例进入 ACTIVE、Worker 看见可用端点，分别有自己的完成条件。沿这些条件读源码，可以识别“启动成功”究竟指哪一层。

5.3 故障恢复线

请求错误 / 健康异常 / 引擎 FT / 硬件证据
  → 请求级取消与重试，或实例撤流
  → FaultManager → RecoveryPlanner
  → 恢复策略 → NodeManager → 原生引擎
  → 幸存端点视图 → 重新发布服务

故障线把前两条线重新连接起来。一个请求失败可能只需要换一次尝试，也可能暴露实例级问题。恢复需要重新确认哪些端点能够承接请求，并让后续成员同步继续遵守恢复结果。

目录 第一遍关注 后续深入

每轮只扩大一个维度。先沿成功路径明确对象和顺序，再增加并发、重试和拓扑变化。复杂性逐步加入，已经建立的调用关系就能持续复用。

六、如何把阅读变成可复述的理解

6.1 九篇文章的递进关系

第 1 篇从配置与注册追到上线，建立资源来源。第 2 篇跟踪完整请求，建立阶段关系。第 3 篇进入调度与共享内存，解释多个 Worker 的竞争。第 4 篇连接缓存索引和负载收益。第 5 篇处理流式、取消、重试和精度探测。第 6 篇下沉到 NodeManager 的原生进程管理。第 7 篇重新回到 Controller，理解大 EP 恢复。第 8 篇用指标、测试和复盘建立验证证据。

6.2 每篇留下一个可以检查的产出

最短练习是给一个请求起名 R1，记录它的 req_id、attempt、P/D endpoint 和每次负载增减。再给一个实例起名 I1，记录各节点什么时候注册，什么时候启动，哪个心跳导致它上线。最后模拟一个 DP 异常，标出请求侧、控制器和引擎各自做什么。三张时序图会把阅读中的零散函数连接起来。

测试可以作为第二份接口文档。先看 fixture 构造了什么对象，再看断言确认什么行为，最后回到实现寻找保障。读测试时无需立刻准备真实模型环境；实际执行测试则遵守仓库的 tests/run_tests.sh 入口，并区分通过、跳过和真实硬件覆盖。

6.3 从源码理解走向技术表达

项目介绍可以围绕“请求如何找到引擎、引擎如何变成服务、服务失败后如何恢复”展开。个人经历则进一步说明自己完成了部署、压测、排障、实验还是代码修改。每项性能结论都要保留模型、硬件、并行配置、输入输出长度、并发、基线与统计口径。后续文章中的算例用于解释公式，实际收益需要实验记录支撑。

本系列对照源码提交 841e50df，写作日期为 2026 年 11 月 11 日。公开代码可能继续演进，定位时同时保留版本和符号名。当前内容来自静态源码阅读，集群吞吐、精度和恢复时间要通过相应环境验证。
