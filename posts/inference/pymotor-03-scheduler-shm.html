请求已经走到 BaseRouter.prepare_resource()，下一步需要选择具体端点。如果系统只有一个 Worker，读取负载、选最小值、加上新请求负载，看起来已经足够。多个 Worker 并行执行时，同一份旧视图可能被反复选中，端点还会在健康变化或恢复过程中被删除。调度因此同时涉及策略与并发状态。

本篇沿 AsyncSchedulerClient.select_and_allocate() 展开，先解释评分与记账，再进入共享内存布局、CAS 竞争和清理。KV 亲和的索引和分层公式在下一篇展开，这里先把它放回完整的分配机制。

一、实际请求通过哪个 Scheduler

1.1 Mgmt 管成员，Worker 执行选点

当前 Coordinator 使用多进程运行。scheduler/runtime/scheduler_server.py 在 Mgmt 内组织成员、共享内存、控制消息与全局状态。Inference Worker 中的 AsyncSchedulerClient 持有本地缓存，读取共享负载，执行候选选择与分配提交。阅读 scheduler.py 时应结合这个生产调用路径理解它的辅助职责。

这条设计减少了每次分配和释放都访问中央调度 RPC 的往返。成员控制仍通过 IPC 同步，缓存亲和查询也可能访问 Conductor，因此应明确哪项操作走共享内存、哪项操作仍需要通信。Worker 调度主路径

模块 所处位置 核心责任
runtime/scheduler_client.py Inference Worker 成员缓存、策略调用、CAS 提交、释放和控制消息
runtime/scheduler_server.py Mgmt 成员刷新、SHM owner、熔断与精度控制状态
runtime/scheduler_connection_manager.py Worker/Obs 生命周期 建立与关闭运行时连接
runtime/zmq_protocol.py 通信边界 消息类型及序列化合同
allocate_arbitration.py Worker 内的公共逻辑 验证候选、竞争后重新读取与选择
runtime/kv_usage.py、dp_stats.py、scheduler_metrics.py 调度观察与辅助 KV 压力、各 DP 分布和运行时指标

1.2 策略之前先建立可行集合

角色、引擎类型、协议能力、定向约束和熔断状态先决定哪些实例能够处理请求。一个负载很低的端点，如果无法满足当前 P/D 协议，也不能成为合法目标。算法上的最优应当在可行集合内讨论，否则分数再低也无法完成请求。

把分配拆成“可行性过滤、候选排序、并发提交、请求记录”四个阶段。每一阶段对应不同的失败原因，日志与测试也应按这些边界理解。

二、四种策略各自观察什么

2.1 按角色选择策略

SchedulerConfig 将 prefill 与 decode 策略分开。P/U/E 按 Prefill 侧配置选择策略，具体亲和能力还受角色分支限制。当前动态分桶正式配置用于 Decode，Decode 也支持负载均衡和轮转，KV 亲和主要用于 P/U。配置字段与实际角色分支要一起阅读。调度配置与角色约束

策略 主要信号 适合解释的问题 源码入口
load_balance 端点负载、实例平均压力，D 可结合 KV 压力 怎样避免把流量继续送到繁忙目标 policy/load_balance.py
round_robin 轮转计数与可用端点 怎样以简单规则分散请求 policy/round_robin.py
kv_cache_affinity 缓存覆盖、剩余计算估计、当前负载 怎样利用重复前缀且避免热点 policy/kv_cache_affinity.py
dynamic_bucket 输入长度、桶平均负载、长度与负载亲和 怎样缓解长短请求混合干扰 policy/dynamic_bucket.py

2.2 轮转与动态分桶的调用方也很重要

Round robin 容易帮助建立策略接口概念，但多个 Worker 各自维护计数和偏移，严格的全局串行轮转顺序需要结合实际实现判断。策略的共同分配路径仍然管理在途计数，即便该策略提交的 token 增量可以为零。

DynamicBucketSelector 先按确定顺序把 endpoint 分成短桶与长桶，更新桶平均负载，再结合输入长度与负载比例，利用 sigmoid 计算是否切换目标桶，最终选择桶内轻负载端点。selector 由 Worker 持有，某些通用策略入口直接回退到负载均衡。因此只看类的默认方法，可能错过真正的动态分桶生产路线。动态分桶和 Worker-owned selector

策略名称只告诉读者大体思想。完整行为还由角色过滤、Worker 持有的运行状态和分配提交路径共同决定。

三、评分、需求和提交量为什么要分别记录

3.1 先手算一次负载均衡

基础负载均衡对端点评分时，既关注该端点的负载，也保留一小部分实例整体压力。实例总负载按可调度端点数归一化，避免大 DP 实例仅因端点多就被额外惩罚。默认实例压力系数为 0.05。端点优先的复合评分

\[S(e)=L_e+\alpha\frac{L_{\mathrm{instance}}}{N},\qquad \alpha=0.05.\]

设 A 端点负载 100，所在实例总负载 1,000，有四个可调度端点。B 端点负载 108，所在实例总负载 200，有两个端点。两者评分分别为 112.5 和 113，A 略优。若 A 已接受一个负载 20 的请求，端点负载变为 120、实例总负载变为 1,020，评分便变为 132.75，此时 B 更合适。这个例子同时说明实例项应随提交后的账本变化更新。

3.2 active_tokens 是调度模型中的数值

domain/workload_calculator.py 定义不同角色的需求估计。P/U 在已经获得有效 token IDs 时使用输入 token 数，缺少 token 时使用历史字节长度估计。普通 D 路径当前返回请求体长度的浮点值。E 则根据多模态内容计算相应估计。因此，变量虽然叫 active_tokens，解释指标时仍需说明使用的是哪条路径。

例如一个 JSON 请求体为 6,000 字节，tokenization 得到 2,048 个输入 token，普通 P 需求可为 2,048，而普通 D 需求代理值为 6,000。两者可以分别用于同角色候选之间的比较，不能据此得出 D 真实计算量是 P 的近三倍。角色需求与亲和提交量

3.3 亲和排序成本与最终提交量

亲和策略从输入长度 I 和加权命中 M 估计剩余计算，再结合已有负载排序。选中最终端点之后，P/U 亲和提交量为 max(0, I-M)。排序中的 overlap_credit 和各评分权重有各自用途，不会按同一公式再次乘进提交量。动态分桶与轮转又有自己的需求路径，源码通过 candidate_policy 和角色确定最后采用的数值。

建议对每次分配记录五列。输入长度属于请求表示，matched 属于缓存收益模型，score 属于排序，committed 属于共享账本增量，实际延迟属于运行测量。把它们分别放在表里，能够解释“命中提高却没有变快”等现象。

四、共享内存同时承载成员结构和高频负载

4.1 Python 与 Rust 之间的布局合同

Python 端 workload_shm/layout.py 定义结构，writer 管成员和状态标记，reader 读取视图并检查版本和心跳，native 经 ctypes 连接 Rust。Rust crate workload_shm_rs 定义对应布局、错误码和原子操作。

该版本布局为 schema 5，头部 64 字节，每个端点槽位 32 字节。槽位包含 instance_id、endpoint_id、role、flags、generation、request_count、active_tokens 和 total_requests。头部还保存成员版本、心跳序列及角色相关序列。部分历史函数名仍含 v4，应以实际布局和版本检查为准。schema 5 共享内存布局

机制 保护的对象 避免的问题
seqlock 成员结构快照 读到一半新、一半旧的成员表
CAS 高频负载提交 多个 Worker 基于同一旧值覆盖更新
generation 槽位复用后的资源身份 旧请求继续操作已经分配给新成员的槽位
VALID / BLOCKED 当前槽位可分配状态 成员缓存传播期间仍向失效或隔离目标提交
heartbeat 共享段所属 Mgmt 的时效 长期使用已经陈旧的运行状态

4.2 为什么成员快照需要一致读

Mgmt 写成员结构时会推进 seqlock 序列。读者在读取前后检查序列，发现写入中或版本发生变化便重新读取。由此可以得到同一版本下的端点身份、数量与状态结构。高频负载仍由槽位原子操作更新，两类机制保护不同频率和粒度的数据。

共享内存建立在同一 Coordinator 的进程组中。多个 Coordinator Pod 各自拥有自己的运行时，不能把这份共享段解释为全服务所有进程共同访问的分布式全局账本。部署规模变化时，应进一步确认负载视图的作用范围。

布局可以做一次容量手算。默认最大槽位数为 10,240，若只按头部与槽位主体计算，字节数为 64 加上 10,240 乘以 32，得到 327,744 字节。这个量说明用于选路的紧凑计数结构可以保持较小体积，但成员对象、HTTP 连接和请求缓存另有自己的内存成本。测量进程 RSS 时需要把这些结构分别归因。

同一槽位里也保存了多个统计量。active_tokens 用于负载估计，request_count 表达当前在途分配数量，total_requests 表达累计分配。一个亲和请求可能因完整命中而提交很小甚至为零的 token 增量，但它仍是一条需要管理生命周期的请求。观察零负载时，配合在途和累计计数，才能区分“没有请求”与“请求的模型增量很小”。

可行性检查与最终提交都要识别资源状态。成员通知让 Worker 尽快更新认识，共享段检查在提交边界再次确认目标是否仍可用。

五、两个 Worker 同时选择同一端点会发生什么

5.1 用一个竞争例子理解 CAS

假设 A 当前负载为 100。Worker X 和 Y 都读到了这个数，分别希望增加 20。X 用期望旧值 100 提交，成功后 A 变为 120。Y 仍以 100 为期望值提交时，原子比较发现旧值不一致，返回 CHANGED。Y 重新读取负载并进入仲裁，可以继续选择 A，也可以因其他端点更轻而改选。

若 X、Y 最终都选择 A，两次合法增加得到 140。后续两次请求分别释放 20，账本回到 100。关键条件是每次成功分配记录实际提交量，并在清理时按该记录释放。这个例子没有模拟成员变更，加入 generation、BLOCKED 和 SLOT_INVALID 后，还能覆盖端点被隔离或槽位被替换的情况。

5.2 不同失败码对应不同动作

select_and_allocate() 处理 OK、CHANGED、BLOCKED、SLOT_INVALID 等返回。OK 后修补本地缓存、记录各 DP 分配并输出最终 scheduled 日志。CHANGED 会刷新后重新仲裁，BLOCKED 与 SLOT_INVALID 会排除候选后继续尝试。重试次数受限，耗尽后返回分配失败。原生动态库未接入时，当前路径也会拒绝分配。

allocate_arbitration.py 将“候选是否仍然有效”与“如何根据新负载重选”封装为公共逻辑。unified 亲和重选可携带各端点 Prefill 成本，配合更新后的复合负载重新评分。快路径与重选路径的日志 score 口径需要结合调用点解释，最终端点以成功提交的 scheduled 记录为准。候选验证与重新仲裁

将这个过程接到性能分析，调度耗时至少包含视图刷新、策略计算、可能的外部索引查询和 CAS 重试。只测评分函数的运行时间，无法完整描述请求在调度阶段停留多久。相反，看到某次调度较慢，也应先区分查询等待、竞争重试和成员同步，才能判断该优化算法、通信还是状态传播。

CAS 保障一次比较更新的原子性。请求完整生命周期还需要成员身份检查、提交后的本地记录、异常补偿和释放确认共同完成。

六、分配正确之后，怎样把负载还回去

6.1 两份状态之间的补偿

共享账本与 Worker 请求记录是两个状态载体。前者已经增加负载，而后者写入失败时，资源申请代码需要尝试回滚。执行阶段结束后，释放逻辑根据 req、attempt、角色和端点归属找到实际提交量，成功确认后再清理记录。重复释放与遗漏释放都会改变未来选点，因此释放标记和确认顺序值得精读。

请求退出时，BaseRouter._manage_request_context() 在保护取消的清理范围内等待后台释放，再回收残余记录。先等待在途释放是为了避免同一份记录同时被正常释放和残余回收两次扣减。若等待过程本身失败，源码也有相应保护分支。这个清理保证应在具体运行边界内理解，进程突然消失等故障还需要结合生命周期与恢复机制分析。请求级账本补偿与清理

6.2 建议阅读的测试与练习

先用 test_load_balance_policy.py 核对评分，再读 test_dynamic_bucket.py 观察长度、桶划分和负载边界。随后进入 test_allocate_arbitration.py、test_workload_shm_native.py 与 test_base_router_prepare_resource.py，把竞争、布局、候选失效和补偿连接起来。Rust 测试与 Python 原生桥接测试还能够检查 ABI 和结构版本。

练习分三轮。第一轮手算 A/B 的复合评分，改变实例端点数观察结果。第二轮在纸上模拟 X/Y 同时提交，让 Y 经历一次 CHANGED。第三轮在 Y 重试前删除 A，解释旧 generation 与 SLOT_INVALID 怎样影响选择。每一轮都追加正常结束、客户端取消和资源记录失败三种清理分支。

完成后用自己的话分别说明一个算法决策和一个并发保证。前者解释候选为什么更优，后者解释其他 Worker 和成员变化发生时结果怎样提交。两方面都能对应到函数、输入和测试断言，才能把调度机制讲完整。
