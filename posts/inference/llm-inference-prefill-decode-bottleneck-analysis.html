LLM 推理性能怎么分析：从 Prefill、Decode 到 PD 分离与并行策略

LLM 推理部署不是先背「TP 多少、DP 多少」的经验，而是先把请求拆成计算形状、访存、通信和调度。 一旦看清 vLLM / PagedAttention、 DistServe 这些系统背后的共同结构，就能独立判断为什么 prefill 偏 compute-bound、decode 偏 memory / latency-bound，以及 PD 分离该怎么配。

PD 分离 推理框架 硬件与 Kernel

2026年8月18日 · MOFANG

这篇文章写给一个很具体的问题：看到类似 4p(tp=8,dp=1), 2d(dp=8,tp=2) 的配置时，为什么有人能快速判断 「decode 侧 TP=2 通常更稳」「长 prompt 要看 prefill 队列」「长上下文要看 KV cache」？这不是玄学，也不是只靠经验。 它背后有一条可复用的分析链路：

\[ \text{请求长度分布} \rightarrow \text{算子形状} \rightarrow \text{计算 / 访存 / 通信瓶颈} \rightarrow \text{并行策略} \rightarrow \text{TTFT / TPOT / 吞吐 / 尾延迟} \]

一、第一性问题：同一个模型，为什么 Prefill 和 Decode 瓶颈不同

Decoder-only Transformer 的一层可以粗略拆成 QKV projection、attention、O projection、MLP、norm 和 residual。 训练时我们习惯把它看成一个整体，但推理时必须拆成两个阶段：prefill 处理已有 prompt，decode 逐 token 生成新内容。

阶段 输入形状 主要动作 常见瓶颈
Prefill [B, S, H] 一次性处理 prompt，写出整段 KV cache 大 GEMM、attention 计算，通常更偏 compute-bound
Decode [B, 1, H] 每步生成 1 个 token，读取历史 KV，再写入新 KV KV 读取、通信同步、调度开销，通常更偏 memory / latency-bound

这里的关键不是「prefill token 多、decode token 少」这么简单，而是矩阵形状变了。设 batch size 为 \(B\)，prompt 长度为 \(S\)，hidden size 为 \(H\)。 prefill 里 MLP 的大矩阵乘接近：

\[ [B\cdot S, H] \times [H, 4H] \]

decode 每步则接近：

\[ [B, H] \times [H, 4H] \]

当 \(S\) 很大时，prefill 的矩阵乘有足够多 token 维度去摊薄 kernel launch、访存和通信开销；decode 每次只有一步，除非 batch 非常大，否则 GPU 很容易吃不满。

第一条结论： prefill 的大 GEMM 计算密度高，通常更能吃 Tensor Core；decode 的每步计算小，还要读历史 KV、做通信和调度，所以更容易被显存带宽、通信延迟和调度开销限制。

二、用 Roofline 判断：到底是算不动，还是喂不饱

性能分析里最有用的入门模型是 Roofline。它不告诉你全部细节，但能逼你先问一个问题：一个算子慢，是因为算力不够，还是因为数据搬运不够快？

\[ T \approx \max\left(\frac{\text{FLOPs}}{\text{Peak FLOPS}},\frac{\text{Bytes}}{\text{Memory Bandwidth}}\right) \]

另一个等价视角是 arithmetic intensity：

\[ \text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes}} \]

如果一个算子每读 1 byte 能做很多计算，它更可能 compute-bound；如果读写很多、计算很少，它更可能 memory-bound。 大 GEMM 往往计算密度高，KV cache 读取、LayerNorm、sampling、小 batch decode 往往计算密度低。

模块 读写特征 计算特征 直觉判断
Prefill MLP / QKV GEMM 权重和激活可在 tile 内复用 矩阵大，FLOPs 多 更偏 compute-bound
Decode KV attention 每步读取历史 K/V，长度随上下文增长 当前 query 很少 更偏 memory-bandwidth-bound
TP collective 跨 GPU 交换 partial result 不产生模型计算 更偏 communication-bound
Scheduler / batching 元数据、队列、block 管理 模型计算外开销 更偏 latency-bound

这解释了为什么「GPU 利用率低」不能直接等价于「卡不够」。decode GPU 利用率低，可能是 batch 不够大，也可能是 HBM 带宽、KV cache、TP 同步或调度器把它卡住了。

一个手算例子：为什么 decode 会被 KV 拖慢

假设模型有 80 层，GQA 后每层 KV 大约需要读取 16 个 KV head，每个 head 维度 128，bf16 为 2 bytes。 单个请求、上下文长度 8192 时，每步只读 KV 的量近似是：

\[ 2 \times 80 \times 8192 \times 16 \times 128 \times 2 \approx 5.37\ \text{GB} \]

这里的第一个 2 是 K 和 V。实际实现会有并行切分、cache layout、kernel 优化和重用，但这个数量级足够说明：长上下文 decode 每生成一个 token 都在持续扫描历史状态。

三、KV Cache 是 Decode 的第二个模型

很多新手分析 decode 时只看权重大小，但线上 serving 里 KV cache 经常和权重一样重要。KV cache 的显存占用近似为：

\[ \text{KV} \approx 2 \times L \times S \times H_{kv} \times D_{head} \times \text{bytes} \times B \]

其中 \(L\) 是层数，\(S\) 是上下文长度，\(H_{kv}\) 是 KV heads 数，\(D_{head}\) 是 head 维度，\(B\) 是并发 batch。 MQA / GQA 的价值，就在于让 \(H_{kv}\) 小于 attention heads，从源头减少 KV cache。

这条公式能解释两类部署现象。第一，长上下文不只是 prefill 慢，decode 每个 token 也会变慢，因为每步读的历史 KV 变长。 第二，decode 侧提高 TP，比如从 tp=2 到 tp=4，常常不是为了更低 TPOT，而是为了降低单卡权重和 KV 压力，让更长上下文或更大 batch 放得下。

第二条结论： decode TP 变大通常是容量手段，不是延迟手段。它可能让显存更安全，但会引入更多 collective，同步延迟可能让 TPOT 变差。

四、TP/DP 的本质：一个换显存，一个换副本

Tensor Parallelism 把单层权重切到多张 GPU 上。它的好处是单卡显存压力下降、单层计算被拆分；代价是每层需要在 TP group 内通信。 Data Parallelism 则复制完整 replica；它不降低单 replica 内的显存压力，但能提供更多并发服务副本。

并行方式 主要收益 主要代价 推理部署直觉
TP 降低单卡权重 / KV 压力，提高单 replica 容量 每层 collective，TP 越大通信越复杂 prefill 更能摊薄；decode 更敏感
DP 增加 replica 数，降低排队，提高并发 权重复制，占用更多总显存 decode 通常喜欢更多 DP
PP 跨层切分，适合超大模型跨节点 bubble、流水调度和首 token latency 在线 decode 要谨慎
EP MoE expert 分布式放置 token routing 和 all-to-all MoE 模型必须单独分析

通信时间可以粗略写成：

\[ T_{comm} \approx \text{latency} \times N_{collectives} + \frac{\text{Bytes}}{\text{Bandwidth}} \]

decode 阶段每生成一个 token 都要跑所有层，且每层可能都有 collective。因为单步计算量小，通信 latency 很难被隐藏。 这就是为什么 decode tp=2 往往比 decode tp=4 更利于低 TPOT，前提是显存放得下。

五、PD 分离：把 TTFT 和 TPOT 拆开优化

PD 分离的核心不是多起几个进程，而是承认 prefill 与 decode 的资源曲线不同。prefill 影响首 token 前的计算和排队；decode 影响后续每个 token 的速度。 因此两个关键指标可以拆成：

\[ \text{TTFT} \approx T_{queue}^{P} + T_{prefill} + T_{kv\ transfer} + T_{first\ decode} \] \[ \text{E2E} \approx \text{TTFT} + N_{out} \times \text{TPOT} \]

如果请求是长 prompt、短 output，TTFT 往往主导体验；如果是短 prompt、长 output，TPOT 往往主导体验。 这就是 P/D 配比必须跟 workload 绑定的原因。

流量形态 压力位置 更该优化 配置倾向
短 prompt、长 output decode 长时间占用 TPOT、decode 并发 decode 小 TP、多 DP
长 prompt、短 output prefill 大请求排队 TTFT、prefill 吞吐 更多 prefill 副本，长短请求隔离
长 prompt、长 output 两侧都重，KV cache 大 TTFT、TPOT、显存容量 PD 分流 + decode 容量校验
共享 prefix 多 重复 prefill 浪费 prefix cache 命中 KV-aware routing、RadixAttention 类机制

例如同样 64 卡，4p(tp=8,dp=1), 1d(dp=16,tp=2) 与 4p(tp=8,dp=1), 2d(dp=8,tp=2) 的 decode 总卡数一样，但后者把 decode pool 分成两个故障域和调度域。理论峰值未必更高，尾延迟和长短请求隔离却可能更稳。

六、用同一套框架分析 64 卡配置

现在回到一个具体例子。四个方案都大致把 32 卡给 prefill，32 卡给 decode：

方案 会变好 会变差 更适合
4p(tp=8,dp=1), 1d(dp=16,tp=2) decode replica 多，TPOT 和并发通常好 单个 decode pool 较大，长短混合可能有队头阻塞 短 prompt、长输出、高并发
4p(tp=8,dp=1), 1d(dp=8,tp=4) 单 replica 显存更宽松，KV/batch 容量更大 TP 通信更重，decode 副本减半，TPOT 常变差 超长上下文或显存压力大
4p(tp=8,dp=1), 2d(dp=8,tp=2) decode 隔离更好，长短请求可分流，尾延迟更稳 需要更好的路由，否则两个 d 可能负载不均 综合默认，长短混部
2p(tp=8,dp=2), 2d(dp=8,tp=2) prefill engine 少，内部 batching 可能更集中 prefill 路由粒度变粗，TTFT 尾延迟可能不如 4p 稳 prefill DP 调度成熟的框架

这张表不是固定答案，而是按前面的分析链路推出来的。你需要先确认：decode tp=2 是否放得下模型和目标上下文？ TP group 是否跨节点？KV transfer 是否走高带宽链路？router 是否能让两个 decode pool 负载均衡？如果这些条件改变，排序也会改变。

一个实用默认： 如果没有特殊显存约束，先试 4p(tp=8,dp=1), 2d(dp=8,tp=2)。它不是所有 workload 的理论最优， 但通常在 TTFT、TPOT、隔离性和工程风险之间最均衡。

七、训练独立分析能力：六步检查表

以后看到任何 LLM 推理配置，都可以按下面六步拆。不要先问「别人怎么配」，先问系统结构允许你推导出什么。

步骤 问题 判断方向
1. 算资源 p_num * tp * dp 和 d_num * tp * dp 各是多少？ 先确认 P/D 总卡数，而不是被名字迷惑
2. 看 workload 输入长、输出长、并发高、SLO 卡 TTFT 还是 TPOT？ 长输入偏 P，长输出偏 D
3. 看形状 主要是在跑 [B*S,H] 大 GEMM，还是 [B,H] 小步循环？ 判断 compute-bound 还是 memory / latency-bound
4. 看 KV 上下文长度、GQA/MQA、block size、prefix cache 命中如何？ 判断 decode 显存和带宽压力
5. 看通信 TP 是否跨机？collective 次数和带宽如何？KV transfer 是否拥塞？ decode 对通信 latency 更敏感
6. 映射指标 变化影响 TTFT、TPOT、goodput 还是 tail latency？ 避免只看平均吞吐

最后一定要用实验校验直觉。建议至少压四组 workload：短输入短输出、短输入长输出、长输入短输出、长输入长输出。 每组都看 TTFT、TPOT、E2E latency、GPU 利用率、HBM 带宽、KV cache 使用率、队列时间和 P/D transfer 时间。 只测一个平均 QPS，很容易把真正的瓶颈藏掉。

结语：从配置记忆，到结构推理

LLM 推理配置没有脱离 workload 的最优解。tp=8、dp=16、4p2d 这些数字只是结果， 不是原因。真正可迁移的能力，是把请求拆成 prefill 和 decode，把每个阶段拆成计算、访存、通信和调度，再把它们映射到 TTFT、TPOT、吞吐和尾延迟。

记住这条主线就够了：prefill 是大矩阵，通常更能吃算力；decode 是逐 token 小步循环，通常更怕 KV、通信和调度。 PD 分离的价值，就是允许你不再用同一套并行策略同时迁就两个阶段。
