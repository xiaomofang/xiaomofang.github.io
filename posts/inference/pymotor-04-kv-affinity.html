一、把缓存位置放进 Prefill 选路

1.1 从重复文档请求开始

设想一个文档问答服务，每次输入由固定系统提示词、一份长文档和末尾的用户问题组成。第一次请求在 P1 上完成 Prefill，后续请求更换问题，但保留相同文档。此时 P1 可能已经持有数千 token 的 KV，P2 却拥有更低的排队负载。选择 P1 可以省去重复计算，选择 P2 则可能更早开始执行。缓存亲和调度必须把这两种收益放进同一次决策。

PyMotor 用两类状态支持这个决策。共享内存账本描述端点已经承接的调度负载，KV Conductor 描述各实例、各 DP 拥有哪些可复用前缀。Worker 先结合两者提出候选，再通过 CAS 提交真实分配。引擎接到请求后，才执行缓存加载和模型计算。理解这一先后顺序，才能把“调度器预计命中”与“引擎最终复用”分别测量。

1.2 缓存状态来自过去，请求查询发生在现在

阅读入口

先读 KvCacheAffinityPolicy.select_endpoint_candidates_from_list()，只追 token、Conductor 响应和候选列表三个变量。角色限制由 Worker 调用方继续检查，当前亲和主要作用于 P/U 路径。亲和策略源码

二、连续前缀怎样变成可查询的索引

2.1 同一块内容需要放回上下文路径

因果自回归模型在一个位置上的隐藏状态依赖此前上下文。KV 复用因此需要从相同前缀出发，沿连续路径确认覆盖。用 A、B、C、D 表示 token block，新请求为 A→B→C→D。持有 A→B→C→E 的端点可匹配前三块，持有 A→Q→C→D 的端点只能匹配第一块。后者出现 C、D，并不足以继续前缀。

ConcurrentRadixTree.find_matches_detailed() 从根的第一条边开始遍历，并维护仍然持有这条路径的 worker 集合。走到下一块时，有些 worker 仍在子节点持有集合中，有些已经退出。退出的 worker 在当前深度结算，仍能继续的 worker 再向下走。这使一次查询能够得到多个端点各自的最长前缀，而非仅得到整棵树的一个最大值。并发前缀树

2.2 LocalBlockHash 与 SequenceBlockHash 的分工

hashing.rs 将 token 块的内容转换为 XXH3 哈希，用作本地查询路径中的 LocalBlockHash。事件中的 SequenceBlockHash 则承担引擎块身份与父子上下文关联，参与反向删除、下层缓存续接等操作。同一份内容 hash 可以帮助找到树边，沿哪条父链、哪个实例与 DP 使用这条边，仍由上下文与持有关系约束。

顺着数据结构读代码时，先找查询如何按模型和租户定位 IndexerEntry，再找 token 如何转成块 hash，最后进入树遍历。Python 当前客户端使用 default 租户。块粒度、模型身份和 tokenize 结果必须与缓存事件保持一致。混合 KV 模型里，事件的 block_size 还可能与引擎某个同名配置具有不同的具体粒度。Conductor 查询与注册客户端

手工追踪

画三条 worker 路径，分别在第 1、3、4 块中断。读 find_matches_detailed() 时标出每次更新的 active workers 和 results，验证结果是否分别为 1、3、4。这个练习直接对应树节点持有集合的语义。

三、HBM、CPU、Disk 怎样组成分层覆盖

3.1 两条事件流共同确认下层数据

设备 HBM 上的 KV 由引擎事件维护，包含存入、删除和清空等变化。下沉到 CPU 或磁盘时，引擎事件通常提供 token 内容与块身份关联，存储池事件则提供保存完成和介质位置。Conductor 需要把两侧信息匹配，才能建立可以用于查询的下层索引。

事件允许乱序到达。引擎信息先到时保存内容映射，Pool 确认先到时保存 pending 事件，另一半出现后再完成索引。长期无法配对的信息通过维护任务与 TTL 回收。代码中的 offload、pending、content 缓存各自服务于这条配对过程，读者可以逐一追它们的插入、查询和删除位置。Pool 事件与配对逻辑

3.2 续接必须保持实例与 DP 归属

find_matches_with_coverage() 先查询 HBM，获取匹配深度和最后一个 sequence hash，再以合法断点查询 CPU/Disk。下层也可以拥有从根开始的完整前缀。断点续接需要保持同一实例、同一 DP 与父块身份的连续性，否则可能把其他端点的上半段拼到本端点下半段，产生虚假的完整命中。

查询内部记录各介质的绝对覆盖终点，最终响应再按优先级切成互斥贡献。若 NPU 覆盖到第 48 块、CPU 到第 56 块、Disk 到第 64 块，则返回的贡献分别为 48、8、8 块。这样同一前缀在多个介质上有副本时，不会重复记入收益。分层查询与 build_response

\[ B_n=E_n,\qquad B_c=\max(0,E_c-E_n),\qquad B_d=\max(0,E_d-\max(E_n,E_c)). \]
变量口径

E 表示连续覆盖的绝对终点，B 表示去重后的介质贡献。Conductor 的 matched_tokens 使用未加权贡献总和，权重留给 Coordinator 应用。先核对这层口径，再解读调度日志。

四、从分层命中推导调度评分

4.1 五个数值贯穿一次选择

输入长度记为 I，每块 token 数记为 b。Conductor 返回原始覆盖 R，Coordinator 按介质权重折算加权命中 M，进而计算剩余 Prefill 成本 C、综合评分 S 和实际负载提交增量 W。这些数值有不同的用途，应当分别记录。

\[ M=\min\!\left(I,\operatorname{round}\left[b(w_nB_n+w_cB_c+w_dB_d)\right]\right), \quad C=\max(0,I-\gamma M),\quad S=aC+\lambda L. \]

其中 γ 对应 overlap_credit，a 对应 prefill_load_scale，λ 对应 load_weight，L 为端点当前调度负载。默认三项评分系数均为 1，介质权重为 NPU=1、CPU=1、Disk=0。权重体现收益折算，配置值与真实加载速度之间需要通过实验校准。KvAffinityConfig

4.2 算一个能够改变直觉的例子

设输入 8192 token、每块 128 token。A 的互斥贡献为 48/8/8 块，当前负载 6000。B 为 16/8/0 块，负载 1000。C 暂无缓存且负载为 0。按默认权重计算，得到下表。所有数据都是教学假设。

端点 原始覆盖 R 加权命中 M 剩余成本 C 当前负载 L 评分 S
A 8192 7168 1024 6000 7024
B 3072 3072 5120 1000 6120
C 0 0 8192 0 8192

B 获得最低评分。A 的缓存更多，已有负载却抵消了部分收益。C 的排队压力最低，需要计算的输入最多。如果 A 的负载下降到 3000，它的评分变成 4024，选择随之转向 A。如果 CPU 权重降为 0.5，则 A 的 M 变为 6656，说明分层加载成本也可以改变排序。

4.3 unified 与 load_gated 的取舍

unified 对所有有效候选计算综合评分，同分初选随机打散。load_gated 则先保留负载最低的 N 个端点，再在集合中优先选择最长加权命中，随后比较负载。load_gate_topn 未设置时采用默认值 2。前一种提供连续折中，后一种在候选形成阶段设置负载边界。_select_with_load 与 _select_load_gated

练习

保持 A、B 的缓存数据不变，逐步增加 A 的负载，手算两者评分交叉的位置。再将 load_weight 设为 0，解释这时所有请求为什么更倾向最长缓存前缀，以及高并发时可能出现什么分布。

五、从候选走到真实提交，再处理回退

5.1 排序成本与账本增量分别计算

亲和策略在 req_info.kv_affinity_debug 中保存各候选的命中、负载、剩余成本和分层覆盖，Worker 据此构造分配候选。select_and_allocate() 对目标执行身份、角色、能力、阻断等检查，再向共享内存做 CAS。期间其他 Worker 可能修改同一端点负载，因此初选候选与最终提交端点可能不同。

当前 P/U 亲和路径的实际提交增量为 max(0, I−M)。例如 A 的 M=7168，即使将 overlap_credit 改为 0.5，使排序剩余成本增加到 4608，实际提交增量仍为 1024。请求账本必须记录最终端点及实际提交量，结束时再按记录释放。_committed_workload_for 与 select_and_allocate

初选使用端点负载，CAS 冲突后的全局亲和仲裁会结合更新视图和实例平均压力重新评分。最终 scheduled 日志中的 score 也需按具体路径解释。分析时先看 policy、fast_path、repicked 和最终端点，再对照各阶段公式。竞争后的候选仲裁

5.2 回退原因决定可观测性

情况 当前行为 阅读注意点
最佳加权命中率不超过已开启阈值 返回空列表，调用方转负载均衡 阈值要求严格大于，等于也回退
缺 tenant 或没有任何当前实例数据 返回 None，记录亲和不可用并转负载均衡 与低收益主动拒绝区分
部分实例缺索引 以零命中参与比较 保留冷实例凭低负载接请求的机会
prompt 短于一个配置块 跳过 Conductor 查询，按零命中进入评分 后续阈值规则仍然适用
Conductor 连续查询失败 客户端进入冷却，查询返回空结果 当前 3 次失败触发 30 秒冷却
负载均衡也无候选 尝试轮转，最终可分配资源仍可能为空 回退仍受可用拓扑约束

命中率门槛使用 max(M)/I。上例最佳值为 87.5%，阈值设为 87.5% 或 90% 均会回退，设为 0 则关闭门槛。查询客户端当前配置单次 timeout=3 秒，冷却前的失败尝试仍可能增加延迟。测试回退时，应记录这些等待，而非只检查最后是否返回成功。

冷启动的反馈环

若零缓存实例被直接移除候选，它会失去积累缓存的请求。源码把部分缺失索引当成零命中参与评分，使低负载新实例仍有机会建立缓存。这是调度策略与缓存分布互相影响的一个例子。

七、怎样证明缓存亲和改善了服务

7.1 先给调度留下选择空间

选路对照实验需要至少两个合格 P 端点。只有一个 P、且 P 侧 DP1 时，可以测引擎缓存复用，却缺少比较目标端点选择的空间。实验应固定模型、硬件、TP/DP、输入输出长度、采样参数、D 侧容量和请求序列，同时给各策略相同的冷缓存或预热条件。

建议比较普通负载均衡、load_weight=0 的纯亲和、默认 unified，再按需增加 load_gated。冷缓存负载揭示查询开销，固定长文档加变化短后缀揭示 Prefill 节省，热门前缀加高并发揭示热点折中。受控下沉和查询失败注入分别检查介质权重与故障回退。所有故障实验应在专用测试环境完成。

7.2 将同一 req_id 的证据连起来

依次记录 tokenize 长度、Conductor 原始覆盖、加权命中、初选候选、最终 scheduled 端点、引擎实际前缀复用及客户端首 token。最终日志中的 matched 和 hit_rate 使用加权口径，hbm/cpu/disk 表示介质 token 数，committed 则用于账本。索引更新和引擎缓存生命周期之间存在时间差，因此链路验证要一直走到实际引擎与客户端。

性能结果同时报告 TTFT 的 P50/P95/P99、TPOT、成功请求吞吐、token 吞吐、错误率、调度/查询耗时与各 P/DP 分布。固定请求序列并重复运行、交换策略执行顺序，可以降低一次预热和流量波动带来的偏差。分位数应基于合并样本或直方图估计，避免平均各端点的 P99。

观察到“Conductor 覆盖很高、TTFT 却没有下降”时，可以顺着时间线继续缩小范围。若请求先花很长时间完成 tokenize 或查询，减少的 Prefill 计算可能被入口开销消耗。若请求确实到达命中端点，而该端点已经排了很多工作，问题落到负载折中的权重和账本代理信号。若索引显示覆盖、引擎实际复用却偏低，则进一步核对事件时效、逐出、模板、块粒度和存储加载。每一步都用同一个请求身份关联证据。

查询开销本身也值得拆开。长上下文意味着更多 token 要编码并经 HTTP 发送，Conductor 再进行哈希、树遍历、下层续接和响应编码。当前客户端默认使用 MessagePack，源码还在查询端记录哈希与匹配相关时长。测量时可以把请求长度分桶，比较查询耗时是否随输入增长，以及收益主要出现在何种前缀复用比例。这样才能判断调度参数适合整个业务，还是只适合某类长文档请求。

权重扫描应先固定其他变量。保持同一缓存快照和候选负载，单独改变 CPU 权重，观察预测的端点切换。随后在可控下沉条件下测实际加载与首 token 时间，再选择能反映业务代价的参数。再扫描 load_weight，观察热点端点的流量是否减少、冷实例是否获得请求、尾延迟是否改善。将两个维度同时任意变化，会让结果难以归因。

还可以加入一次删除验证。让一段已知前缀先进入索引，再触发对应块删除或 worker 注销，确认后续查询的覆盖下降。随后让该端点重新承接请求，检查缓存能够再次积累。这个过程检验的是索引生命周期与选路反馈，不依赖吞吐提升的假设，也适合在深入压测之前作为功能验收。

7.3 从测试回到实现

Python 优先阅读 test_kv_cache_affinity.py 中的 CPU 权重、部分 tenant、短 prompt、阈值边界和 load-gated 测试。Rust 优先阅读 indexer/tests.rs 中的 HBM→CPU 续接、同实例同 DP 约束、Disk 扩展、分层互斥贡献和删除维护测试。先抄出测试输入与断言，再定位实现中保证该行为的分支。亲和策略测试、分层索引测试

一次测试的输入也能转化为面试中的可解释例子。例如，将两个候选的命中设为相同、负载设为不同，检查算法能否偏向低负载端点。将两者负载设为相同、命中设为不同，检查排序是否偏向更长前缀。再构造某个实例完全缺少索引的响应，确认它仍在候选范围。最后把候选的共享内存 generation 改变，解释为什么最早的评分不能授权它继续完成分配。
