Mooncake 学习（0）：架构总览、组件拆解与一次 KVCache 流转

先不钻进某个函数。这一篇要建立一张能指导后续读码的地图：Mooncake 不是一个“RDMA 工具”，而是以 KVCache 为中心，把推理计算、缓存存储、异构传输和全局编排接起来的分布式基础设施。

一、先定边界：Mooncake 到底解决什么

1.1 LLM 推理为什么需要另一种基础设施

Prefill 一次处理整段 prompt，主要受矩阵计算吞吐影响；Decode 每生成一个 token 都要读取历史 KV，逐步变成访存受限。把两者放在同一组实例，长 prompt 的计算突发会影响 Decode 的 token 间延迟。另一方面，system prompt、多轮对话和相同前缀会反复产生相同的 KV，若只放在单卡显存里，跨请求和跨节点都无法复用。

Mooncake 的核心判断是：两个阶段真正需要交换的中间产物不是完整请求，而是 KVCache。因此可以把 Prefill 和 Decode 拆成 PD disaggregation / XpYd，再把 GPU 之外的 DRAM、NVMe 等资源组织成共享 KV 池。

边界先记住：Mooncake 不负责模型权重、Attention kernel 或 token 生成。推理引擎负责算，Mooncake 负责让已经算出的 KV 在正确的节点、正确的地址和正确的生命周期内可用。

1.2 “KVCache-centric”不是一句口号

传统服务通常以请求为调度单位；KVCache-centric 系统还要围绕“哪些前缀已经存在、在哪里、能否读、何时淘汰”做决策。于是请求路由、Prefill 计算、Decode 接棒、缓存复用和资源回收都围绕 KV 对象展开。

问题Mooncake 的回答对应组件
数据放哪GPU/DRAM Segment，必要时下沉到本地盘、共享盘或 3FSStore、Storage Backend
怎么搬按地址和长度提交批量 READ/WRITE，尽量零拷贝并行传输Transfer Engine
谁能读Master 返回 COMPLETE 副本，并用 lease 保护读期间的对象Master、Client
没空间怎么办近似 LRU 驱逐、软/硬 pin、offload 和副本迁移Eviction、Task Manager
控制面挂了怎么办快照加 OpLog，etcd/Redis/Kubernetes Lease 协调主备HA

二、四层架构：从硬件到推理框架

读源码时可以沿依赖反向走：先看应用如何提出 put/get 或 KV connector 请求，再看 Store 如何返回副本描述，最后落到 Transfer Engine 的 submitTransfer 与具体 Transport。这样不会把“调度时机”“对象协议”和“网卡执行”混成一层。

三、物理部署：两张网络与四类角色

一个典型 XpYd 集群包含 Prefill 节点、Decode 节点、可选的独立 KV 池节点，以及 Master/元数据服务。推理节点也可以同时贡献 DRAM Segment，所以“存储节点”和“计算节点”不是必须的两种机器。

通道承载内容关键性质
RDMA 数据面KV 的 READ/WRITE节点间直达，目标地址是已注册的 DRAM/VRAM
TCP 握手/通知GID、QP 参数、完成通知小流量控制面，不搬大块数据
Master RPCPutStart、PutEnd、GetReplicaList 等分配地址和维护状态，不经过数据
etcd/Redis/HTTP 元数据Segment 描述、RPC 地址、HA 状态可替换；P2P 模式可减少中心依赖

节点内拓扑同样重要：GPU 到 NIC 的 PCIe 距离、NIC 所属 NUMA、GPU 间 NVLink 都会影响真实带宽。Transfer Engine 会生成位置到 HCA 的优先矩阵，优先选择本 NUMA 或本 PCIe 路径；故障时才退到备选路径。

部署提醒：RDMA 内存注册通常要求足够的 memlock；多 NIC 环境可用 MC_MS_FILTERS 限定设备，大段内存可考虑 hugepage。没有 RDMA 时，Transfer Engine 可以使用 TCP，但性能语义不是同一回事。

四、Transfer Engine：统一的“搬运动词”

4.1 Segment 和 BatchTransfer

Segment 是可被引用的地址空间。RAM Segment 逻辑上覆盖一个进程的地址空间，实际只有注册过的 Buffer 可被远端访问；也可以存在 NVMe-oF Segment。每个进程通常有一个本地 Segment，其他进程通过名称 openSegment 引用它。

BatchTransfer 是一组非连续 READ/WRITE 请求，描述本地地址、远端 Segment、远端偏移和长度。调用方注册本地内存、打开目标 Segment、分配 Batch、提交请求，再通过 getTransferStatus 观察异步完成状态。Store 的 TransferSubmitter 只是把这个底层接口包装成更适合对象读写的 Future。

4.2 初始化与传输路径

  1. 1
    发现资源

    初始化 RPC 端口、接入 etcd/Redis/HTTP 元数据服务，探测 HCA、GPU、NUMA 和 PCI 拓扑。

  2. 2
    发布 SegmentDesc

    公布设备、优先矩阵、Buffer 地址和每张 NIC 对应的 rkey；对端据此知道“在哪里读/写”。

  3. 3
    选择 Transport

    根据对端协议和本地硬件选择 RDMA、TCP、NVLink、HIP、NVMe-oF、EFA、昇腾等后端。

  4. 4
    切片并异步提交

    大请求拆成片，按本地/远端拓扑挑路径，放入 worker 和 QP 窗口；CQ 完成后聚合为 Batch 状态。

RDMA 版本的关键对象可以记成 Context → EndPoint → QP。Context 对应 HCA，EndPoint 对应本地 NIC 到远端 NIC 的连接，QP 承担实际 work request。连接通常惰性建立，失败后会从端点池移除并重建。大传输切片、多个 QP、CQ 轮询和重试共同把带宽变成流水线，而不是一次阻塞调用。

Transfer Engine 的价值不是“只支持 RDMA”。它把 RDMA、TCP、GPU 互联、NVMe 等差异收敛在 Transport 接口后面，上层只表达“从哪个地址向哪个 Segment 搬多少字节”。

五、Mooncake Store：控制面与数据面分离

5.1 Master 是地址簿，不是 Redis 数据转发器

Master 维护 key 到副本的映射、Segment 空间、状态、租约和淘汰信息；Client 挂载连续内存并真正持有数据。客户端从 Master 拿到副本描述符后，数据直接在 Client 之间通过 Transfer Engine 传输，Master 不在大流量路径上。因此容量和带宽可以随 Segment/NIC 横向增加，Master 的负担主要随元数据和请求数增长。

5.2 Put 为什么要三段式

PutStart 根据切片长度和 ReplicateConfig 预分配副本，并登记正在处理的 key；Client 将数据写到远端内存或 SSD；所有副本成功后调用 PutEnd，副本才变成 COMPLETE，随后 Get 才能看到。失败则调用 PutRevoke 回滚。这个协议的重点是：读者永远不会读到半个对象。

# 语义上的 Store 写入，不是完整实现
replicas = master.put_start(key, slice_lengths, config)
for replica in replicas:
    transfer_or_write_file(replica)
if all_writes_succeeded:
    master.put_end(key)
else:
    master.put_revoke(key)

5.3 Get、复制与分配

GetReplicaList 只返回可读副本，并可授予读租约。Client 通常优先本机内存，再选远端内存，之后才回退本地盘或共享盘。对象可按切片条带化到不同 Segment；副本数是尽力而为，资源不足时可能得到少于请求数量的副本，但每个切片的放置仍需满足系统约束。Upsert 支持不存在则插入、存在则更新，Copy/Move 由异步任务系统支撑再均衡和 Drain。

状态/机制作用
INITIALIZED → PROCESSING → COMPLETE把“空间已分配”和“数据已可读”分开
Lease读期间保护副本，租约过期前不应被淘汰
Soft pin一段时间内优先保护热点前缀，长期不访问可失效
Hard pin永久跳过自动淘汰，只能显式删除
Eviction高水位或分配失败时回收过期对象，通常近似 LRU

六、分层存储与高可用：缓存系统如何活下去

6.1 三层缓存

与 SGLang HiCache 结合时，可以把 GPU 看作 L1、本机 Host Memory 看作 L2、Mooncake Store 看作共享 L3。Mooncake 自身也支持从内存副本向 LOCAL_DISK、共享盘或 3FS 下沉。热数据可以被本地热缓存短路，冷数据让出昂贵的 DRAM；读取时再提升到更快层级。

HiCache 的 HiRadixTree 记录 token 前缀在 L1/L2 的位置，L3 的存在和位置则按需询问后端。预取要求命中部分构成连续前缀，并可用 best_effort、wait_complete 或 timeout 在延迟和命中率之间取舍；回写则有 write-through、选择性 write-through 和 write-back 三种风格。

6.2 Master HA 与数据面容错

高可用模式把 Master 做成由 Lease 协调的主备/多实例：快照提供元数据基线，OpLog 传播增量，standby 追平后才允许提升。主节点失效时客户端跟随新的 leader。由于 KV 数据本身在 Client 副本中，Master 切换主要影响新的元数据查询，不需要把所有 KV 经过 Master 搬一遍。

这里要区分两种故障：链路故障由 Transport 的重试、端点重建和备用 NIC 处理；Client 故障由副本和重新复制处理；Master 故障由选主、快照和 OpLog 处理。三者分别属于数据传输、数据副本、控制元数据三个故障域。

七、生态集成：同一底座的不同用法

集成主要用途Mooncake 扮演的角色
vLLM PD 分离Prefill 产出 KV，Decode 拉取并生成Transfer Engine 作为 KV 连接器的数据面
vLLM Store Connector跨请求、跨实例的前缀复用Mooncake Store 提供池化 KV
SGLang HiCacheGPU/Host/L3 分层缓存L3 后端和 RDMA 读写能力
P2P Store训练 checkpoint 向大量节点分发节点边拉边成为新数据源
mooncake-ep / mooncake-pgMoE dispatch/combine、容错集合通信复用 Transfer Engine/RDMA 设施
mooncake-rl / reshardRL rollout↔训练、权重重分片规划跨阶段数据总线和传输计划执行底座

因此，“Mooncake 集成”不是唯一模式：点对点 TE 路径追求 PD 交接的低延迟，Store 路径追求全局前缀复用和分层容量；两者可以在同一集群中叠加。

八、把它串成一次请求

  1. 1
    路由

    入口根据负载与前缀亲和性选择 Prefill/Decode，过载时可提前拒绝无法满足 SLO 的请求。

  2. 2
    命中或计算

    先查本地/共享 KV；未命中的前缀由 Prefill 计算，已命中的部分直接复用。

  3. 3
    交接

    Prefill 把远端地址、Segment、block/page 信息交给 Decode；此时要延迟释放仍可能被读取的源 KV。

  4. 4
    搬运与生成

    Decode 分配目标 block，Transfer Engine 批量 READ/WRITE，数据就位后进入逐 token Decode。

  5. 5
    沉淀

    新 KV 按策略写入 Host/L3，热点保留，冷数据 offload；未来相同前缀跳过重复 Prefill。

一条主线：上层决定“要哪个 KV”，Store 决定“它在哪里且能否安全读”，Transfer Engine 决定“怎样最快搬过去”，硬件决定“这条路径的真实成本”。

九、后续源码学习路线

后续逐模块读码时建议按下面顺序，而不是从某个 vLLM connector 的长文件随机跳入：

  1. Transfer Engine API：先看 TransferEngine、Segment、BatchTransfer 和状态轮询。
  2. RDMA Transport：再看内存注册、QP、端点池、切片、CQ 和拓扑选路。
  3. Store Master：重点追 PutStart/PutEnd/PutRevoke、GetReplicaList、分配器、租约和淘汰。
  4. Store Client：追 RealClient、DummyClient、共享内存、读写路径和 SSD backend。
  5. HA 与 HiCache：最后看快照/OpLog、选主、预取/回写和多 Rank 同步。
  6. 上层集成：再回到 vLLM、SGLang，观察应用如何把 block/page 生命周期映射到上述抽象。
Mooncake 的本质不是“把 RDMA 接进推理框架”，而是把 KVCache 变成可寻址、可传输、可复制、可分层、可治理的分布式对象。理解这条主线，后面每个模块都只是同一问题在不同层次上的具体答案。
