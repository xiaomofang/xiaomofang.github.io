MooncakePD 分离推理框架硬件与 Kernel

Mooncake 是月之暗面（Moonshot AI）Kimi 大模型服务使用的推理基础设施，围绕 KVCache 设计了分离式的服务架构：Prefill 和 Decode 可以部署在不同的计算实例上，节点上的 CPU、DRAM、SSD 等资源也可以参与 KVCache 的存储和传输。它本身不负责模型计算，而是提供缓存管理、数据传输以及与推理框架之间的连接能力。

本文参考Mooncake 官方中文文档和Mooncake 源码深度学习手册。前者主要介绍项目的公开设计、API、部署方式和集成示例；后者按照物理架构、Transfer Engine、RDMA、Store、HA、生态和数据流整理源码阅读路径。本文先把这些内容合并成一张总览图，后面再逐一展开代码。

一、从什么问题开始理解 Mooncake

1.1 Prefill 和 Decode 的矛盾

Prefill 一次把 prompt 送进模型，通常是计算密集型；Decode 每次只生成一个 token，却要反复读取从第一个 token 到当前位置的历史 K/V，逐渐表现为访存密集型。两者混在同一批 GPU 上，长 prompt 的计算突发会挤压 Decode 的 token 间延迟；而相同 system prompt、多轮对话前缀又会让相同 KV 被重复计算。

因此 Mooncake 的第一步不是“换一种 RDMA API”，而是重新定义系统的中间产物：Prefill 和 Decode 之间最值得搬运的不是请求文本，而是已经计算好的 KVCache。将 Prefill 集群和 Decode 集群分开，就是 PD disaggregation / XpYd；把闲置的 CPU DRAM、GPU 显存和 SSD 组织为共享容量，就是 KVCache-centric。

本文的范围：Mooncake 不保存模型权重，也不执行 Attention 或 token 生成。上层推理引擎负责计算，Mooncake 负责 KVCache 的存储、查找、传输和生命周期管理。

1.2 为什么 KVCache 适合成为系统对象

KVCache 有三个很适合分布式对象存储的属性：它可以用请求前缀对应的 block/page 命名；写入后通常不可变，天然适合多副本和读多写少；它的价值由复用次数决定，适合租约、pin、热度和淘汰策略。于是系统要解决的就不只是“缓存命中没有”，而是一个完整对象生命周期：

二、四层架构：每层解决一个不同问题

后续读代码时，可以用这四层来定位问题。GetReplicaList 属于 L3 的对象语义，submitTransfer 属于 L2 的数据搬运，vLLM connector 则负责把上层请求生命周期映射到这些接口。这样看，文件之间的职责会比较清楚。

三、物理世界：控制面和数据面为什么分开

典型部署包括 Prefill 节点、Decode 节点、可选的独立 KV 池节点、Master 和元数据服务。一个 Client 既可以是请求发起者，也可以贡献一段 DRAM 作为“被别人读写的存储服务器”。这正是 Mooncake 与传统中心化缓存的关键不同：数据不必穿过一个存储服务器。

数据面与控制面分离后，Master 的故障不会直接切断已经建立的传输，Master 也不会因为吞吐随节点线性增长而成为带宽瓶颈。相应地，系统需要维护地址、生命周期和租约协议：地址失效、源 buffer 过早释放、目标副本未完成，都会带来数据一致性问题。

四、Transfer Engine：从地址到字节的执行层

4.1 Segment 是“可被引用的地址空间”

官方文档把 Segment 定义为传输可用的源/目标地址范围集合。RAM Segment 可以覆盖 DRAM 或 VRAM，NVMe-oF Segment 则描述可直接访问的持久化空间；实际可远端读写的只是已经注册的 Buffer。调用方通常先注册本地内存，再 openSegment 打开目标，之后用一组请求描述 READ/WRITE。

一个请求最重要的不是“某个 tensor 对象”，而是本地地址、远端 Segment、远端偏移、长度和操作方向。这使 TE 可以服务 KV，也可以服务 checkpoint、hidden state、专家通信或其他大块数据。

4.2 为什么需要 Transport 抽象

同一个“搬运”动作可能落在 RDMA、TCP、节点内 NVLink、HIP IPC、NVMe-oF、AWS EFA、昇腾或其他设备互联上。Transport 抽象把这些后端收敛到统一生命周期：安装、注册内存、提交传输、查询状态。MultiTransport 根据对端 Segment 描述和本地拓扑选择具体实现；这也是 Mooncake 可以在异构硬件上复用上层存储语义的原因。

4.3 RDMA 热路径拆解

  1. 1
    注册内存

    每张 HCA 都需要对应的 memory region 和 lkey/rkey。GPU 内存还可能走 GPUDirect 或 dmabuf 注册路径。

  2. 2
    发布与发现

    SegmentDesc 发布设备、Buffer、拓扑优先级和远端 key；对端先发现描述，再决定使用哪条路径。

  3. 3
    惰性建链

    首次传输通过 TCP 握手交换 GID、QP 等信息，EndPoint 推进到可用状态；失败后从连接池移除并重建。

  4. 4
    切片、窗口与完成

    大请求切片后进入 worker 队列，受 QP/CQ 信用窗口约束；CQ 完成逐片回收信用，最终聚合为 Batch 状态。

零拷贝不是一个单点优化。它至少包括应用 buffer 不经额外 staging、节点间不经 Master/中间服务器、GPU 数据不绕到 CPU DRAM。任一环节引入复制，端到端收益都会打折。

五、Mooncake Store：把搬运升级成对象协议

5.1 Master 与 Client 的职责反转

Master 看起来像“服务端”，但它不持有 KV 数据。它维护 key、对象大小、切片位置、Replica 状态和租约；Client 一方面接受上层 Put/Get，另一方面挂载连续内存、注册 TE，并作为其他 Client 的数据源。官方文档甚至允许配置纯客户端或纯存储节点。

5.2 PutStart / PutEnd / PutRevoke 为什么像轻量事务

如果没有这三段式协议，Get 可能看到只写完一半的对象；并发 Put 同一 key 也可能互相覆盖。processing_keys、副本状态机和失败回滚共同保证：对象要么以完整版本出现，要么不出现。官方文档强调 Get 返回正确且完整的数据；源码手册进一步把它定位为 Master 中的状态机与 RAII 回收问题。

5.3 Get 不是“随机找一份副本”

Get 先向 Master 请求 GetReplicaList，只接受 COMPLETE 副本，并通过 lease 保护正在读取的对象。Client 再根据位置选择本机内存、远端内存、LOCAL_DISK 或共享 DISK。读路径的优化顺序通常是：本地热缓存短路 → 本机 Segment → 远端 RDMA READ → 盘/3FS 回退。对象的副本不是为了让 Master 多一份记录，而是为了让数据面在节点故障或热点访问时拥有替代路径。

六、分层存储、HiCache 与 HA

6.1 从 GPU 到 SSD 的容量金字塔

与 SGLang HiCache 集成时，GPU 显存可视为 L1，Host Memory 是 L2，Mooncake Store 是共享 L3。HiRadixTree 在本地记录 token 前缀的树结构和 L1/L2 位置，L3 位置按需向后端查询。预取把连续命中的前缀从 L3 拉到 L2；回写则按 write-through、选择性 write-through 或 write-back 策略下沉。

Mooncake Store 自身还可把内存副本 offload 成 LOCAL_DISK、共享盘或 3FS。Bucket 后端把多个小对象追加到固定 bucket，减少 inode 和 open 开销；3FS USRBIO 则面向并行文件系统提供用户态批量 I/O。分层的关键不是“盘也能存”，而是把容量、带宽、延迟和复用热度放在同一个策略里权衡。

6.2 Master HA 为什么不等于 KV 数据复制

Master HA 保护的是地址簿，不是把 KV 再复制一遍。主节点用 Lease 参与选主，快照提供某个时刻的元数据基线，OpLog 追踪之后的 PutEnd、PutRevoke、Remove 等变更，standby 追平后才允许提升。Master 宕机时，数据仍留在 Client 的副本里；切换期间主要暂停新的元数据查询，已经建立的数据传输不必经过新 Master。

这里可以分别看三种故障：RDMA 链路抖动由重试、备用 NIC 和端点重建处理；Client 故障由其他 Replica 和复制任务处理；Master 故障由选主、快照和 OpLog 处理。它们涉及的是不同的故障边界。

所以介绍某个框架接入 Mooncake 时，还需要说明它使用的是 TE 直连路径，还是 Store 池化路径。前者主要用于单次交接，后者主要用于跨请求复用，HiCache 则把 Store 放进层级缓存体系。

八、一次请求的完整心智模型

读到这里，可以用四个问题检查自己是否真的理解了架构：第一，为什么 Decode 需要外部 KV；第二，为什么 Master 不能承载数据流；第三，为什么 PutEnd 之前 Get 不应可见；第四，为什么一个 Master 故障不必等于 KV 数据丢失。后面的源码阅读，几乎都是这四个问题在不同文件里的实现。

九、接下来怎样读源码

  1. 先读 Transfer Engine API：锁定 TransferEngine、Segment、BatchTransfer、注册内存和状态轮询。
  2. 再读 RDMA Transport：顺着 Context → EndPoint → QP，理解 MR、握手、切片、QP/CQ 窗口和故障重建。
  3. 再读 Store Master：重点追 MountSegment、PutStart/End/Revoke、GetReplicaList、分配策略、租约和淘汰。
  4. 再读 Store Client：比较 RealClient 与 DummyClient，看共享内存、TransferSubmitter、LocalHotCache 和 SSD 读写。
  5. 最后读集成：把 vLLM/SGLang 的 block/page 生命周期映射回 Store 对象和 TE buffer，才能理解 connector 中的延迟释放与异步预取。
从整体上看，Mooncake 把 KVCache 的产生、命名、放置、传输、复用、保护、下沉和回收连接起来。Transfer Engine 处理数据搬运，Store 处理对象位置和可见性，集成层把这些能力接入推理调度。后续逐模块阅读时，可以沿着这三条线继续展开。
