先把 Coordinator 的进程与状态分清

父进程、Mgmt、Obs 和 Worker

CoordinatorDaemon.run() 初始化进程管理器，并按 Mgmt、Obs、Inference 的顺序拉起子进程。Mgmt 先准备控制通道和共享内存，后续进程再连接。多个 Inference Worker 处理业务请求，Obs 汇总指标，父 Daemon 组织角色变化和子进程监督。

启动顺序与状态归属紧密相关。Mgmt 持有成员控制状态和共享内存 owner，Worker 持有本地请求上下文、成员缓存和 SchedulerClient。请求转发时可以在本 Worker 选择目标并提交负载，管理面通过控制消息、成员变更和共享段提供协作。Coordinator 进程生命周期

子模块 职责 与请求的关系
daemon/coordinator_daemon.py 启动、信号、主备角色与停止顺序 决定当前服务角色及进程集合
daemon/subprocess_supervisor.py 子进程存活监督 发现请求处理进程异常
daemon/role_shm_holder.py 共享角色与父进程心跳 为 readiness 与失效判断提供状态

一个请求由谁记住

models/request.py 定义 RequestInfo，记录请求身份、请求数据、token、时间状态、追踪和重试相关信息。domain/request_manager.py 管理当前 Worker 的在途请求及实际分配的负载记录。一个根请求可能经历多次内部尝试，PDDispatchSession 和 AttemptContext 为每次尝试保存 P/D 资源、阶段任务与释放状态。

给 R1 画两层身份。外层 req_id 表示用户的一次请求，内层 attempt_seq 表示某次执行尝试。将资源分配、错误与释放都标到对应 attempt 上，后续阅读重试和流式恢复会清楚很多。

HTTP 入口怎样建立统一请求上下文

从接口注册进入 dispatch

入口在 api_server/inference_server.py。路由注册将 Chat Completion 等 API 连接到处理函数，_handle_openai_request() 检查请求内容、必要字段、认证和服务可用条件，并注入调度客户端、配置与 RequestManager。app_builder.py 负责应用和中间件组装，base_server.py 承担通用服务逻辑。

同目录的 management server 接收成员刷新和运行时控制，observability server 提供观察接口。业务链先跟 inference server 即可，等要解释“这些成员从哪里来”时再回到管理服务。入口中间件中的限流也要结合实际状态作用域理解，字段名称本身无法证明跨 Pod 共享限流。推理请求入口

handle_request 与 RequestInfo

router/dispatch.py::handle_request() 调用请求信息构造逻辑，接入追踪父上下文，执行 tokenization 和上下文预算处理，再调用 select_router_class()。这里的 req_len 记录原始请求体字节长度，token_ids 才表示编码后的输入序列，两者后续会用于不同负载路径。

假设 R1 的 JSON 包含长系统提示和短用户问题。原始 JSON 长度还包含字段名、角色和结构符号，token 长度则由模板与 tokenizer 决定。即便两条请求的用户问题相同，只要 chat template、tools 或系统提示不同，输入序列也可能变化。先明确输入的实际表示，才能解释缓存查询和长度估算。请求上下文和 Router 选择

入口层建立用户请求合同，dispatch 建立内部执行上下文。后面的 Router 可以依赖明确的请求身份、输入表示和依赖对象来编排阶段。

Render 如何连接客户端协议与 token 请求

为什么 tokenize 要有统一入口

TokenizationService.tokenize() 优先按配置和 API 合同使用 Render，允许的失败分支再尝试本地 tokenizer。统一结果可以供缓存亲和查询、上下文预算和引擎 token-only 请求复用，减少各阶段独立套模板造成的偏差。服务还处理不同 API 的输出预算字段，以及多 prompt 等输入的标准表示。

Render 返回的 TokenizedRequest 携带 prompt token 与相应生成元数据。开启 token 混淆时，还需要区分语义 token 与引擎实际使用的物理 token。此时错误回退必须服从混淆合同，代码会在要求 Render 的路径上拒绝无法满足条件的执行。统一 tokenization 与回退

render/api_spec.py、models.py API 合同与标准 token 结果 哪些入口与字段受到支持
vllm_render_client.py Render/Derender HTTP 调用 可用性、错误和响应验证
response.py 非流式 token-only 结果还原 客户端响应形状如何恢复
streaming_response.py 逐个增量结果还原 请求与 choice 的状态如何保持

跟踪一次长度预算变化

假设模型有效上下文上限为 8,192，Render 得到 6,000 个输入 token，用户请求最多生成 3,000 个。开启相应上下文预算处理后，可用输出空间为 2,192，请求的有效输出预算会被收紧到这个范围。这里先按输入长度与配置上限做预算，接下来 Router 和 Adapter 还会根据 P/D 阶段改写具体请求。示例数字用于说明控制流，真实 token 数应以模板编码结果为准。

Render 是协议预处理与还原服务，Encode 角色负责多模态编码阶段。阅读 BaseRouter.do_encode() 时应继续追它的可用角色、请求转换和阶段数据，避免仅凭名称把两条路径合并。

HANDOFF 怎样把 P 和 D 串成一次请求

先有合法拓扑，再有一次 attempt

select_router_class() 按当前可用拓扑、引擎能力和熔断状态选择策略。有兼容 P/D 组合时可以进入 UnifiedPDRouter，其他符合降级条件的组合可能进入 PDHybridRouter。只有 D 可用时还需要相应 decode colocation 能力。缺少合法路线时，入口会得到服务不可用错误。

UnifiedPDRouter._generate_response() 为根请求创建 session，并在受限次数内建立 attempt。HANDOFF 的 _create_attempt() 先申请 P 资源，允许将 D 分配延后。资源申请经 BaseRouter.prepare_resource() 进入 Worker 的 SchedulerClient，选择成功后记录最终端点与负载归属。P/D attempt 与执行编排

适配器为什么要校验 P 响应

VllmProtocolAdapter.build_prefill_request() 复制原请求，注入引擎请求身份，设置非流式与短生成预算，并加入远程 Decode 所需的 KV 字段。P 完成后，parse_prefill_response() 检查返回的交接参数和远程 Prefill 标记，再建立 PrefillMetadata。D 请求通过 build_decode_request() 携带这张票据。

这一步把原生协议的字段约束集中在 Adapter。Router 负责何时申请、发送、等待和释放，Adapter 负责原生消息应满足什么结构。P 的 HTTP 状态成功仍不足以保证 D 能继续执行，交接字段必须满足协议合同。原生 P/D 协议适配

可以手工抄三份小字典来跟踪 R1。第一份保存用户的 messages、生成预算 128 和 stream=false。第二份表示 P 请求，保留必要输入，将阶段生成预算收紧到 1，并加入远程 Decode 标记。第三份表示 D 请求，使用交接票据并保留用户要求的生成预算。实际字段还受 API 类型影响，例如 Responses 使用 max_output_tokens。这个练习的重点是每一次修改属于哪个合同。

继续观察对象隔离。Adapter 会复制传入的数据，再注入原生请求身份和阶段字段。这样 P 阶段对预算的修改不会直接把用户原始请求改成只生成一个 token。若后续还有第二次 attempt 或需要构造 D 请求，原始请求和阶段副本之间的边界便尤为重要。读 deepcopy、数据类和 Mapping 参数时，应将它们放进这个多阶段重用场景理解。

延后选 D 改变了什么

_run_handoff_nonstream_attempt() 等待 P 完成后发起 P 负载后台释放，再调用 _ensure_handoff_decode_resource() 申请 D，最后发送 D 请求。长 prompt 的 Prefill 期间，D 的负载可能已经变化，延后选择可以使用较新的视图，同时避免把尚未进入 Decode 的请求提前记入 D 账本。

做一个时间线练习。设 P 执行持续 800 毫秒，D 生成持续 400 毫秒。若一开始便为 D 提交负载，该负载会覆盖约 1,200 毫秒的整个窗口。延后提交时，D 侧分配更贴近实际使用阶段。这个数字例子解释记账窗口，具体收益需要测量调度、排队、传输和引擎执行时间。

后台发起释放与释放确认是两个时刻。阅读时把“阶段计算结束”“提交释放任务”“共享账本已更新”分别标在时间线上，才能解释短暂负载和清理等待。

TRIGGER、BOOTSTRAP 和混部怎样改变控制流

相同 P/D 目标，不同阶段驱动方式

路线 典型入口 阶段关系 需要追踪的状态
HANDOFF vLLM 交接型 Connector P 返回票据后派发 D ticket、延后 D 分配、P/D 释放
TRIGGER vLLM layerwise 路线 先启动 D，D 回调 metaserver 触发 P 回调 Worker、attempt 身份、旧回调拒绝
BOOTSTRAP SGLang 原生 PD P/D 用 bootstrap 信息协同执行 bootstrap_host、port、room 与 peer endpoint
PDHybrid 可兼任阶段的合法实例 选一个目标完成请求 角色能力、降级条件与当前拓扑

TRIGGER 需要 Worker 的 metaserver 接收回调。请求上下文保存在具体 Worker，所以回调要抵达正确进程，并且携带当前尝试的身份。迟到的旧尝试回调必须被识别，避免给新 attempt 注入错误阶段信息。

SGLang Adapter 根据 pair 和 attempt 构造稳定 bootstrap room，D 请求还需要知道对应 P 的 bootstrap endpoint。Abort 协议和内部响应字段也由引擎适配器封装。普通 OpenAI 路径与 token-only 路径的 body 又会不同，阅读时先固定一个 API 合同，再对照扩展分支。

domain 层为什么不断出现

domain/scheduling.py 定义选中资源等结果，instance_provider.py 提供调度依赖接口，instance_manager.py 保存成员视图。agent_hint.py、scheduling_constraint.py 和 scheduling_pin.py 解析或表达定向约束，block_offset_translator.py 连接消息边界与 KV block 坐标，responses_input.py 适配 Responses 输入。

这些模块帮助 Router 在通用对象上工作。看到字段后还需追踪其消费方，例如一个优先级或会话提示只有被调度或引擎路径使用，才形成完整行为。源代码阅读应从定义继续走到实际调用。

转发边界还包括 HTTP 客户端。BaseRouter 依据 ScheduledResource 建立请求目标，使用连接池和配置超时发送原生请求。api_client/ 中的 Controller、Conductor 和原生引擎客户端则服务于各自的管理、索引或状态查询。相同的 HTTP 技术被用于不同语义，沿调用方确认用途，可以避免将一次 Conductor 查询误画为推理数据转发。

当 Controller 发布删除事件时，旧端点连接和关联请求也需要收尾。成员缓存、客户端连接池和 RequestManager 因而存在衔接关系。正常请求只看“发送并收到响应”容易忽略这部分，加入“请求执行途中目标被删除”的练习，才会看见领域对象与基础通信层为何需要彼此通知。

建议将三种 P/D 协议画成三条独立时序。它们共享资源、请求和错误基础设施，但开始阶段、等待条件及回调边界各有不同。源码中的能力检查决定哪些实例能够配对。

请求完成的标志包含资源清理

响应整理与上下文退出

D 返回后，Router 合并必要的使用信息、维持客户端响应形状，并剥离 kv_transfer_params 等内部协议字段。token-only 结果按需经过 Derender。流式请求还要控制何时真正向客户端提交内容，这将在流式与恢复篇展开。

BaseRouter._manage_request_context() 将请求加入 RequestManager，在退出路径中保护清理操作。它先等待相关后台释放，再回收残余负载，最后删除请求记录。资源申请成功但本地账本写入失败时，prepare_resource() 也会尝试补偿回滚。这个流程连接共享账本与进程本地状态。请求上下文与资源回收

用测试重走 R1

先读 test_pd_protocol_adapter.py，观察 P 请求、P 响应和 D 请求的断言。再读 test_router_native_handoff.py 的成功路径，看 mock P 返回什么、mock D 收到什么。随后对照 test_base_router_prepare_resource.py 和 test_workload_action_handler.py，理解异常和取消如何触发回滚与释放。

最后自己建立一张执行记录。第一列写 req_id 和 attempt_seq，第二列写当前阶段，第三列写 P/D endpoint，第四列写任务状态，第五列写实际负载记录。模拟 P 成功后 D 分配失败，再模拟 D 返回前客户端取消。能够指出哪些对象仍需清理、由哪个 finally 或上下文处理，就完成了从入口到收尾的一次源码阅读。

另一个检查方法是为每条跨边界调用标明数据大小。入口传原始 JSON，Render 传协议和 token 元数据，P/D 转发传各阶段原生请求，KV 票据承载交接信息，Connector 处理实际 KV 张量。这个练习把控制信息与大型数据流放回正确位置，也帮助后续分析网络与延迟成本。

读完之后还应能解释同一个接口为何出现不同执行路线。配置提供允许范围，当前健康成员提供可行拓扑，请求合同提供输入与响应要求，三者共同决定最终 Router。将这三项逐个替换，再观察选择函数的分支，可以比背诵类名更稳固地掌握结构。

本篇的阅读产出是一条带状态归属的调用链。HTTP body、RequestInfo、AttemptContext、ScheduledResource、handoff ticket 和最终响应应当各有位置，异常路径也应能沿同一张图返回。

把机制讲清楚

先自行作答，再展开查看参考回答、源码定位与追问解析。把答案落到对象、状态和代码位置上。

HANDOFF 为什么可以延后选择 D？

参考回答

HANDOFF 中，D 执行需要 P 返回有效交接信息，资源选择可以靠近进入 Decode 的时刻进行。当前 _create_attempt() 允许先取得 P，P 完成后再经 _ensure_handoff_decode_resource() 申请兼容 D。这样能参考较新的 D 负载，并缩短提前占用 D 账本的窗口。

这属于阶段编排与负载记账的选择，并不表示 P 返回后已完成全部数据传输。D 请求携带票据，Connector 继续落实 KV 使用。还应检查当前 attempt 是否已经有 D 资源，延后分配函数会在资源已存在时直接返回，避免重复申请。

源码定位 · _run_handoff_nonstream_attempt() / _ensure_handoff_decode_resource()

继续追问 · 标出 P 完成、发起释放、释放确认和选择 D 四个时间点。

追问参考 实际顺序是 P 完成、提交 P 的后台释放任务、开始延后选择 D。释放确认可能与 D 分配并行，不能把发起释放当作共享账本已经扣减。请求结束时还要等待在途释放，再进行残余记录回收。

交接票据与 KV 张量各经过哪里？

参考回答

P 响应中的 kv_transfer_params 先经过 VllmProtocolAdapter 校验，再保存为 PrefillMetadata.handoff_ticket。构造 D 请求时，Adapter 把这份票据复制到请求体。Coordinator 因而负责传递协议元数据，并保持同一次 attempt 的 P/D 关联。

实际 KV 数据由引擎、Connector 及配置的传输或存储后端处理。HTTP 成功还要满足交接合同，当前解析会要求非空参数及正确的 do_remote_prefill 标记。说明字段含义时，应结合所用 Connector 的约定，避免从一份票据推导所有后端的数据路径。进一步分析时，还要记录引擎版本和当前启用的传输后端。

源码定位 · PrefillMetadata / VllmProtocolAdapter.parse_prefill_response()

继续追问 · 跟踪 PrefillMetadata 里的元数据，再说明实际数据流。

追问参考 PrefillMetadata 保存 handoff_ticket 和可选 usage。票据描述继续执行所需的远端 KV 交接参数，usage 保存统计信息。其后可追 build_decode_request() 如何注入参数，再进入具体 Connector 确认地址、块身份与数据搬运。

切换引擎为什么需要 Adapter？

参考回答

Router 负责选择资源、组织阶段、等待任务、处理失败和释放负载。Adapter 将通用阶段转换成原生 API 与 body，统一请求身份、交接字段、P 响应校验和必要的 abort 请求。这样更换引擎协议时，可以集中检查消息合同，同时保留公共生命周期处理。

Adapter 也需要结合实例宣告的引擎类型和调度能力使用。配置了一个名称，仍需确认 P/D 两端能够按同一协议协作。阅读时先识别 coordination mode，再追构造请求、解析结果和停止尝试的调用顺序，才能说明兼容边界。

追问参考 HANDOFF 先等 P 返回票据，再发 D；TRIGGER 先发 D，由 D 回调当前 Worker 的 metaserver 触发 P；BOOTSTRAP 为 P/D 准备共同的 host、port、room 信息并协同执行。三者的同步条件决定资源准备和失败清理方式。
