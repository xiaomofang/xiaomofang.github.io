前几章已经把用户请求走过的 Coordinator、调度器和缓存索引串了起来。本章沿着另一条链走到设备所在的节点，观察 Controller 发出的启动指令如何变成原生引擎进程，以及进程运行以后谁负责收集健康事实、执行重启和协调故障恢复。NodeManager 把全局实例管理与节点上的具体执行接在一起，它的代码适合用“接收命令、生成规格、启动进程、观察状态、执行收尾”五个动作来阅读。

一、从一个节点代理建立运行地图

1.1 应用骨架怎样组合模块

NodeManager 继承公共的 Application，在 init_modules() 中先建立 Daemon 和 NodeManagerAPI。当 Daemon 的活动服务包含引擎时，应用继续建立 RegisterManager、HeartbeatManager，最后启动本地退出仲裁。这个顺序有明确依赖，仲裁线程读取心跳管理器提供的端点事实，因此需要等共享配置和模块对象都绑定完成。仅运行 KV 服务的 Pod 使用更小的模块集合，代码由活动服务决定是否参加引擎注册与心跳。源码 · NodeManager 应用组装

1.2 按状态归属理解文件

注册管理器保存 Controller 分配的实例身份和启动参数，心跳管理器保存当前端点状态，进程监督器保存本地进程对象，Daemon 负责把服务运行和退出决策协调起来。读到同一个 endpoint id 出现在几个文件里时，要追问每个模块保存的是哪种事实。实例已经注册、进程已经创建、健康接口已经通过、实例已经进入调度池，分别对应四个里程碑。

本章阅读目标

选择一个端点，追踪它的 instance_id、dp_rank、设备可见范围、业务端口和运行状态。读完后，应能说明这五项信息在哪产生、由谁消费，以及启动失败时怎样回收已经创建的资源。

二、注册、API 就绪和启动身份

2.1 先具备接收命令的能力

api_ready_event.py 定义了进程内的就绪事件。注册线程在向 Controller 发起注册前先等待 NodeManager 管理 API 就绪，因为 Controller 完成实例组装后会立即回调启动接口。当前 _register() 等待 30 秒，超时会记录错误并继续尝试注册。随后使用从 2 秒开始、最大 32 秒的指数退避，持续尝试直到注册成功。阅读这个函数时，应把 API 等待超时和注册重试间隔分别记录。源码 · API 就绪事件 源码 · 注册与启动身份

2.2 RegisterMsg 与 StartCmdMsg 分别传什么

_gen_register_msg() 从配置读取 job、模型、角色、引擎类型、dispatch 能力、FT 能力、业务端口、并行配置、设备数和节点数等，构造 RegisterMsg。Controller 汇总这些描述，随后给各节点发送 StartCmdMsg，其中包含分配好的实例身份、端点、master 信息和 node rank。注册消息告诉控制面本节点能提供什么，启动消息带回控制面已经确定的执行拓扑。源码 · 组件间消息合同

ranktable 路径还有硬件差异，A5 路径会跳过 HCCL ranktable 加载。快照恢复需要重注册和身份重绑，已有进程的本地 endpoint key 可能需要映射到新启动消息中的 id。理解这条分支时，应追 ReregisterMsg、注册管理器保存的 endpoints，以及监督器的 rebind_endpoint_ids()。这样才能解释恢复出来的进程怎样重新进入统一实例身份体系。

三、从不可变规格走到原生进程

3.1 models、factory 与 config_factory

native_engine/models.py 把启动拆成几个明确的对象。LaunchContext 保存角色、实例、DP rank、node rank、地址、端口、环境和可选快照信息。CommandSpec 保存 argv、环境和工作目录。ProbeSpec 保存健康路径、超时、重试和是否仅检查进程。LaunchSpec 组合命令与探针。前几个对象使用冻结 dataclass，并对映射复制或包装，便于在启动前固定输入。可变的 RuntimeProcess 由监督器独占管理，保存进程句柄与本地运行状态。源码 · 启动规格与运行态

factory.py 根据归一化的引擎类型选取无状态 Backend，config_factory.py 再惰性加载 vLLM 或 SGLang 的 CLI 配置转换器。BaseNativeEngineBackend.prepare() 先建立并验证 EndpointConfig，加载当前角色对应配置，交给转换器生成 CLI，最后返回 LaunchSpec。这些函数能够在没有模型进程的测试里验证大部分参数传播。源码 · Backend 公共转换 源码 · 配置转换工厂

3.2 用四个 DP 端点跟一次启动

设一个教学实例在当前节点有 DP0、DP1、DP2、DP3 四个业务端点，每个端点使用两个本地设备。NativeEngineService._pull() 逐个端点复制基础环境，计算设备可见范围，用 endpoint id 填充 LaunchContext.dp_rank，再传入业务端口、master 和 node rank。vLLM 转换器最终生成原生 data-parallel-rank 等参数，监督器以 endpoint id 为 key 保存进程。这个例子表达参数传播关系，具体可见设备集合仍由部署配置和服务中的计算函数决定。源码 · 原生引擎服务 源码 · vLLM 参数转换

假设 DP0、DP1 成功启动，构造 DP2 的规格时失败。服务记录本轮已经启动的 endpoint id，异常处理会逆序停止这些进程，再把失败交给上层。监督器自身也约束重复启动，同一端点已经运行且规格相同会返回“本次没有新启动”，规格不同则报错。这样外层回滚只回收本轮真正创建的进程，避免重复命令把既有运行态当成本轮产物清掉。

3.3 进程组和探针的生命周期

ProcessSupervisor.start() 使用 argv 列表启动进程，记录启动时间与进程组身份。state() 先看进程是否退出，再按探针检查原生服务。普通端点使用健康接口，headless 端点可使用进程检查，快照路径还会解释不同健康返回状态。冷启动阶段允许加载模型，超过启动窗口仍不健康则推进本地状态。停止通过进程组协调子孙进程退出，并保留超时后的强制收尾路径。源码 · 进程监督器

四、服务注册、KV 服务和启动加速

4.1 registry 与 protocols 让 Daemon 管理不同服务

services/registry.py 使用装饰器登记服务，按配置发现并导入对应模块，再实例化活动服务。空服务配置默认保留 engine。具备 prepare 阶段的服务按 prepare_priority 排序，数值较小者先准备。DaemonService 约定 stop 与 health_check，PreparableService 再增加 prepare。Daemon 因而可以通过稳定合同管理引擎和存储服务，同时让每种服务封装自己的配置、进程与健康细节。源码 · 服务注册表 源码 · 服务合同

子模块 负责的工作 与引擎的连接
mooncake/lifecycle.py 准备配置并管理独立 Store 服务进程，处理本地健康和重启 KV 服务拉起阶段启动，向存储体系贡献容量
mooncake/bootstrap/ 封装特定 Ascend 平台的进程启动准备 隔离运行环境和通信资源差异

Mooncake 与 Memcache 的实现都有服务生命周期边界。Memcache 在 inprocess 模式下准备用户管理的配置，standalone 模式才由本模块启动专用子进程。Mooncake 的生命周期层选择对应硬件 bootstrap，并协调服务进程的通信资源。阅读时应先判断配置激活了哪个 backend 和模式，再沿实际启动函数进入子进程。源码 · Memcache 生命周期 源码 · Mooncake 生命周期

4.2 启动加速的输入、覆盖和适用性

startup_acceleration.py 根据配置解析可复用缓存根，生成引擎环境，并检查 Startup Plan 文件和图复用目录。启用图复用时，它会产生 eager、编译及图模式相关覆盖，D 角色使用对应的 decode-only 图模式。这里完成的是运行前准备和配置衔接，某份历史 profile 是否适用于本轮模型、设备和引擎执行仍由后续引擎判断。学习时可对照覆盖合并函数，观察嵌套配置怎样保留其他原生选项，以及冲突如何被记录。源码 · 启动加速准备

五、健康事实、虚推和统一退出仲裁

5.1 健康采集与心跳发送分开

HeartbeatManager 维护端点列表、状态、退役集合与端点代际。状态线程等待 Daemon 提供的引擎就绪事件后轮询本地运行态，报告线程按节奏发送心跳。配置更新和端点更新受锁保护，外部读取获得稳定快照。端点变化会推进 generation，避免仲裁沿用上一轮拓扑的连续异常计数。代码还保留冷启动宽限期，让模型加载与业务异常能够按不同阶段处理。源码 · 心跳与端点事实

5.2 virtual_inference 的几个小模块

健康接口能够表达服务自身的判断，小型推理请求又提供了一种实际执行信号。capabilities.py 判断配置、DP master、headless 和使用率阈值是否允许开启 vLLM 虚推。spec.py 固定探测目标身份，requesters.py 发送小型 Completion 并读取容量等待指标，worker.py 组织预热、周期请求和连续失败，ai_cube.py 采样 AI Cube 使用率。当前路径围绕所选 active DP master 运行，缩容更换 master 后会重新协调探测目标。源码 · 虚推 Worker 源码 · 虚推能力判断

虚推失败需要结合负载解释。当前 Worker 在周期检查中采样 AI Cube 峰值，高负载时延长请求间隔。低使用率下的小请求失败还会查询 capacity-waiting 信号，容量排队或指标不可用时存在跳过失败计数的分支。最终异常标志会反馈到服务运行状态，再由 Daemon 统一仲裁退出。可以用“进程仍在、健康接口失败、虚推失败、容量等待大于零”四个事实组合，练习解释每层知道什么。SGLang 路径还应结合它的原生健康语义单独阅读。

5.3 有期限的 freeze 协调本地恢复

Daemon 的进程监督线程和退出仲裁线程分别处理进程死亡与连续异常。退出仲裁读取心跳事实，在宽限期或 freeze 有效期间重置异常计数。freeze 使用截止时间，后来的冻结请求取更长的有效期限，避免一个较短操作覆盖已经建立的恢复窗口。引擎故障上报被 Controller 接受后，Daemon 才按恢复等待窗口冻结。这样能够给全局恢复留出机会，同时在消息丢失或恢复没有继续时通过期限恢复本地判断。源码 · Daemon 监督与退出仲裁

六、FT 代理与退役端点的一致收尾

6.1 status、apply、guard、finalize

EngineFtManager 定期查询原生引擎 FT 状态，并提供恢复期间的主动查询和指令代理。query() 并发刷新指定端点，传输失败会形成 unknown 结果。明确 dead 的引擎响应才提供不可逆移除所需的权威证据。apply() 当前接受 retry 和 scale_down 指令，校验端点归属并转换原生参数。scale-down 的 store 端口还会结合 master rank 解析，因此参数检查覆盖 rank 类型、范围和最终端口范围。源码 · 引擎 FT 代理

guard() 为恢复事务建立带身份和期限的本地保护，finalize() 把提交或放弃结果交给 Daemon。提交退役集合时，需要同时更新心跳事实和 FT 监控出口。假设 DP2 已在全局缩容事务中退役，如果心跳仍不断把 DP2 的旧异常送回 Controller，恢复证据就会反复出现。代码中的 retired 集合以及身份校验，正是为了让多个观察出口与同一次拓扑提交一致。对应的 API 路由在 node_manager_api.py，阅读时应把 HTTP body、事务 request id 和本地端点集合作为一组追踪。源码 · NodeManager 管理与 FT API

再看一条本地重启时序。原实例已经保存四个端点，Controller 通过 engine-restart 请求要求 NM 原地重拉。Daemon 需要先校验当前实例身份和已有启动参数，建立恢复等待窗口，停止旧引擎，再用保存的角色与端点规格重新启动。心跳管理器应在新运行态建立后继续上报这一实例，进程监督器则持有新的进程对象。这个例子中逻辑实例身份与操作系统进程身份各有生命周期，排障记录应同时保存两者，否则很容易把迟到的旧进程消息与新运行态混在一起。源码 · 本地引擎重启编排

阅读过程中还可以建立一份“状态转换记录”。每一行写下触发动作、调用前的端点代际、启动规格、进程状态、心跳状态和退出仲裁是否冻结。例如进程创建后，业务健康可能仍在启动宽限期内，心跳也还没有让全局实例进入可服务状态。随后原生探针通过，虚推是否开启又取决于能力条件。这样逐项标注之后，一条笼统的“服务未就绪”就能被拆成配置转换失败、进程创建失败、模型尚在加载、业务执行异常或成员发布尚未收敛等可继续定位的阶段。

6.2 用已有测试完成本章练习

先读 test_backends.py 和 test_config_contract.py，为 DP rank、master 和设备配置画一条规格转换线。再读 test_service.py、test_supervisor.py，手工模拟第二个端点启动失败，写出哪些进程属于本轮、哪些需要回滚。接着用 test_heartbeat_manager.py 和 test_daemon.py 跟一遍健康异常、freeze 到期和退出仲裁。最后阅读 test_engine_ft_manager.py、test_retired_metrics.py，检查提交退役端点以后哪些出口需要同步过滤。练习产出应包含输入消息、状态所属对象、调用顺序和失败收尾，随后就能进入下一章的全局恢复编排。测试 · 引擎服务 测试 · FT 代理
