前面几篇已经跟踪了请求、缓存、进程和恢复事务。接下来要回答的，是怎样从运行证据判断系统是否按设计工作。一次请求变慢，可能发生在 tokenization、调度、Prefill 排队、KV 加载或 Decode。一个吞吐数字下降，也可能来自请求长度变化、实例退役或计数器重置。读懂 PyMotor 的可观测性代码，需要把采集边界、聚合语义和请求时间线放在同一张图上。

从原生端点到服务视图

把一份指标沿调用链送出去

指标链路从原生引擎的 /metrics 开始。Coordinator 的 NativeEngineApiClient 获取文本，MetricsCollector 定期采集和解析，把结果关联到实例与端点，再通过语义聚合引擎生成实例、角色和服务视图。MotorMetricComputer 追加速率、实例计数及容量信号，Obs 服务把结果输出给外部监控。这里要同时记住数据从哪里来，以及经过了几次变换。阅读 MetricsCollector

采集线程会在本轮获得有效结果时更新缓存和版本，并复用这些结果向调度侧发布 KV 使用率，避免为了相同信息再抓取一次引擎指标。服务处于备用等不应提供指标的状态时，采集器会清理旧结果。数据有效性与进程角色因此共同决定对外观察到什么。阅读采集线程与服务门控

先认识七个文件的分工

子模块 负责的变换 阅读时追问

get_metrics() 支持 full、instance、role、dp、node，以及只输出 Motor 指标的 motor 视图，格式可选择 Prometheus 文本或 OpenTelemetry 兼容对象。端点调度状态等附加指标主要跟随 full 与 motor 视图输出。学习时应先选择问题对应的视图，研究 DP 倾斜就先保留 DP 维度，研究整体需求则观察服务和角色维度。阅读聚合范围定义、阅读指标视图输出

聚合方式决定数字的含义

从名字、类型继续走到语义

Metric 保存名称、帮助文本、类型以及标签和值的列表。MetricRegistry 进一步给已知指标标记语义。累计请求、运行请求数和队列深度通常求和，热点资源指标取最大值，资源利用率和缓存指标按当前实现求算术平均，元信息选取一份。未知指标根据类型走默认路径，直方图合并，其余类型通常求和。研究一个新指标时，先查注册表，再追输出视图，才能解释聚合结果。阅读指标语义注册表、阅读语义归约

假设端点甲报告 90 次命中、100 次查询，端点乙报告 1 次命中、10 次查询。服务级命中率应先汇总命中数与查询数，再得到 91÷110，约为 82.7%。如果先计算两个局部比例再平均，会得到 50%，因为它给只处理少量查询的端点分配了同样权重。源码使用 RatioPair 描述分子分母关系，再从聚合结果派生比例。这个算例是统计口径演示。阅读 _derive_ratio()

分位数从合并后的分布推导

延迟直方图由 bucket、count 和 sum 共同描述。聚合引擎先按相同标签与桶边界累加，再从合并后的累计桶估计 P50、P95、P99，并由总和除以数量计算均值。它的分位数函数采用桶内线性插值。这样一个流量大的端点会按它实际贡献的样本影响分布。直接平均各节点已经算好的 P99，会丢失样本量和分布形状。阅读直方图合并与分位数计算

标签仍然重要。模型、角色或其他保留标签不同的桶应分别处理。聚合上下文还会影响角色过滤，当前服务范围会按注册的 role_scope 选择来源，DP 视图本身保留细粒度数据。阅读测试时，可以手工构造两个端点、三个桶，先计算每桶合计再对照实现，观察某条标签出现或缺失时结果如何变化。阅读聚合与分位数测试

一次口径检查

看到平均 KV 利用率下降时，再查看最大值和 DP 分布。看到服务 TTFT 下降时，再检查样本量、请求长度和统计起点。当前部分利用率采用算术平均，异构端点容量不同时，还需要结合各端点容量解释整体资源状态。

从累计计数到容量建议

两次采样之间才有速率

累计 token 数表示截至采样时已经完成的工作。TPS 来自相邻采样的差值与时间间隔。MotorMetricComputer 按 job、DP rank 和具体标签序列保存基线，识别实例身份变化或计数器显著下降引起的重启，并修正后续累计值。每个标签各有基线，避免把一个标签的历史迁移到另一个标签。第一次采样建立基线，尚不能提供完整的采样区间。阅读计数器修正与速率计算

可以用一个小练习理解状态的价值。第一次采样看到累计 10,000 token，五秒后看到 12,000 token，这个区间为每秒 400 token。若引擎随后重启，原始计数变为 200，直接相减会产生负吞吐。实际代码通过序列状态处理这类情况，再把有效增量交给派生指标。这个练习还应加入同一指标的两个不同标签，检查它们是否保持独立历史。阅读 _compute_effective_and_rate()

需求、供给与 KV 约束

CapacityPlanner 的需求侧从请求增量、token 增量和时间间隔估计请求到达率与平均长度，再使用指数移动平均减少抖动。零增量和负增量有保持旧样本等处理。供给侧通过观测样本及可选先验维护 P/D 容量估计。只有把需求和容量放在同一单位下，副本需求才有可解释性。阅读需求跟踪与容量估计

\[ D=\operatorname{EMA}(\lambda)\operatorname{EMA}(\bar L),\qquad N_{\mathrm{throughput}}=\left\lceil\frac{D}{C\rho}\right\rceil \]

其中 D 是 token 每秒的需求，C 是每实例容量，ρ 是目标利用率。假设平滑需求为每秒 24,000 token，每实例容量为每秒 10,000 token，目标利用率 0.8，吞吐约束要求三个实例。D 侧还会比较 KV 容量约束，若后者要求四个实例，最终选择四个。实际规划器使用到达率、KV 驻留相关时间以及平均输入输出长度估计 KV 需求，并在有有效容量信息时计算该约束。以上数字用于演算。阅读 compute()

规划器输出所需副本、利用率、容量校准状态和有条件的 P/D 比例。metric_computer.py 对建议比例进一步平滑与限制范围，缺少有效校准或需求时可使用当前比例。hpa_contract.py 为约定指标生成将冒号替换为下划线的别名，便于外部指标适配器消费。Pod 的创建与缩减由外部部署和控制链执行，学习时应沿着指标消费方继续追踪。阅读 HPA 命名合同、阅读容量规划测试

把整体变化还原成一次请求

Trace 保存阶段与关联关系

TracerManager 配置 OpenTelemetry provider、采样器和 OTLP exporter，提取与传播 traceparent、tracestate。TraceObj 保存当前请求的 span、事件、错误、首 token 时间及 token 计数。Provider 支持在配置变化时更新，并在退出时进行 shutdown。读这部分时，要继续寻找 Router 在哪里创建 span、在哪里设置首 token，才能确定每个数字覆盖的执行范围。阅读 TracerManager 与 TraceObj

同一条用户请求可以画出到达、tokenize、选 P、发 P、P 完成、选 D、首个可见输出和结束几个时间点。若总 TTFT 增加，逐段比较这些边界能帮助定位新增等待。引擎本地的延迟直方图与客户端端到端延迟各有起止范围，报表应明确采样位置。当前 TraceObj 依据被调用方设置的首 token 时间计算 TTFT，并用自身的 token 计数计算 TPOT，复核时还要追该计数怎样累计。阅读 set_end_and_ttft_tpot()

日志、告警和资源清单连接状态变化

common/logger 负责 logger 构建、formatter、handler、轮转压缩与限频。多进程日志可以经 ZMQ handler 汇聚到主进程的 LogCollector，再写入统一文件。分析一次恢复时，应沿请求身份、实例身份、endpoint 和恢复事务身份关联记录，把“检测到异常”“开始撤流”“apply 成功”“幸存者发布”排成时间序列。阅读日志汇聚、阅读限频日志

common/alarm 则定义 Record、Alarm、Event、严重程度、发生与清除时间以及序列化协议。实例异常、精度异常、拥塞、主备切换等对象把不同来源的事实转换为可消费的运维事件。Controller 的 alarm_store 保存查询状态，inventory_collector 汇总资源清单。日志适合追过程，告警对象和清单适合表达当前运维状态，三者可以用同一实例身份相互定位。阅读告警记录合同、阅读 Controller 观测门面

公共基础设施怎样支撑这些链路

从公共能力追到具体调用方

目录或文件组 职责 与前文的连接
common/app/application.py 模块注册、信号、配置传播、daemon loop、逆序停止 Controller 与 NM 的应用骨架
common/http 连接复用、超时、TLS、证书与 FT 协议客户端 推理与管理调用的边界处理
common/etcd 客户端、锁、版本化持久状态及 protobuf 控制状态恢复和主备所需存储
common/standby 主备角色循环、租约续期和角色回调 哪些进程当前应对外提供服务
utils/config_watcher.py、config_runtime.py 监听变化并传播配置 组件能否使用新的运行参数
utils/port_allocator.py、env.py 端口与环境参数 部署参数到组件入口
utils/process_utils.py、snapshot_utils.py 进程与快照辅助 本地执行及恢复准备
utils/ip.py、net.py、validators.py 地址、网络和输入校验 跨组件协议的可用性
utils/singleton.py、consecutive_counter.py 线程安全单例与连续计数 单进程状态复用及异常判定

Application 以逆序停止模块，遇到异步 stop 会等待协程完成。默认启动钩子保留给具体应用覆盖，因为部分模块在构造时启动，另一些模块等待端点配置或外部命令。配置监听发生变化时，再逐模块调用支持的 update_config。阅读基类时，把这些生命周期约束与 Controller、NM 的覆盖方法对照起来，能理解为什么不能仅凭一个 start 方法的存在决定调用时机。阅读应用生命周期

持久状态模型保存 data、version、timestamp 和 checksum，读取时验证完整性。锁与租约控制主备竞争，状态快照用于恢复数据，这两种用途应沿各自调用者学习。普通 Python 单例在当前进程内复用对象，跨 Worker 的负载一致性还要通过前文的共享内存机制。阅读持久状态模型、阅读主备运行循环

构建产物也是运行前提

setup.py 声明 Python 版本至少为 3.11，并把运行依赖安装与 wheel 安装分开组织。build.sh 串联 protobuf、Rust 和 Python 打包，共享负载的 libmindie_workload_shm.so 是必需产物，脚本会在构建和归档验收时检查它。KV Conductor 的二进制则按构建条件作为可选组件打包。Python 源码阅读完成后，还需要核对运行镜像包含哪些原生产物及其 ABI。阅读 Python 打包、阅读构建与归档验收

scripts 提供 Rust 工具链和 protobuf 等辅助，docker 组织镜像，model_configs 保存典配，examples 连接部署和功能示例，docs 保存设计说明。pre-commit 与流水线配置承接格式、类型风格、日志和静态检查。遇到“源码有这个功能，但运行环境没有”时，应该顺着这些目录检查源码版本、wheel、镜像和启动参数如何关联。阅读构建与工程约定

用实验把源码理解变成可复核的经历

先把测试当成输入输出教材

第一轮实验可以完全围绕现有 mock 测试。先读 test_semantic_metrics.py 的直方图和比例断言，再读 test_capacity_planner.py 中请求增量、零增量、负增量、吞吐约束和 KV 约束的样本，最后读 test_tracing.py 的上下文传播、事件和安全请求结构。每次只改变一个输入，预先写下期望结果，再沿实现寻找保障它的分支。执行 Python 测试时使用项目的 tests/run_tests.sh 入口，并检查 passed、failed 与 skipped 的具体含义。阅读语义测试、阅读规划测试、阅读追踪测试

第二轮再进入隔离测试环境，选一个可复现的现象。缓存亲和实验可以固定请求序列，控制预热条件，同时记录最终调度端点、分层命中、引擎实际复用、客户端 TTFT 和成功吞吐。故障恢复实验可以从异常证据出现开始计时，记录撤流、apply、finalize 与 survivor 发布。对应的进程内测试为协议与状态边界提供基础，真实集群实验补充设备、通信与部署行为。阅读请求实验基线、阅读恢复实验基线

简历中的每个动作都能找到证据

项目介绍可以先交代系统范围，再说明自己实际负责的部分。源码学习阶段可以记录完成了哪些链路分析和实验复现，部署排障阶段可以记录拓扑、问题、定位依据及处理结果，代码开发阶段则进一步指向变更、测试和验收。叙述顺序保持为场景、问题、负责范围、技术方法、验证条件与结果。这样面试官追问某个函数、指标或故障分支时，你能回到具体证据继续展开。

性能结果需要同时保存模型、硬件、引擎版本、并行配置、输入输出长度、并发、缓存预热、失败率和统计口径。若优化对象是调度耗时，就给出该阶段的观测边界。若结果是端到端 TTFT，就使用客户端样本并结合 Trace 解释变化来自哪里。吞吐增加也要与正确性和成功率共同报告。单个数字背后的实验合同，决定别人能否复核这段经历。

把机制讲清楚

先自己回答，再展开核对。把答案落到对象、状态和代码位置上。

各端点的 P99 能直接平均吗？

全服务分位数需要原始样本或可合并直方图。合并相同语义和边界的桶后再估算分位数，才能保留样本量对分布的影响。

继续追问 · 用不同流量的两个端点解释平均分位数丢失的信息。

TTFT 高，怎样缩小问题范围？

按客户端端到端时间线拆解 tokenize、选路、P 排队与计算、KV 处理、D 首次生成及响应输出。聚合指标定位范围，Trace 与 req_id 日志核对具体请求。

继续追问 · 先验证请求长度和样本口径，再判断哪个阶段变化。

怎样把源码理解写成自己的项目经历？

先说明实际负责的部署、开发、排障或验证范围，再给出问题、方法、验证条件与结果。项目已有能力和个人交付需要分别有可核验依据。

继续追问 · 准备一份配置、一个关键调用链、一组对照结果和一次失败处理记录。
