向一个分布式推理服务发送请求之前，集群必须先知道模型在哪里、哪些节点属于同一组、哪个地址能接收请求。PyMotor 将这件事拆成配置解析、节点注册、实例组装、进程启动、健康判断和资源发布。沿着这条启动链阅读，能够把部署文件与日后看到的每一个 HTTP endpoint 联系起来。

本文以普通 vLLM 多端点部署为主线。涉及跨节点、单 HTTP 多 DP、主备和快照恢复时，会说明额外的条件。配置、状态和事件都以本系列对应的源码修订为依据。

一、配置要穿过哪些层才能生效

1.1 部署资源、Motor 配置与原生引擎参数

部署配置包含不同层次的决策。实例数量与每实例 Pod 数决定资源组织，DP、TP、PP 等决定模型执行拓扑，调度策略与超时则决定服务行为。读到某个配置项时，首先找它的消费方。一个值可能被 generator 写进环境变量，也可能进入 NodeManager 的端点配置，最后成为原生引擎启动参数。

examples/deployer/deploy.py 负责组织部署，lib/config_validator.py 校验组合，lib/generator/ 生成各组件资源。config/ 中的组件配置类与引擎 resolver 则把部署输入转换为运行时对象。这一条数据流值得在阅读笔记里单独画出来。部署入口源码

子模块 承担的工作 建议追踪的输入
generator/engine.py 引擎工作负载、设备、环境与挂载 角色、Pod 数、模型目录与资源声明
generator/controller.py、coordinator.py 控制与请求服务资源 地址、端口、配置与主备要求
generator/infer_service.py、single_container.py 服务集合与组合部署 部署模式及组件布局
generator/kv_conductor.py、render.py 缓存索引与请求预处理服务 可选功能开关及连接信息
generator/kv_cache_store.py、mf_store.py、storage.py KV 服务与存储资源 后端类型、介质与持久卷
lib/nodeport_allocator.py、generator/k8s_utils.py 端口分配和 Kubernetes 操作 暴露端口、ConfigMap 与工作负载
docker_deploy.py、slurm_deploy.py 其他运行环境的部署入口 同一配置在不同平台的落地方式

1.2 Resolver 如何处理新旧配置

config/resolver.py 递归把键名中的连字符归一化成下划线，再通过引擎适配器把原生参数映射为 Motor 内部字段。配置同时包含新 engine_config 和历史 model_config 时，前者优先，冲突会记录日志。并行配置中的 world size 由解析结果重新计算。这说明调试时需要检查解析后的值，原始文件中的同名项未必是最终值。Resolver 与引擎参数映射

以普通 vLLM 路径为例，取 DP=4、TP=2、PP=1、PCP=1，内部模型得到每端点并行规模 2、整体规模 8。默认多端点布局可以提供四个 DP 业务入口，每个入口由 TP2 对应的设备组织支持。启用 EP 后，专家阶段还需要按引擎定义的通信域协作。这个例子只用于理解字段，Pod 如何承载这些设备仍由具体部署决定。

\[W_{\mathrm{endpoint}}=\mathrm{PCP}\times\mathrm{TP}\times\mathrm{PP}=2,\qquad W=\mathrm{DP}\times W_{\mathrm{endpoint}}=8.\]
阅读配置时选三个参数做纵向追踪即可。将 tp_size 追到原生 CLI，将 job_name 追到实例聚合，将业务端口追到 Endpoint。这样能先建立跨模块的关系，再逐个补齐配置项。

二、容器角色怎样找到应用入口

2.1 boot.sh 是部署与源码之间的桥

startup/boot.sh 根据 ROLE 分发到角色脚本。prefill、decode、union、encode 进入引擎角色脚本，最终启动 NodeManager。controller 和 coordinator 分别进入各自 Python main。组合角色把多个组件放进同一容器，可选角色还包括 Render、KV Conductor 与 KV 存储服务。

因此，读部署脚本时应检查“最终执行哪个 main、传入哪个配置路径、设置哪些运行环境”。将所有 shell 辅助函数都读完才进入 Python，会让主线被大量准备逻辑打散。先从 ROLE 分发跳到明确的 Python 入口，再返回查需要的参数来源。角色启动分发

2.2 Application 提供长期运行的骨架

Controller 和 NodeManager 复用 common/app/application.py 的生命周期能力，包括模块注册、配置监听、信号处理、后台循环和停止。Controller 装配 Assembler、InstanceManager、EventPusher、API，以及按配置启用的 FaultManager 和观测模块。NodeManager 装配服务监督和 API，配置包含引擎服务时再启用注册、心跳相关模块。

这使“一个组件”成为若干协作模块的集合。部分模块有自己的后台线程，部分逻辑要等待外部启动指令，阅读时应继续追构造、start 和 stop 的实际调用。主备配置又会影响哪些模块当前能工作，所以生命周期应和角色状态一起看。应用生命周期骨架

从部署完成到可接请求，中间至少经历应用启动、引擎启动、健康确认和服务视图发布四个里程碑。每个阶段都应有自己的观察点。

三、NodeManager 怎样描述自己

3.1 RegisterMsg 是本地事实的第一份合同

RegisterManager._gen_register_msg() 从本地配置采集 job、模型、角色、引擎类型、协议能力、FT 能力、业务端口、并行配置、设备数量和跨节点信息，组织成 RegisterMsg。ranktable 的准备也在注册链中衔接，具体硬件路径会影响它的需要程度。

消息的作用是让 Controller 回答三个问题。这个节点属于哪组实例，能够暴露哪些端点，是否具备与其他节点一致的执行和恢复能力。公共消息定义在 common/resources/http_msg_spec.py，最好先读字段，再读消息生成代码。注册消息生成与上报

3.2 注册重试与 API 就绪之间的关系

NodeManager 在注册前等待自己的管理 API 就绪。这样 Controller 很快下发启动命令时，本地端口已经能够接收。源码中的等待存在超时分支，超时会记录问题并继续尝试注册，因此不能仅凭“进入注册循环”推断管理 API 已经可用。

注册失败后，当前实现从 2 秒开始指数退避，间隔最多增长到 32 秒，并持续尝试直到成功。手算失败后的等待序列为 2、4、8、16、32、32 秒。这个设计让控制器稍晚启动时节点能够自行接入，同时降低持续故障时的重复请求频率。重复注册还需要 Controller 端做幂等处理，单靠客户端重试无法保证实例结构正确。

阅读网络边界时同时检查双方。客户端告诉你何时重试、发送什么，服务端告诉你重复消息会怎样改变状态。将这两端作为一组阅读，能够解释“注册成功却重复启动”一类问题。

四、从多个节点组装逻辑实例

4.1 job_name、instance_id 和 endpoint_id

InstanceAssembler.register() 按 job_name 聚合同一个逻辑作业的节点。第一次注册建立 Instance 并分配运行身份，后续节点补充 NodeManager 和 Endpoint。它会检查同一实例的 FT 能力快照是否一致，并处理重复 Pod 注册、正在组装与已经组装等状态。

这三个身份要分开记。job_name 负责聚合，instance_id 标记这次运行的实例，endpoint_id 关联引擎业务入口及 DP rank。一个作业重建之后可能获得新的运行身份，后续删除和恢复操作需要携带正确身份，才能避免旧事件影响新实例。实例注册与组装

4.2 齐备条件与 headless

_assemble_instance() 先过滤异常端点，再判断期望端点或节点是否齐备。普通路径与 nnodes 大于 1 的跨节点路径具有不同条件。当前跨节点多端点分支按 DP size 与 nnodes 的乘积判断预期 NM 数，这个公式需要在对应分支的语境中理解。

跨节点组的从节点可以被标记为 headless。它们继续参与分布式执行，普通请求选择则通过 get_all_endpoints() 过滤这些入口。组装完成后，Assembler 汇总 master、ranktable、node rank 等信息，下发 StartCmdMsg。快照恢复还会携带已有主节点身份，并检查该节点仍然属于当前注册集合。

逻辑实例承载协作计算的整体身份，Endpoint 承载可访问入口。headless、单 HTTP 多 DP 与跨节点模式都会改变二者的映射，读者应依据实际配置画对象关系。

五、健康如何变成可调度能力

5.1 生命周期状态与观察者事件

NM 执行启动命令后，原生进程仍需要完成权重加载、通信初始化和健康确认。HeartbeatManager 将端点事实报告给 Controller，InstanceManager 综合端点状态和心跳时效，推进 INITIAL、ACTIVE、INACTIVE、PAUSED、DELETED 等状态。

实例进入 ACTIVE 后可以触发 INSTANCE_READY 观察者事件。状态是对象当前所处阶段，事件是通知其他模块发生了什么变化。把二者分开，才能读懂同一次状态转移为何同时影响请求成员、故障策略和告警。实例状态机与观察者通知

可以把最短状态路径写成 INITIAL 到 ACTIVE，再由端点异常或心跳超时进入 INACTIVE。服务恢复正常后，满足相应条件的实例可以回到 ACTIVE，持续失效则可能进入 DELETED。PAUSED 提供显式暂停语义，也需要考虑暂停期间异常与超时怎样处理。完整转移表还包含恢复编排与强制隔离的保护，所以手工推演时要同时标注“这个实例是否正在恢复”。

例如，某实例刚被恢复流程撤流，此时一个迟到的正常心跳到达。只按单次心跳恢复服务，会让正在重建的实例重新接流。源码中的额外约束用于协调健康事实与恢复事务。由此可见，心跳是状态机的重要输入，状态机还要考虑当前动作是否允许发布服务能力。

5.2 从观察者队列到 Worker 本地视图

EventPusher 将事件转换为 ADD、DEL、PAUSE、RESUME 等操作，经过队列发送给 Coordinator 的实例刷新接口。将网络发送放进消费者，有助于避免状态机处理直接被慢网络阻塞。失败后还会安排对账与同步，具体空集合和实例身份条件需要读分支。

Coordinator Mgmt 接收刷新后更新成员视图和共享内存，并向 Worker 发布变更。Worker 应用增量或进行全量同步。发布订阅通知有丢失窗口，版本检查与重新拉取提供补偿。因此，Controller 的“已经 ACTIVE”与某个 Worker 的“已经看到新实例”可能存在短暂时间差。实例事件发送与对账

可以手工演练一次两节点注册。第一节点到达时记录“组装中”，第二节点到达后满足齐备条件，两个 NM 收到各自启动指令。随后分别汇报健康，Controller 发布 READY 事件，Mgmt 更新成员版本，Worker 获得新端点。若只看到第二步便开始压测，请求仍可能遇到无可用拓扑。这个例子解释了启动过程为何必须分阶段观测。

Controller 的 InstanceManager 维护生命周期权威，Coordinator 的同名模块维护调度成员视图，Worker 还有自己的缓存。阅读同名类时先标注所在进程和状态归属，能够减少跨模块跳转中的混淆。

六、把公共设施接回这条启动链

6.1 每个工具模块对应一个运行责任

目录或模块 启动链中的作用 需要回答的问题
common/resources/ Instance、Endpoint、Workload 和 HTTP 消息合同 双方对字段和身份的理解是否一致
config/controller.py、coordinator.py、node_manager.py 组件运行配置 值何时解析、何时快照、是否支持热更新
config/endpoint.py、端口配置 端点与端口准备 管理端口和业务端口由谁消费
common/http/ 连接池、TLS、安全客户端及恢复协议 超时、证书和连接失效怎样反馈到调用方
common/etcd/、standby/ 持久化、锁、租约与主备角色 重启恢复和主备切换分别保护什么
utils/config_watcher.py、config_runtime.py 发现并传播配置变化 文件变化后哪个对象真正更新
utils/env.py、port_allocator.py、ip.py、net.py 环境、端口和地址工具 配置地址如何成为可连接地址
logger/、alarm/ 日志收集、限频和事件表达 哪个身份能串起一次启动或一次故障
process_utils.py、snapshot_utils.py 进程与快照辅助 已有运行状态如何重新绑定到新管理进程

部署配套中的 probe、prestop、日志收集、配置模板、补丁工具和 TUI 也可以据此分类。probe 让外部系统观察生命周期，prestop 协调退出，模板和补丁准备可运行环境，TUI 展示操作状态。它们服务于相同主线，第一轮可先沿实际调用读到边界，再回头展开实现。

配置监听也要追到最后一层。文件变化被 watcher 发现后，应用会传播更新，但已用于创建原生进程的并行参数通常需要新的启动过程。某些模块还在构造时保存配置快照。因此“配置文件已经更新”“Python 配置对象已经更新”“当前引擎按新参数运行”是不同观察点。选择一个无状态运行参数和一个并行参数分别追踪，能够看清热更新边界。

6.2 源码阅读与练习

建议依次阅读 resolver.py、boot.sh、RegisterMsg、RegisterManager._gen_register_msg()、InstanceAssembler.register() 和 _assemble_instance()，然后进入 InstanceManager 的转移表、EventPusher.update() 与 Mgmt 的 apply_refresh()。对应测试优先看 test_instance_assembler.py、test_instance_manager.py、test_event_pusher.py 和配置解析测试。

练习时画一张六列纸表，分别记录“时间、节点、输入消息、Controller 状态、发布事件、Worker 可见资源”。让一个节点重复注册一次，让一个启动命令失败一次，再让 Worker 漏掉一次增量通知。能解释每个场景如何恢复到一致状态，就已经把配置、控制和请求三层连接起来了。

本篇的完成标准是亲手追完一个参数和一个资源身份。参数从配置进入启动命令，资源身份从 RegisterMsg 进入 Instance，再进入 Worker 的候选集合。
