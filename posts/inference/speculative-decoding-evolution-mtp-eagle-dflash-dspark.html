投机解码四代演进：从 MTP、Medusa 到 EAGLE、DFlash、DSpark

投机解码从来不是一个方法，而是一条不断在「猜得准」和「猜得快」之间寻找新平衡点的技术谱系。 它从一开始就分叉成两条支线——自回归支线（Draft Model → EAGLE）追求依赖建模的精度， 并行支线（Medusa / MTP → DFlash）追求起草延迟的下限，直到 DSpark 把两条支线重新 缝合在一起。本文顺着这条演化脉络把每一步「为什么这么改」讲透。

读完本文，你应该能回答这几个问题：拒绝采样为什么能保证分布不变？MTP 和 EAGLE 长得像不像、 差在哪？并行草稿为什么会「虎头蛇尾」，又为什么第一步反而能赢自回归？DFlash 和 DSpark 到底谁解决了 什么？以及——训练这样一个草稿器，数据从哪来、怎么喂进去？

一、地基：为什么「先猜后验」不会损失一点精度

所有投机解码方法共享同一个地基：用一个轻量草稿器 \(M_d\) 提议 \(\gamma\) 个候选 token， 再用完整的目标模型 \(M_t\) 做一次前向并行验证整个候选块。差异只在草稿器怎么设计——但验证规则 必须严格保持目标分布不变，否则「加速」就变成了「偷工减料」。这条底线是后面所有架构创新的前提， 值得先讲透。

记 \(p(\cdot)\) 为目标模型在某一位置给出的分布，\(q(\cdot)\) 为草稿器在同一位置给出的分布。 草稿 token \(v\) 是从 \(q\) 里采出来的，但最终输出必须服从 \(p\)。做法是：

  • 接受：以 \(\min\!\bigl(1,\, p(v)/q(v)\bigr)\) 的概率接受 \(v\)。
  • 拒绝：一旦拒绝，本位置及其后所有草稿全部丢弃，从残差分布 \(r(x)=\mathrm{norm}\bigl(\max(p(x)-q(x),0)\bigr)\) 里重新采样一个 token。

为什么这样就无损？对任意 token \(t\)，它被最终输出的概率来自两条互斥路径： 「草稿采到 \(t\) 且被接受」的概率是 \(q(t)\cdot\min(1,p(t)/q(t)) = \min(p(t),q(t))\)； 「某次拒绝后从残差里采到 \(t\)」的概率是 \(\max(0,p(t)-q(t))\)。两者相加：

\[ P(\text{output}=t) = \min\bigl(p(t),q(t)\bigr) + \max\bigl(0,\,p(t)-q(t)\bigr) = p(t) \]

最后一步用到恒等式 \(\min(a,b)+\max(0,a-b)=a\)，对任意 \(a,b\) 都成立。所以无论 \(q\) 是什么样子， 只要验证按这套规则做，输出分布严格等于 \(p\)——草稿器只影响速度，永远不影响写什么。

一个数字例子。 假设目标分布 \(p\) 在某位置给出 cats: 0.52, dogs: 0.19, to: 0.09, eat: 0.07, 其他: 0.13， 草稿分布 \(q\) 给出 cats: 0.40, dogs: 0.25, to: 0.15, eat: 0.10, 其他: 0.10。 若草稿采到 dogs，接受概率是 \(\min(1, 0.19/0.25)=0.76\)；若草稿采到 to， 接受概率是 \(\min(1,0.09/0.15)=0.60\)。一旦被拒，残差分布只在「\(p\) 比 \(q\) 更看好」的 token 上有质量——比如 cats 上 \(\max(0.52-0.40,0)=0.12\)，其他 上 \(\max(0.13-0.10,0)=0.03\)——归一化后重采样，绝不会再采到刚被拒绝、且 \(q\) 本来就高估的 to。

每一步的平均接受率恰好等于两个分布的重叠面积，也是它们总变差距离（Total Variation Distance）的补集：

\[ \alpha = 1 - D_{TV}(p,q) = \sum_v \min\bigl(p(v),\,q(v)\bigr) \]

设 \(\tau\) 为每轮平均接受的 token 数（含验证阶段额外生成的 bonus token）， \(T_{\text{draft}}\)、\(T_{\text{verify}}\) 分别是起草与验证阶段的耗时，每 token 平均延迟为：

\[ L = \frac{T_{\text{draft}} + T_{\text{verify}}}{\tau} \]

这个公式定义了全部可优化的旋钮：降低 \(T_{\text{draft}}\)（起草更快）、 提高 \(\tau\)（\(q\) 与 \(p\) 更贴近，接受率更高）、 降低有效的 \(T_{\text{verify}}\)（验证更聪明，不做无谓的验证）。 接下来要讲的整条演化史，就是不同方法在这三个旋钮上依次做文章的过程——而且从一开始就分成了 两条路线。

二、起点分叉：外部 Draft Model、Medusa 与 MTP

Leviathan et al.（2023）与 Chen et al.（2023）最早提出的形态很朴素：另外训练一个小语言模型 \(M_d\)（比如用同系列的 7B 陪 70B），逐 token 自回归生成 \(\gamma\) 个草稿。它通用、无需改动 目标模型，但代价直白——\(M_d\) 本身是完整的自回归模型，\(T_{\text{draft}}\) 随 \(\gamma\) 线性增长； 且 \(M_d\) 与 \(M_t\) 之间没有共享表示，命中率完全取决于两个独立模型碰巧有多像。

真正的分叉出现在「怎么让草稿器和目标模型共享算力」这个问题上，几乎同时出现了两种答案：

2.1 Medusa：并行支线的起点，独立到近乎极端

Medusa（Cai et al., 2024）在目标模型最后一层的隐藏状态 \(h_t\) 上，挂 \(K\) 个独立的解码头， 每个头 \(k\) 直接从同一个 \(h_t\) 预测 \(t+k\) 位置的 token，彼此之间完全没有条件依赖。 这是并行支线最纯粹的形态：\(T_{\text{draft}}\) 被打到 \(O(1)\)，一次前向出全部候选； 但正因为头之间零依赖，Medusa 是「多模态碰撞」问题最极端的体现——上下文允许 "of course" 或 "no problem" 两种续写时，独立的头完全可能拼出 "of problem"。

2.2 MTP：给独立头接上一根线

MTP（Multi-Token Prediction，Gloeckle et al., 2024；后被 DeepSeek-V3 系统性采用并作为 生产投机解码的默认起草器）走的是另一条路：不再让 \(K\) 个头各自独立，而是把它们链起来。 以 DeepSeek-V3 的设计为例，第 \(k\) 个 MTP 模块的输入是「第 \(k-1\) 个模块的输出表征」与 「第 \(k-1\) 个未来 token 的 embedding」拼接后过一个 Transformer block，再复用共享的 LM head 投影出第 \(k\) 个未来 token 的 logits：

\[ h'_k = \mathrm{Block}_k\bigl([\,e(x_{t+k-1});\; h'_{k-1}\,]\bigr), \qquad \mathrm{logits}_{t+k} = W_{\text{lm}} h'_k + b \]

注意这个形状——「拼接前一位置的 token embedding 与前一步的表征，过一层网络，再投影」—— 和后面要讲的 EAGLE 几乎是同一张图纸。这不是巧合：只要你想让并行头之间有依赖， 最直接的办法就是把上一步的采样结果（或其 embedding）显式喂回去，MTP 和 EAGLE 都独立走到 了这一步。

2.3 MTP 的软肋：训练看到的是真值，推理喂的是自己的猜测

MTP 模块是在预训练阶段与主干联合训练的：损失函数里 \(e(x_{t+k-1})\) 用的是 ground truth 的下一个 token（teacher forcing）。但把它当作投机解码的草稿器使用时， 第 \(k\) 步喂进去的 \(x_{t+k-1}\) 必须是模块自己在第 \(k-1\) 步刚采样出的 token—— 训练分布和推理分布不一致（exposure bias）：模块从没在训练时见过「自己犯错后该怎么修正」这种输入。 一旦前面某一步采样偏了，链条后续的偏差会被放大，而模块本身对此毫无免疫力。

此外，MTP 模块是和主干模型联合训练的通用组件，通常只服务于「给预训练提供额外监督信号、顺便兼职做 投机解码」这个次要目标，深度和容量都比较保守（DeepSeek-V3 只用 1 个 MTP 模块，即 \(\gamma=1\) 的推测）， 很难深挖到 \(\gamma\){=}5、7 甚至更长的候选块。

方法 头间关系 \(T_{\text{draft}}\) 核心问题
外部 Draft Model 完整自回归 \(O(\gamma)\) 与目标模型零共享，命中率靠运气
Medusa 完全独立 \(O(1)\) 多模态碰撞最极端，块内零依赖
MTP 链式依赖 \(O(\gamma)\) 训练用真值、推理喂猜测，exposure bias

EAGLE 正是在看清这两条支线各自的病灶之后，把「链式依赖」这条路做到极致——它同样是自回归的， 但用两处专门的设计，逐一堵上 MTP 留下的两个缺口。

三、自回归支线的巅峰：EAGLE

先固定全篇要反复用到的一个玩具例子：词表 10 个 token {0:I, 1:love, 2:cats, 3:dogs, 4:to, 5:eat, 6:pizza, 7:very, 8:today, 9:<eos>}， 已确认前缀「I love」，草稿窗口长度 \(\gamma{=}3\)。目标模型在「I love」之后给出的分布 \(p(\cdot \mid \text{I love})\) 长这样：

tokencatsdogstoeatpizzavery其他
logit2.41.40.60.30.1-0.4更低
softmax51.6%19.0%8.5%6.3%5.2%3.1%6.3%

3.1 EAGLE 的两个部件

记 \(h_t \in \mathbb{R}^d\) 为目标模型在位置 \(t\)、LM head 之前那一层的隐藏状态， \(e(\cdot)\) 为词嵌入查表（与 \(W_{\text{lm}}\) 一样直接复用目标模型的，冻结不训）。 EAGLE 的草稿器只有两个部件——一个 \(2d \to d\) 的全连接层、一层 decoder——整个训练只训它俩：

\[ h^{(k)} = g\bigl([\,h^{(k-1)};\; e(x_k)\,]\bigr), \qquad x_{k+1} \sim \mathrm{softmax}\bigl(W_{\text{lm}} h^{(k)} + b\bigr) \]

沿用前缀「I love」（love 是上一轮确认的最后一个 token，\(h_I\)、\(h_{\text{love}}\) 都是目标模型上一轮前向算出来的真值）：

  • 第 1 步：\(g([h_{\text{love}}; e(\text{love})]) \to h^{(1)} \to\) LM head \(\to\) cats
  • 第 2 步：\(g([h^{(1)}; e(\text{cats})]) \to h^{(2)} \to\) LM head \(\to\) eat
  • 第 3 步：\(g([h^{(2)}; e(\text{eat})]) \to h^{(3)} \to\) LM head \(\to\) pizza

3 个 token = 3 次串行前向，草稿结果 cats | eat | pizza。这个结构和上一节的 MTP 骨架几乎一模一样，真正的分水岭在下面两处。

3.2 为什么必须喂 token embedding：边缘分布 vs 条件分布

假设不喂 \(e(x_k)\)，草稿器只拿到 \(h^{(k-1)}\)，那它要拟合的对象就是对所有可能取值求和的 边缘分布：

\[ p\bigl(h^{(k)} \mid x\bigr) = \sum_{u \in \mathcal V} p(y_k=u \mid x)\cdot p\bigl(h^{(k)} \mid x, y_k=u\bigr) \]

求和里第一项是「这一位取 \(u\) 的概率」，第二项是「已知这一位取了 \(u\) 之后，特征该长什么样」。 从 \(h_{\text{love}}\) 出发，cats 51.6%、dogs 19.0%、to 8.5%…… 每一个取值都会导出一条完全不同的后续分支，草稿器被迫去拟合这些分支混合起来的均值—— 一个天然更「糊」的目标。把 \(e(x_k)\) 喂进去之后，分支被显式确定，拟合对象重新变成单峰的 条件分布 \(p(h^{(k)} \mid x, y_k)\)。EAGLE 论文给出的实测数据是加速比从 1.9× 提到 2.8×——这一个改动几乎是全篇最大的单点收益。

这个「边缘 vs 条件」的区别是全文的主线：下一节 DFlash 的后缀衰减、再下一节 DSpark 的 Markov Head， 本质上都是同一个问题的不同解法。

3.3 Training-Time Test：补上 MTP 留下的 exposure bias 缺口

光有「喂 token embedding」这一步还不够——如果训练时喂的 \(e(x_k)\) 永远是 ground truth， 就会重蹈 MTP 的覆辙。EAGLE-3（Li et al., 2025）引入 Training-Time Test： 训练阶段完整模拟真实的推测解码 rollout，让草稿器在训练时就吃到「自己刚采样（或模拟采样）出来的」 token embedding，而不是干净的真值。这样草稿器学会的不是「假设前面全对该怎么预测」，而是 「不管前面对不对，都要给出此刻最合理的延续」——直接对齐推理时的真实分布，彻底堵上 MTP 的 exposure bias 缺口。

3.4 EAGLE-2 / EAGLE-3：树状验证与多层特征融合

在这两处地基之上，后续版本继续加固：EAGLE-2（Li et al., 2024）观察到「草稿树」比「草稿链」验证效率 更高——与其线性生成一条候选序列，不如动态展开一棵候选树，用一次前向验证多条分支，进一步提升 \(\tau\)；EAGLE-3 除了引入 Training-Time Test，还把目标模型多层（浅、中、深）的隐藏状态融合后 再喂给草稿器，而不只是用最后一层——更丰富的特征来源让草稿器能同时捕捉词法和语义层面的线索。

3.5 代价：\(T_{\text{draft}}\) 依然随 \(\gamma\) 线性增长

无论怎么加固，EAGLE 的起草过程本质上仍是链式的——预测第 \(k\) 步必须先有第 \(k-1\) 步的真实 （或采样）结果。这意味着 \(T_{\text{draft}} \propto \gamma\)：草稿窗口越长，起草耗时越接近线性堆叠， 很快会把验证阶段省下来的时间吃回去，因此 EAGLE 系草稿器只能用很浅的网络（通常 1 层）、 较短的 block。这正是并行支线一直想要解决的问题——只是它一直没能一并解决「块内依赖」， 直到 DFlash 才把并行做到接近可用的地步。

四、并行支线的突破：DFlash——像 Diffusion 一样一次成型

DFlash（Chen, Liang & Liu, 2026）的思路是：既然串行是因为「必须先有前一个 token 才能算下一个」， 那就用 MASK 占位符把未来位置先占上——这个结构和扩散模型几乎一一对应，论文标题就叫 Block Diffusion for Flash Speculative Decoding。

4.1 结构：锚点 + Mask，一次前向、块内双向注意力

输入是一个 anchor token（上一轮验证确认的最后一个 token）加上 \(\gamma\) 个 mask token， 块内使用双向注意力（is_causal=False），\(\gamma\) 个 mask 位置能看到完整上下文， 也能互相看见：

续用同一玩具例子，草稿器一次前向给出三组 logits（只列 top-3，实际是完整 10 维）：

排名\(U_1\)（第 1 位）\(U_2\)（第 2 位）\(U_3\)（第 3 位）
top-1cats (2.4)very (1.3)pizza (1.2)
top-2dogs (1.4)to (1.1)eat (1.0)
top-3to (0.6)eat (0.7)today (0.7)

三个位置各自独立取 argmax，得到 cats | very | pizza——草稿延迟从 \(O(\gamma)\) 降到了 \(O(1)\)。

4.2 KV 注入：把目标上下文焊进每一层，而不只是输入端

目标模型跑一次前向，每一层都会输出一份隐藏状态；DFlash 按固定层号（等间距、跳过第 0 层和最后 几层）挑出若干层，拼接后投影成紧凑的上下文特征，再拼进草稿模型每一层的 K、V：

\[ H_{\text{ctx}} = \mathrm{RMSNorm}\bigl(W_c\,[H^{(l_1)};\,\ldots;\,H^{(l_m)}]\bigr) \]

Query 只来自草稿 token 自身，目标特征仅仅是给掩码位置多提供的 KV 条目，绕过草稿器自身的 Q 投影和 FFN，开销很小。这和 EAGLE 的差别正在这里——EAGLE 只在输入端把目标特征拼进第一层， 信号往上走会逐层衰减；DFlash 让每一层都能直接读到。从数学上看，它的作用是把草稿分布 \(q\) 往目标分布 \(p\) 上拉，两者越贴近，\(\alpha=1-D_{TV}(p,q)\) 越高，接受率也就越高。 所以 DFlash 的两个设计正好分工：Mask 占位符负责快，KV 注入负责准。

「KV」注入的是什么？ 这里的「KV」指的是数据的存放形式，不是数据来源。\(k_{\text{ctx}}\) 是拿目标模型的隐藏状态、 用草稿模型自己的 \(W_K\) 投影出来的，和目标模型的 KV Cache 本身无关——这个「伪装成 KV」的手法， 后面第七节讲训练数据管线时还会再遇到一次，是同一个思路的两处不同应用。

4.3 反直觉：并行为什么反而赢了自回归

DFlash 的整体接受长度全面压过 EAGLE-3，这与「逐步自回归生成质量更高」的常规认知相悖。 原因在位置 1：预测第一个位置的 token，无论架构是因果还是并行，都只依赖目标模型 提供的上下文，差异纯粹来自架构容量。自回归草稿器延迟是 \(O(\gamma)\)，被迫做得很浅（通常 1 层）； 并行草稿器延迟 \(O(1)\)，能低成本堆到 5 层甚至更深。而投机解码是严格的前缀存活过程， 位置 1 一旦被拒，整块作废，杠杆最大。所以哪怕并行架构后面掉得厉害，全局接受长度 仍然更优。

4.4 代价：后缀衰减与多模态碰撞

差异不在草稿器这边——同一个网络、同一次前向，每个位置拿到的输入信息量完全一样。差异在它要对齐的 目标那边。验证永远是因果的，位置 \(k\) 比的是：

\[ \alpha_k = 1 - D_{TV}\bigl(p(\cdot \mid x, y_{<k}),\; q_k(\cdot \mid x)\bigr) \]

位置 1 两边条件集完全一样，不存在差距；位置 2 起，草稿器手上永远只有前缀，给出的最好也只能是 跨分支混合的边缘分布 \(p(y_2\mid x) = \sum_u p(y_1{=}u\mid x)\,p(y_2\mid x, y_1{=}u)\)， 熵天然高于任何单一分支，而它要对齐的恰恰是其中某一个分支；位置越靠后，草稿器要混合的分支越多、 分布越糊，目标模型那边条件却越加越多、分布反而越尖锐——两边越拉越远，这就是后缀衰减。

值得停下来想一层：块内明明是双向注意力，位置之间能互相看见，为什么还会拼出不连贯的组合？ 用一组数字看清楚：假设前缀「I love」下，位置 1、2 的真实联合分布有两个明显的峰：

组合联合概率
cats · to0.30 ← 峰
dogs · very0.30 ← 峰
cats · very0.22
dogs · to0.18

边缘化之后，位置 1 是 cats 0.52 / dogs 0.48，argmax 取 cats； 位置 2 是 to 0.48 / very 0.52，argmax 取 very。两个位置各自独立取 argmax，拼出 cats · very——概率只有 0.22，而两个真正的联合峰都是 0.30。 （这组数字是为说明现象构造的示意值，非真实论文数据。）

双向注意力让网络内部完全可以在隐藏层编码出联合分布 \(q(y_1,\ldots,y_\gamma \mid x)\)， 但它对外的输出接口是彼此独立的 logits 向量，每个至多是这个联合分布在该位置上的边缘—— 而边缘的 argmax 不等于联合的众数（mode）。所以问题的根源并不是「位置之间没有信息交流」， 而是采样时把这条交流硬生生切断了——这正是多模态碰撞的本质。

这个观察对后面理解 DSpark 至关重要：既然网络内部已经隐式编码了联合结构，只需要给采样过程 「开一个出口」，把「各位置独立取边缘 argmax」改成「按实际采到的前驱修正后续 logits 再采样」， 链式结构就能被找回来——而且几乎不需要额外的建模能力，只需要一个很轻的修正模块。

五、汇流：DSpark——把依赖还给草稿，把预算还给系统

走到这里，两条支线的病灶已经很清楚：自回归支线（EAGLE）依赖建模强，但 \(T_{\text{draft}}\) 线性增长；并行支线（DFlash）起草快、位置 1 强，但后段迅速衰减。DSpark（Cheng, Yu, Shao, Li, Xiong et al., DeepSeek-AI & 北京大学, 2026）的做法不是在两者之间取舍，而是把并行主干 和轻量串行修正拼在一起，同时再补一刀解决「验证多少」这个此前没人管的系统问题。

5.1 起草侧：并行骨干 + Markov Head

DSpark 保留 DFlash 的并行主干，一次前向出全块基础 logits \(U_1,\ldots,U_\gamma\)， 然后加一个极轻的串行头，从左到右为每一位的 logits 加一个依赖前缀的转移偏置：

\[ z_k(v) = U_k(v) + B(y_{k-1}, v) \]

\(B(y_{k-1}, \cdot) \in \mathbb{R}^{|V|}\) 可以想成一张 \(|V|\times|V|\) 转移表在「上一个词是 \(y_{k-1}\)」这一行查出来的修正向量。完整转移矩阵在 10 万词表下有 \(10^{10}\) 个元素，不可用， DSpark 用低秩分解 \(B=W_1W_2\)（秩默认 256）近似，实现上就是一个 embedding 查找表加一个线性投影， 存储和每步计算都很小。回到玩具例子：第 2 位主干本来判断 very(1.3) > to(1.1)， 但 Markov Head 读到上一位实际采到的是 cats，查表得到 \(B(\text{cats},\cdot)\) 给 to 加了 +1.2、给 very 减了 0.4，修正后 to(2.3) > very(0.9)， 草稿从 cats | very | pizza 被拉回 cats | to | eat——骨架是并行主干给的， 纠正是串行头给的，实测这个串行头带来的延迟开销只有 0.2%–1.3%，却能让一个仅 2 层的 DSpark 打赢 5 层的 DFlash。

5.2 验证侧：置信度头 + 硬件感知调度器

起草更准之后，另一个此前没人管的问题浮出水面：并行架构很容易吐出很长的草稿块，但不加区分地 验证全部 token，会在高并发场景下把宝贵的 batch 容量浪费在注定被拒绝的尾部上。DSpark 用一个 轻量置信度头预测「前面都过了的前提下，这一位也能通过验证」的条件概率 \(c_k\)， 前缀存活概率由链式法则累乘 \(a_k=\prod_{i\le k} c_i\)；再用一个硬件感知调度器， 结合当前系统负载与离线 profile 出的吞吐曲线 \(\text{SPS}(B)\)，把所有候选按存活概率全局排序， 贪心纳入直到边际吞吐开始下降——轻载时把空闲算力换成更长的草稿，重载时只验高置信前缀。

置信度不改变输出质量（目标模型仍是唯一裁判），只决定怎么分配验证预算——这正是 「Confidence-Scheduled」这个名字的含义。这两个机制的完整数学细节（置信度头的解析监督标签、 Sequential Temperature Scaling 校准、调度算法的非预见性证明、以及与 DeepSeek-V4 的工程整合） 在站内已经有一篇专题文章讲透，这里不再重复，感兴趣可以直接跳转： 《DSpark 深度解析：半自回归生成与置信度调度》。

七、训练与工程闭环：怎么产出一个又快又准的 Drafter

算法讲完，剩下全是数据和管道的事——这部分对应 vllm-project/speculators 的实践， 也是这条演化史里最容易被忽略、但决定「论文能不能落地」的一环。

7.1 训练目标里藏着的结论

以 DSpark 为例，三项损失加权求和，权重不是随手调的：

\[ \mathcal{L} = 0.1\,\mathcal{L}_{\text{ce}} + 1.0\,\mathcal{L}_{\text{tv}} + 0.1\,\mathcal{L}_{\text{conf}} \]

分布匹配损失 \(\mathcal{L}_{\text{tv}}\) 的权重是交叉熵 \(\mathcal{L}_{\text{ce}}\) 的 10 倍， 这不是调参偏好，是第一节 \(\alpha = 1 - D_{TV}(p,q)\) 的直接推论：最小化 \(L_1\) 距离 就是在直接最大化接受率。草稿模型的训练目标从来就不是「预测下一个正确 token」， 而是「让输出分布贴近目标模型」——这也是为什么单纯优化交叉熵训出来的草稿器，接受率往往不如 专门优化过总变差距离的版本。三项损失都乘一个指数衰减的位置权重 \(w_k \propto e^{-(k-1)/\lambda}\)，因为位置 1 的错误会作废整块，越靠前的位置权重越高。

7.2 数据只能在线产：为什么不能提前 dump 到硬盘

两个要求把「离线产数据、批量喂训练」这条路堵死了：一是草稿器要拟合目标模型在它自己输出 分布上的行为，所以训练用的回复必须由目标模型自己重新生成，数据集只能提供 prompt； 二是 EAGLE 系草稿器吃的是目标模型多层 hidden state，每个训练样本是「token 序列 + 多层隐藏状态」 的配对，而隐藏状态的体量比 token 大得多。更麻烦的是，只要目标模型换个版本或换个精度， 整个 dump 立刻作废；训练时再把这些数据读回来，又是一堵实打实的带宽墙。 唯一可行的路线是 produce → consume → free：每一批数据生成后立刻被训练消费、 随即释放，零陈旧、路径上完全没有持久化存储。

7.3 把 hidden state 伪装成 KV：复用 vLLM KVConnector 与 Mooncake

在线产数据意味着要在「目标模型做 prefill 的机器」和「训练草稿器的机器」之间实时传输隐藏状态， 而这条通路其实不需要重新发明——它和 vLLM 的 PD 分离（Prefill-Decode Disaggregation）架构长得 一模一样，只是把「D（Decode 实例）」换成了「Trainer」。speculators 的做法是直接复用 vLLM 已经打磨好的 KVConnector：

\[ \underbrace{[\text{block},\,\text{block\_size},\,\text{num\_heads},\,\text{head\_size}]}_{\text{KV Cache 布局}} \;\Longleftarrow\; \underbrace{[T,\,L,\,H]}_{\text{辅助激活栈}}, \quad \text{令 num\_heads}{=}L,\ \text{head\_size}{=}H \]

令 num_heads = L（目标模型层数）、head_size = H（隐藏维）， 辅助激活栈就严丝合缝地落进 KV 槽位，一个字节不用改——层轴被伪装成注意力头，于是无需 reshape、 无额外注意力计算；分页管理、块分配、槽位映射、生命周期全部沿用 KV Cache 现成的机制， 前缀缓存还自动生效（重复 prompt 不用重跑目标模型）。走了 KV 这条路，就自动继承了整个 KVConnector 生态。

后端选择 Mooncake 也不是因为「RDMA 比磁盘快」这种粗糙理由，而是需求写完后 只剩它满足全部约束：

硬性要求共享文件系统NCCL 集合通信裸 RDMAMooncake
跨节点，不假设共享 FS✗✓✓✓
按 key 寻址（生产者不知道谁何时消费）✗✗✗✓
单边读取，不占生产者 CPU✗✗✓✓
有界 + 可驱逐（背压可控）✗✗✗✓

集合通信要求固定通信域、锁步参与，而这里的传输是异步、动态、多对多的；裸 RDMA 传得动， 但寻址、生命周期、驱逐、背压全得自己重新写一遍。Mooncake 四条全中，而且 vLLM 做 PD 分离时 已经在生产里用它——架构完全对上：生产者池（目标模型 prefill）和消费者池（Trainer）跑在不同机器上， 中间用一个按 key 寻址的 KV store 异步传张量，这和 PD 分离是同一套基础设施。

7.4 三条命令看完整流程

产出的 config.json 里，配方和 checkpoint 是同一个对象，字段与训练参数一一对应， serving 引擎自动检测走哪条草稿路径；verifier 字段锁定了训练时对应的确切目标模型—— 草稿器和验证器是绑死的一对，换一个目标模型就得重训草稿器。这也是为什么第一节反复强调的 「无损」前提如此重要：草稿器的一切改动都不能绕开验证规则，否则丢掉的就不只是速度。

结语：一条支线走到头，另一条支线开始补课

回看这条演化史，会发现它并不是一条直线，而是两条互相纠正的支线：自回归支线一路把「依赖建模」 做到极致，从 MTP 的链式拼接到 EAGLE 的特征级自回归、再到 Training-Time Test 堵上分布偏移， 代价是起草延迟线性增长；并行支线一路把「起草延迟」压到极限，从 Medusa 的完全独立到 DFlash 的 KV 注入，代价是块内依赖被采样过程硬生生切断。DSpark 没有在两条支线里选边站， 而是看清了「双向注意力已经隐式编码了联合结构，只是采样接口把它掐断了」这一件事， 用一个几乎零开销的 Markov Head 重新打开这个出口——顺带把「验证多少」也从固定超参数 变成了一个感知系统负载的动态决策。

更值得记住的是最后一节：算法上的无损证明只是故事的一半，能不能真正把训练数据在线产出来、 能不能复用现成的 PD 分离基础设施而不是重新造轮子，往往才是一篇论文能否走进生产环境的 决定性因素。

自回归支线教会草稿器「怎么想」，并行支线教会草稿器「怎么快」——DSpark 的答案不是二选一， 而是让「想」和「快」分别只做自己最擅长的那一半工作。
