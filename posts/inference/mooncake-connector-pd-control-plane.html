Mooncake Connector 读码（一）：PD 分离里，vLLM 到底在编排什么

打开 mooncake_connector.py 的第一件事，不是去跟 TransferEngine 的 RDMA。 是先问：一次请求从 Prefill 算完，到 Decode 开始拉 KV，调度器手里交换的到底是什么。

PD 分离 Mooncake 推理框架

2026年8月14日 · 7 分钟 · 1880 字 · MOFANG

Prefill–Decode 分离把「算 prompt」和「逐 token 生成」拆到两套实例。 中间必须搬家的，是已经写好的 KV Cache。 很多人把这件事直接叫做「用 Mooncake」——名字没错，层级却容易混： Mooncake 仓库负责把字节从一块 NPU 搬到另一块；vLLM-Ascend 的 Connector 负责决定何时搬、搬哪些 block、搬完才能释放。

本系列对着 mooncake_connector.py 读。第一篇只走控制面：Scheduler 进程里的四个钩子。 Worker、ZMQ 握手、TransferEngine 的 batch_transfer_sync_read，放到后面几篇。

一、读码前先画地图：三层，不是一个名字

开源仓库里，「Mooncake」至少出现三次，职责完全不同：

层 在哪 管什么
vLLM 接口 上游 vLLM 的 KVConnectorBase_V1 规定 Scheduler / Worker 各有哪些钩子。Connector 必须实现它们，才能挂进引擎生命周期。
Connector vllm-ascend 的 kv_p2p/mooncake_*.py 何时传、传哪些 block、TP/PP 怎么切、握手端口、延迟释放。本文读的就是这一层。
Mooncake 本体 kvcache-ai/Mooncake Transfer Engine（高速搬运）+ Store（分布式 KV 池）。vLLM / vllm-ascend 不包含这份源码，运行时 import mooncake.engine。
  • 绿：Connector / vLLM 编排（本篇主色）
  • 蓝：Prefill / 生产 / 发送 / 延迟释放
  • 橙：Decode / 消费 / 拉取
  • 紫：Mooncake TransferEngine（本篇只标边界）
官方镜像会预装 Mooncake，不等于源码合进了 vllm-ascend。 Connector 里真正碰到本体的地方，目前几乎只有 from mooncake.engine import TransferEngine 以及 initialize(..., "P2PHANDSHAKE", "ascend", ...)。

二、门面类：一个进程只活一半

MooncakeConnector 几乎不做业务，只按 KVConnectorRole 分叉。 这是读后面所有方法前必须钉死的事实：Scheduler 进程没有 Worker 对象，Worker 进程没有 Scheduler 对象。 

class MooncakeConnector(KVConnectorBase_V1, SupportsHMA):
    def __init__(self, vllm_config, role, kv_cache_config=None):
        ...
        if role == KVConnectorRole.SCHEDULER:
            self.connector_scheduler = MooncakeConnectorScheduler(...)
            self.connector_worker = None
        elif role == KVConnectorRole.WORKER:
            self.connector_scheduler = None
            self.connector_worker = MooncakeConnectorWorker(...)

来源：vllm-ascend · mooncake_connector.py · MooncakeConnector.__init__（约 1453 行）

门面上的 Scheduler 方法全部 assert self.connector_scheduler is not None 再转发； Worker 方法同理。Pull 模型下，save_kv_layer / wait_for_layer_load 是空实现—— KV 不是按层推的。那是第四篇 Layerwise 的故事。

三、一次请求的控制面时间线

先把整条链画出来。本篇只走到橙色框里的「打包 meta」；紫色的 TE read 下一篇才展开。

四、Prefill：request_finished 为什么要 delay_free

Prefill 实例上，请求带着 do_remote_decode=True：意思是「我只负责把 prompt 算完，生成交给别人」。 引擎把状态推到 FINISHED_LENGTH_CAPPED 时，会回调 Connector。 

if (
    params is None
    or not params.get("do_remote_decode")
    or request.status != RequestStatus.FINISHED_LENGTH_CAPPED
):
    return False, None

...
delay_free_blocks = sum(computed_block_lens) > 0
if delay_free_blocks:
    self._reqs_need_send[request.request_id] = time.time()

return delay_free_blocks, dict(
    do_remote_prefill=True,
    do_remote_decode=False,
    remote_block_ids=computed_block_ids,
    remote_engine_id=self.engine_id,
    remote_request_id=request.request_id,
    remote_host=self.side_channel_host,
    remote_port=self.side_channel_port,
    ...
)

来源：vllm-ascend · MooncakeConnectorScheduler.request_finished（约 1848 行）

返回值是一个二元组：(要不要推迟释放 block, 传给对端的 dict)。 两个字段要一起读：

  1. 1
    delay_free = True

    Prefill 的 KV 还在本地 HBM 里。Decode 还没拉。 若此刻按普通请求回收 block，对端读到的就是脏数据或未映射地址。 所以把 request_id 放进 _reqs_need_send，等 Worker 侧收到 DONE_RECVING 再放——那是第二篇的 TaskTracker。

  2. 2
    dict 是 Decode 的寻宝图

    注意标志位翻转：Prefill 侧的 do_remote_decode 变成 Decode 侧的 do_remote_prefill=True。 同一份物理 KV，在两边用两个相反的动词描述「你该拉我」。

字段 Decode 拿它做什么
remote_block_ids 远端哪些 page 有数据。可能已经按 SWA / compress / Mamba 裁过。
remote_host / remote_port ZMQ 握手基址。真实 per-rank 端口 = 基址 + device_index。
remote_engine_id / remote_request_id 对上是哪台引擎、哪条请求，避免串单。
remote_ptp_size Prefill 的 TP。Decode 用来算 GQA 要拉几份 head。
remote_multi_nodes_meta_mapping 跨机时，port offset → 真实 host / engine_id。
本篇刻意不展开 _get_transfer_block_ids 和 sliding-window 裁剪。 它们改变的是「寻宝图里有哪些 block」，不改变交接协议本身。第三篇讲数据面时再对着这些函数读。

五、Decode 三连：从「有一张图」到「本步要拉」

上游（网关 / proxy / disagg 调度）把上面那个 dict 挂到 Decode 侧的 request.kv_transfer_params。 Decode Scheduler 每个 step 按固定顺序问 Connector 三件事。

① get_num_new_matched_tokens：拉多少，而且是异步

if params is not None and params.get("do_remote_prefill"):
    token_ids = request.prompt_token_ids or []
    actual = self._state_prefill_token_count(len(token_ids))
    params["num_computed_tokens"] = num_computed_tokens
    count = max(actual - num_computed_tokens, 0)
    if count > 0:
        return count, True   # True = 异步加载

return 0, False

来源：MooncakeConnectorScheduler.get_num_new_matched_tokens（约 1752 行）

返回的第二个布尔值是协议的关键：True 表示这些 token 的 KV 会在调度 step 之间异步灌进本地 cache， 引擎可以先分配 block，不必卡在传输完成。 若这里返回 (0, False)，后续两步根本不会把请求放进待拉队列。

② update_state_after_alloc：记下本地坑位

引擎已经为「外部即将填入的 token」分配了 page。 Connector 把「本地未哈希的 block」和远端寻宝图绑在一起，丢进 _reqs_need_recv。 

if params is not None and params.get("do_remote_prefill"):
    if params.get("remote_block_ids"):
        local_block_ids = blocks.get_unhashed_block_ids_all_groups() if num_external_tokens > 0 else []
        local_full_block_ids = blocks.get_block_ids() if num_external_tokens > 0 else tuple()
        self._reqs_need_recv[request.request_id] = (
            request, local_block_ids, local_full_block_ids, num_external_tokens,
        )
    params["do_remote_prefill"] = False  # 每个请求只触发一次传输

来源：MooncakeConnectorScheduler.update_state_after_alloc（约 1790 行）

最后一行把 do_remote_prefill 关掉，防止 preempt / 重调度时重复拉。 本地 local_block_ids 才是 TransferEngine 写入的 dst；远端 remote_block_ids 是 src。

③ build_connector_meta：本步唯一交给 Worker 的包裹

Scheduler 与 Worker 不共享 Python 对象。跨进程传递的是 MooncakeConnectorMetadata： 

class MooncakeConnectorMetadata(KVConnectorMetadata):
    def __init__(self):
        self.requests: dict[str, ReqMeta] = {}
        self.requests_to_send: dict[str, float] = {}
        self.reqs_in_batch: set[str] = set()

来源：MooncakeConnectorMetadata（约 1420 行）

build_connector_meta 把 _reqs_need_recv 转成 ReqMeta，再清空队列。 Prefill 侧同一函数还会带上 requests_to_send（那些 delay_free 的时间戳）， 让 Worker 知道「这些 block 还在等对端 ACK」。

ReqMeta 是控制面的终点。读它等于读「Decode Worker 开始拉之前手里已经有什么」：

ReqMeta 字段 来自哪里
local_block_ids 本步 alloc 的未哈希 page（dst）
remote_block_ids 及 host/port/engine Prefill request_finished 写下的寻宝图（src）
num_external_tokens ① 算出来、引擎据此 alloc 的外部 token 数
读码检查点（本篇过关题）： Prefill 为什么必须 delay_free？ do_remote_decode 和 do_remote_prefill 分别出现在哪一侧？ Scheduler 和 Worker 之间靠什么结构传递「拉谁、拉哪些 block」？

六、本篇故意没讲什么

控制面走通之后，下一跳是 Worker：把 KV tensor 的 data_ptr 注册进 TransferEngine， 再按 ReqMeta 向 Prefill 的 handshake 端口要元数据，最后 batch_transfer_sync_read。 那已经是数据面。把它们塞进第一篇，时序会糊成一团。

  • 第二篇 · register_kv_caches、SendingThread 的 ZMQ GET_META / DONE_RECVING、start_load_kv 如何拆成多次 pull。
  • 第三篇 · 连续 block 合并、GQA head 切片、PP layer 范围、传完后的 cat / NZ reformat。
  • 第四篇 · Hybrid 是精简 Pull；Layerwise 把方向反过来，变成每层 save_kv_layer 推送。
  • 第五篇 · 配置里的 use_ascend_direct 在 vllm-ascend 中没有分支；真正生效的是 Mooncake 编译选项与 protocol=ascend。
浅层说法是「用 Mooncake 传 KV」；深层说法是：vLLM 先在纸上完成一次延迟释放的交接，Mooncake 只负责按这张纸搬运。
